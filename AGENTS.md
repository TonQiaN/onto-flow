# AGENTS.md

OntoFlow is a local workbench: Actions wired into workflow graphs, each run getting its own workspace directory and its own DeepSeek Harness subprocess, each Action a session inside it. Read [CONTEXT.md](CONTEXT.md) before naming anything.

## Stance: no compatibility layers

- Do not preserve backward compatibility. Remove obsolete paths instead of adding compatibility layers, fallbacks, or migrations.
- Nothing outside this machine consumes OntoFlow, and there is no migration history to honor: `drizzle-kit push` applies `src/db/schema.ts` in place and no migration files are committed.
- Deleting a subsystem outright is the house precedent — [ADR-0005](docs/adr/0005-folders-not-tags.md) removed the tag tables, API, and components with no alias layer.

## Commands

Run everything from the repository root: `data/` resolves from `process.cwd()` in `src/db/index.ts`, `src/server/fs-safety.ts`, and `drizzle.config.ts`, so another working directory is another database. No external service has to be running — the engine is the `@deepseek-ai` npm closure booted inside a per-run subprocess ([ADR-0006](docs/adr/0006-deepseek-harness-as-execution-engine.md)). What must exist is the model credential: put `DEEPSEEK_API_KEY` in `.env.local` (gitignored) and export it before any command that runs a model. Credentials travel by reference name only: the value is picked from the Next process environment at spawn time and never enters a composition file, a log, or a run directory. Workflows that feed PDF inputs rely on Poppler's `pdfinfo`, `pdftotext`, and `pdftoppm` on `PATH` — Action sessions call them through the built-in `bash` tool ([ADR-0011](docs/adr/0011-bash-in-session-no-platform-preprocessing.md)).

```sh

npm run db:push     # drizzle-kit push; applies src/db/schema.ts in place, no migration files
```

### Checks

There is no git hook, no linter, and no formatter. The gate is GitHub Actions plus the commands above, and running them locally before you push is still your responsibility, because CI only tells you after the fact.

- `.github/workflows/ci.yml` runs on every pull request and on every push to `main`, and its two jobs are the merge gate. `check` is `npm ci → npm run typecheck → npm test → npm run build`; `e2e` builds a fresh `data/ontoflow.db` with `db:push` + `db:seed`, runs `npx playwright test` (the Playwright config starts the dev server), and uploads `test-results/` + `playwright-report/` on failure. Neither job has a model credential, so neither spends money. `npm test` includes `src/server/harness/composition-boot.test.ts`, which really boots a harness subprocess on the default composition, once with every default-on toggle off, once more with the search toggle on, and once with a sample contract Tool's generated wrapper included — no model call, no credential; on ubuntu the bash sandbox rung is the npm-distributed `landlock-run`, which the boot loads but never runs a command through — the kernel fence itself is exercised only by the paid smokes.
- `.github/workflows/smoke.yml` is not a gate: `workflow_dispatch` plus one scheduled run a day (`0 20 * * *` UTC) on macOS with `secrets.DEEPSEEK_API_KEY`, running `db:push`, `db:seed`, `smoke-harness`, then `smoke-engine`. It runs on macOS because the bash sandbox's kernel fence has only been exercised under Seatbelt, and it fails at the first step when the secret is missing rather than midway with `MISSING_CREDENTIAL`.
- `.github/workflows/claude.yml` is on-demand review: mention `@claude` in an issue comment, PR comment, or PR review; it needs `secrets.ANTHROPIC_API_KEY` and the Claude GitHub App, reads `.github/REVIEW.md` and then this file before acting, and may run only `npm run check` / `typecheck` / `test` / `build` / `npx vitest run`. `.github/REVIEW.md` is the shared checklist for Codex auto-review, `@claude`, and humans — this file's invariants regrouped by what to look at in a diff, each item naming the sentence here that owns the reason. `.github/pull_request_template.md` makes three sections mandatory: what changed, which commands ran, which REVIEW.md items were self-checked.
- **A convention that can be checked mechanically is a test, not prose.** `src/rules.test.ts` scans source text for the rules in this file: `force-dynamic` on every route, `handle()` and its four exemptions, no `await db.`, the client/server import boundary (`"use client"` files plus the directive-less shared modules under `src/app/` — `api/` excluded — and `src/components/`) and no `"use server"`, `ontoflow`-prefixed `globalThis` keys, `import "@/server/writers"` on restore routes and one registered writer per `EntityKind`, the list-envelope imports, the raw-`sql` allowlist, `LIKE … escape '\'`, exact `@deepseek-ai` pins, and the byte-identical skills trees. Its whitelists assert that today's exemptions are still exemptions, so fixing one means shrinking the list. A rule here changes in the same commit as that test and the matching REVIEW.md line; a rule the code stops obeying is deleted from all three.
- Run `npm run check` before declaring work done; add `npm run build` when the change touches `src/app/`, `next.config.ts`, or `tsconfig.json`, because `build` catches route and config breakage `typecheck` misses.
- `next.config.ts` carries two pins a dependency change breaks: a new native or server-only package must join `serverExternalPackages`, and the Turbopack `root` pin is what stops Next latching onto a lockfile outside the repository.
- Unit tests are `*.test.ts` under `src/` or `scripts/`; everything under `e2e/` is Playwright, and the two globs do not overlap. `vitest.config.ts` re-declares the `@/*` alias, so a service test that bypasses it cannot resolve `@/db`. The CI `check` job has no `data/` (it never runs `db:push`) and vitest files run in parallel workers, so a unit test swaps an in-memory database onto `globalThis.ontoflowDb` and creates every directory it needs itself (`recursive: true`); none opens `data/ontoflow.db`.
- Unit tests cover pure logic, non-obvious invariants, and the conventions above — from `src/lib/graph.ts` and `src/server/folders.ts` to `catalog.test.ts` and `rules.test.ts`; everything user-visible is covered by Playwright.
- `test:e2e` starts a dev server or attaches to whatever already listens on 3592 (`reuseExistingServer`), so confirm that server was launched from the repository root or you are testing another database. A user-visible change runs its one matching spec, not the suite. The CI `e2e` job runs the whole suite against a seeded database with **no run history**, and it is green: `monitor.spec.ts` and `documents.spec.ts` synthesize their own runs, events, usage, disk fixtures and archived plan in `beforeAll` (the same direct-SQLite pattern as `runs.spec.ts`) and remove them in `afterAll`, so every assertion is against its own fixture or the API payload — never against history that only exists locally.

### Test fixtures cost money, but they are reproducible

`db:seed` writes the five libraries, their folders, a v1 revision each, the `models` rows, the relation rows the three tiers need (`workflow_skills` / `workflow_tools` for the procurement workflow, `action_preloads` for its generate/review Actions), and the sample inputs under `data/samples/` — and nothing else: no runs, no run_events, no node_usage, no purchase_plans. `scripts/seed-resume.ts` and `scripts/seed-leetcode.ts` are part of the same seed list and are just as idempotent. The run history, archived documents, and cost figures exist only in the gitignored local `data/ontoflow.db`; no e2e spec reads them — each synthesizes its own fixture (see Checks).

- **The run history can be rebuilt.** `scripts/run-procurement.ts` and `scripts/run-resume.ts` regenerate it from scratch against the current engine, so losing `data/ontoflow.db` costs money and time rather than being unrecoverable. Rebuilding still means paid model calls — treat it as expensive, not as impossible. (This section used to say the fixture could not be regenerated; that was true of the opencode engine, whose runs no longer have any way of being reproduced.)
- E2E never starts a run that contains an Action node (that spends money) and never clicks 执行清理 / 确认删除 / 中止该运行; the cleanup panel is exercised only through `dryRun`. The one sanctioned run-starting shape is `parallel-runs.spec.ts`: an input→output workflow with no Action nodes costs nothing, still exercises the full engine lifecycle, and deletes its runs in teardown via `DELETE /api/runs/[id]`.
- E2E creates entities under a per-spec `e2e-` Chinese prefix and removes them in teardown through `cleanupByPrefix`, which skips `builtin` rows and re-checks the prefix. `settings.spec.ts` is the exception the rule cannot cover: settings are one document rather than named entities, so it saves the whole document in `beforeAll` and writes it back in `afterAll`.
- **Never assert a count, a first-page containment, or an exact row that real usage grows.** Fetch the API payload in the test and assert the DOM matches it. This bug class has now been fixed three times; the third time it was the run-detail spec asserting that the newest run was the procurement one.

## Conventions

- User-facing strings, error messages, code comments, and test names are Chinese; identifiers are English.
- Every API route body runs inside `handle()` from `@/lib/http`. Four do not: `api/monitor/stream` and `api/runs/[id]/events` return a raw SSE `Response`, and `api/models` and `api/documents` are one-statement GETs that predate the rule — do not copy them.
- **Name collisions are a database concern.** `handle()` maps `UNIQUE constraint failed` to 409, so writers never pre-check a name; folders are the exception, because SQLite cannot constrain a root level whose parent is NULL ([reason](src/db/schema.ts)).
- **Entity-body validation lives in the writer's `parse…Payload`** (workflow's is `parseGraphPayload`); a route hand-narrows only its own non-entity params. All of it is hand-written `typeof` narrowing — there is no schema library.
- **Write paths return a result object; the engine throws.** `runner.ts` turns a thrown error into `run_nodes.error` plus skipped downstream nodes. New service modules use `WriteResult` with `writeOk`/`writeFail` from `@/server/writers/types`; `folders.ts` and `revisions.ts` still carry private structurally identical `Result<T>` copies — converge on `WriteResult`, never add a fourth. `fs-safety.ts` and `monitor/cleanup.ts` throw deliberately and their callers map the throw.
- **better-sqlite3 is synchronous.** Drizzle calls end in `.get()` / `.all()` / `.run()`; never `await db.…`.
- Raw SQL goes through drizzle's `sql` tag — both spellings, `sql\`…\`` and `sql<T>\`…\`` — and only where the query builder cannot express the aggregate: `monitor/` (cleanup, health, metrics), `writers/list.ts` (the `LIKE` search), `engine/action.ts` (the per-session `SUM` rollup), `engine/events.ts` (the `json_extract` tool-name lookup), `revisions.ts` (`max(version_no)`), and `api/runs/route.ts` (the run-list totals); `src/rules.test.ts` pins that allowlist and asserts every listed file still needs it. User input inside `LIKE` is escaped and paired with `escape '\'`.
- Process-level mutable state is parked on `globalThis` under an `ontoflow`-prefixed key so HMR cannot lose it: `ontoflowDb`, `ontoflowCancelledRuns`, `ontoflowRunProcesses`, `ontoflowActiveRuns`, the usage-settlement maps, the skill-projection holds; `src/rules.test.ts` pins the prefix on every key. A module-level `const map = new Map()` is the bug this prevents.
- A server-module unit test assigns an in-memory database to `globalThis.ontoflowDb` and then `await import()`s the module under test; a static import reaches the real `data/ontoflow.db`.
- **There are no Server Actions.** Every mutation is a `fetch` to `/api/*`; new pages start with `"use client"` and load data in `useEffect`.
- Client code imports no runtime value from `@/server` or `@/db`. `import type` from `@/server/monitor/types` is the sanctioned exception, and that module's own `import type { NodeStatus, RunStatus } from "@/app/runs/lib"` is the one accepted reverse dependency.
- **Global settings are one JSON document in a single-row table**, validated whole at the write boundary in `src/server/settings.ts` and read once when a run starts — a change takes effect on the next run, and a running run holds the snapshot it started with. Besides the credential refs, MCP servers, and disabled tools, the document carries `toggles` — the global default of every toggleable composition row, five keys (`webSearch` / `fsSearch` / `strReplaceEditor` / `todo` / `compaction`, `DEFAULT_COMPOSITION_TOGGLES` in `src/lib/workflow-settings.ts`, a partial body fills the rest from the defaults, a non-boolean is 400) — and `defaultInstructions`, the text written to `<run>/home/AGENTS.md`, which upstream `agent-instructions` reads as the user-level `$DSH_HOME/AGENTS.md`, so every Action session gets it unconditionally (factory default `DEFAULT_INSTRUCTIONS`: the four runtime rules that used to be hardcoded in `runner.ts`; ≤ 64 KiB, an empty string is legal). The per-run composition gives `agent-instructions` a batch budget of both instruction limits plus a frame allowance (`INSTRUCTIONS_BATCH_MAX_BYTES` in `src/lib/workflow-settings.ts`), because upstream budgets `$DSH_HOME/AGENTS.md` and `workspace/AGENTS.md` together and, when the batch is over, silently omits the user-level file first. A paid script that temporarily changes this document installs and restores it through `replaceSettingsIfCurrent`; a user save made during the run wins instead of being overwritten by the script's stale snapshot. Credentials appear only as environment-variable names; the value is picked from the Next process environment at spawn time. An MCP `env` key whose name looks like a credential is refused, because that object is written verbatim into the run's composition file.
- **Settings have three tiers: the upper tier declares, the lower one narrows, and Action never toggles a plugin** ([ADR-0016](docs/adr/0016-three-tier-settings.md)). The global document is the baseline. A workflow owns `instructions` (written verbatim to `workspace/AGENTS.md`; an empty string becomes `# <workflow name>\n` so the file still exists; ≤ 64 KiB), `settings.toggles` (only the keys it overrides; unknown keys or non-booleans are 400), `settings.mcpServers` (a subset of global registry names by shape `MCP_SERVER_NAME_PATTERN`, not checked against the registry at save time — a name the registry no longer has is silently ignored at admission), a skill set (`workflow_skills`) and a Tool set (`workflow_tools`). An Action owns only what it picks inside those sets: `action_preloads` ⊆ the workflow's skill set and `action_tools` ⊆ its Tool set. Because an Action is still a shared library entity ([ADR-0010](docs/adr/0010-nodes-own-their-definition.md) is unimplemented), the ⊆ rule is enforced where the set is known, not on Action save: `parseGraphPayload` answers 400 naming the Action and the skill/Tool, and `resolveWorkflow` throws `WorkflowResolveError` (status 422, `issues[]`, the same shape as graph validation) at admission — `startRun` and the resume-match endpoint both map it. `workflows/[id]` PUT treats a missing `instructions` / `settings` / `skillIds` / `toolIds` as "keep the current value" (the canvas saves only the graph and must not empty the sets) and a present one as whole replacement. The merge is `effectiveToggles(global, workflow)` and `global-enabled ∩ workflow-subset` for MCP; both land in `runs.settingsSnapshot` (`RunSettingsSnapshot`: `global` / `workflow` / `effective`, instruction texts as sha256) in the same transaction as the `runs` row, which is what the run page's 设置快照 panel and the audit of "why did this run have `web_search`" read.
- **A globally disabled tool disappears from the session's tool list**, it does not fail when called. `tools.restrict` narrows the visible set and `tools.guard` covers tools registered after the session opened; the observable evidence is the tool's absence from `request/header`, not an error event. The deny list is one set: `disabledTools ∪ (the workflow Tool set's public names − this Action's visible public names)` (`toolFilterForAction`); every Tool in the workflow set is materialized and registered globally, and visibility is subtracted per session.
- **The plugin panel reports a derivation, not a live tree.** There is no long-lived harness host inside the Next process — every run boots its own subprocess — so "what is mounted right now" has no answer between runs. `/api/settings/composition` reports the composition the next run would boot from the **global** toggles alone (a workflow's overrides are not folded in — that answer lives in each run's `settingsSnapshot`) plus the last run's `cordis.yml` as it actually landed on disk. It also projects `PLUGIN_CATALOG` as `groups`: the ten `PLUGIN_GROUPS`, each row with its decision, entry id (a fixed id or `<prefix>*`), workflow-toggle flag, customization, and a mount state (`会挂载 / 按开关未挂 / 按开关已挂 / 不挂 / 备选 / 库 / 按运行生成 / 自有` — `按运行生成` is a prefix row, MCP servers or Tool plugins, with no instance in the preview composition; `自有` is a row of this repository's own code that is not a composition entry) derived from the same `runCompositionEntries` call with the current settings' toggles. Client code cannot import from `@/server`, so the catalog reaches the settings page only through this route; the page renders the ten groups (1–4 and 10 open, 5–9 collapsed) and never keeps its own grouping — `e2e/settings.spec.ts` asserts the DOM against the API payload group by group.
- **All five library list GETs return `{ items, total, page, pageSize }`**, built from `parseListQuery` + `selectLibraryPage` + `listEnvelope` in `src/server/writers/list.ts`. Every other GET defines its own shape.
- The five library pages reuse `src/components/library/`; no page grows its own tree, toolbar, folder picker, or revision panel. Their filter state lives in the URL through `use-library-query`, never in component state.
- Workflows never enter folders; gate every folder path on `isFolderEntityKind`, not an ad-hoc comparison ([ADR-0005](docs/adr/0005-folders-not-tags.md)).
- **Delete protection is per-owner and there are exactly four.** The four referenceable libraries answer 409 through `usedByNames()`; workflow DELETE has its own running-run guard; folder DELETE has its own name-collision guard; run DELETE refuses a running run with 409 through `deleteRun` in `monitor/cleanup.ts` — the destructive path stays in that one module. Do not add a fifth, and do not hand-write a reference join — `src/server/references.ts` is the only module that joins references, and its fact table is: Action ← `workflow_nodes.action_id`, Skill ← `workflow_skills`, Tool ← `workflow_tools`, Object Type ← `action_ports` + `workflow_nodes`. A Skill or Tool is referenced by a **workflow** (detail 「技能集」 / 「Tool 集」, href `/workflows/<id>/settings`), never by an Action: an Action's preloads and visible Tools are a selection inside a set the workflow already references, so they are not references and delete protection does not look at them.
- **Every entity write records a revision inside the same transaction**, capturing the complete definition including relations (an Action's ports, `preloadSkillIds` and `toolIds`; a Skill's `files`; a Tool's whole contract; a workflow's `instructions`, `settings`, `skillIds`, `toolIds`, nodes and edges), and rollback replays the same `write<Kind>()`; a route that can reach revision restore carries `import "@/server/writers";` or restore silently answers 501.
- Untrusted paths pass through `@/server/fs-safety` (`isWithinData` at the request boundary, `resolveWithinData` and `safeBasename` at use); the run subprocess reads and writes whatever is in its workspace.
- Ids are `crypto.randomUUID()` from the schema default; a caller supplies an id only when it must return that id before insert or preserve client-side edge references.
- **Nominal port typing is an edit-time rule, not a TypeScript one and not a runtime one.** Two ports connect only when their `objectTypeId` values are equal ([ADR-0002](docs/adr/0002-nominal-port-typing.md), amended by [ADR-0008](docs/adr/0008-artifacts-not-values.md)); ids stay bare `string`. Nothing checks at runtime that the artifact holds what its type claims — the only mechanical backstop is that a declared artifact must exist on disk.
- **The workflow graph is not a DAG.** Fan-out is one output port with several edges, synthesis is one input port with several edges, and an edge from an exit port back to an upstream Action is a legal cycle ([ADR-0009](docs/adr/0009-exit-ports-and-back-edges.md)). `classifyEdges` decides which edges are back edges by a stable DFS from the entry nodes, and that answer is load-bearing in three places: readiness ignores back edges (a node that waits on one deadlocks its own loop on the first pass), `downstreamOf` ignores them (or the closure swallows the whole cycle), and validation requires every back edge's target to declare a re-entry limit.
- **Every output port declares an artifact path, and a branching Action reports its exit.** Ports sharing an `exitName` form one exit; the data-plane result names the exit taken and only that exit's edges activate, the rest go dead and their downstream is skipped. Re-entry bumps the whole loop body's round together, and round N writes under `rounds/N/` so an earlier round is never overwritten.
- **A synthesis port waits for every incoming edge to settle, not for the first one.** Readiness on a port with several edges means all of them are satisfied-or-dead and at least one is satisfied. Treating "any edge satisfied" as ready lets a synthesis node start before its siblings finish and silently read a subset — observed as a six-critic report that only found five verdicts while all six were on disk.
- **A run with output nodes but none reached is a failure, not a success.** An unreached output node on an untaken branch is normal; all of them unreached means the run produced nothing.
- **A specialized invocation's durable business result lives in `run_results`, not in its cleanup-eligible workspace or event log.** A completion gate verifies the final artifact, then the engine writes its exact content and completion evidence in one transaction before marking the run successful. Workspace/event cleanup keeps it readable; deleting the run cascades it. Never put the full result in `runs.imports`, because run-list/detail APIs expose that metadata.
- **A specialized paid invocation pins behavior, not names.** Before admission it compares three digests with the reviewed seed pins in `src/lib/resume-match.ts`: (1) the workflow behavior digest — sha256 of the canonical JSON of `{ instructions, settings.toggles, settings.mcpServers (sorted), skill-set names (sorted), Tool-set public names (sorted) }` (`RESUME_MATCH_WORKFLOW_BEHAVIOR_SHA256`); (2) every participating Action's `{ name, prompt, rule, providerId, modelId, reasoningEffort, maxReentries, onExhausted, preloadSkillNames (sorted), toolPublicNames (sorted) }` (`RESUME_MATCH_ACTION_BEHAVIOR_SHA256`); (3) the validator Tool's contract digest `toolContractSha256({ publicName, description, parameters, output, timeoutMs, code })` from `src/lib/tool-digest.ts` (canonical JSON sorts object keys, so re-ordering a schema's keys is not a change). The workflow description and a Tool's display name are not part of any contract. Exact ports and topology alone cannot prove that an editable shared Action still performs the promised business task. The seed scripts throw and print old/new values when a pin no longer matches; re-pinning is an explicit review step whose PR description lists both values.
- **A canvas node is a reference to the shared Action**, so editing it from the canvas edits that Action everywhere ([ADR-0004](docs/adr/0004-canvas-edits-the-shared-action.md)).
- **A run freezes executable definitions at admission.** `resolveWorkflow` captures the graph's Object Types, complete Action/model/port definitions, the workflow's `instructions` and normalized `settings`, its skill set (`ResolvedSkillRef { id, name, slug }`) and full Tool rows, each Action's preloads (`ResolvedActionDefinition.preloads`) and visible Tool public names (`toolNamesByActionId`) in one event-loop turn; `startResolvedRun`, capability materialization, and every later Action node consume that same object instead of querying the shared libraries again. Editing a shared Action, Tool, or workflow setting after admission affects the next run, not an already admitted paid run. Skill directories remain the intentional live-symlink exception described below.
- Input and output node ports are always named `"value"`.
- **A Tool is an OntoFlow contract; the cordis wrapper belongs to the platform** ([ADR-0017](docs/adr/0017-tool-is-a-contract.md)). A `tools` row is `{ name (display, Chinese), publicName (`^[a-z][a-z0-9_]{0,63}$`, unique, and not one of `TOOL_RESERVED_PUBLIC_NAMES` in `tool-contract.ts` — the upstream built-in tool names plus `structured_output` / `run_code` / `web_fetch`, because a wrapper registering an upstream name fails the whole boot and a session-level `structured_output` would be shadowed — the name the model calls), description, parameters (object-root JSON Schema), output? (same, or null), timeoutMs? (positive integer or null), code }`, where `code` is an execute module: `export default async function execute(args, ctx: ToolContext)`. `ctx` is the small stable surface in `src/server/harness/tool-contract.ts` — `workspaceDir` / `runDir` / `tmpDir` / `dataDir` / `dbPath` (absolute), `cwd` (the calling session's), `env` (only the whitelisted names: credential refs, the model credential, `ONTOFLOW_DB_PATH` / `ONTOFLOW_DATA_DIR`), `signal`, and `run(command, { cwd?, timeoutMs? })` — and never a cordis Context. `code` may import `node:` builtins and this repository's dependencies (module resolution walks up from the run directory) but must not import `@deepseek-ai/*`; the writer rejects that at save time (its inline `FORBIDDEN_IMPORT` check; `toolCodeProblem` in `src/app/tools/tool-form.ts` is the client mirror) because it is a bare plugin in disguise. At admission `materializeToolPlugins` writes every Tool of the workflow's Tool set to `<run>/plugins/` as two files — `tool-<id>.execute.ts` (the code verbatim) and `tool-<id>.ts` (the generated wrapper: `name` / `inject = ["tools", "shell", "sandboxPolicy"]` / `apply` registering `publicName`, the schemas, `timeoutMs` only when non-null, `output.schema` `{}` when the contract declares none, and `render: (_args, value) => [{ type: "text", text: JSON.stringify(value) }]`) — and includes each wrapper by absolute path. Only `src/server/harness/tool-plugin.ts` knows the upstream registration shape; an upstream API drift is fixed there once, and `composition-boot.test.ts` really boots a composition carrying a sample contract Tool. `ctx.run()` goes through the same `workspace-write` sandbox as `bash` (`sandboxPolicy.resolve({ session })` + `ctx.shell.run`, default 60 s, capped at 120 s) and returns `{ stdout, stderr, exitCode, timedOut, sandbox: { mode, enforced, runnerFailed, denied } }`; a `SandboxUnavailableError` is folded into `runnerFailed: true, enforced: false, exitCode: null` rather than thrown, so a careful Tool gates on `enforced && !runnerFailed` (`run_python` does). File and network effects a Tool makes with Node APIs directly are not fenced by anything. External capability still goes through MCP, not through a Tool.
- **The JSON Schema subset is narrower than JSON Schema, and the write boundary is the gate.** A type array (`type: ["integer", "null"]`) is rejected by `objectSchemaProblem` in `src/server/writers/json-schema.ts` (mirrored client-side in `src/app/tools/tool-form.ts`) for both `parameters` and `output`, so it never reaches a run; omit the field instead of typing it nullable. Upstream `ctx.tools.register` validates only `output.schema`, not `parameters` — a bad parameter schema that slipped past the writer would surface at the model's first call, not at plugin load — which is why the writer, not the loader, owns this rule. The same subset governs an Action's data-plane schema, which `composeNodeScope` asserts at session creation.
- **A Skill is a directory owned by a workflow's skill set, projected to disk, and preloaded by the upstream slash gesture** ([ADR-0016](docs/adr/0016-three-tier-settings.md)). A `skills` row is `SKILL.md`'s body plus `skill_files` (path + bytes; ≤ 32 files, ≤ 1 MiB each, relative `/`-separated paths with no `.`/`..`/empty segments, no control characters, ≤ 200 chars, `SKILL.md` itself not allowed, a path cannot be both a file and another file's directory); PUT replaces the whole file list, so the editor submits it whole. `src/server/skill-library.ts` writes each Skill to `data/skills/<slug>/SKILL.md` plus `data/skills/<slug>/<path>`, writing the new version to `data/skills/.versions/<slug>-<stamp>/` and then swapping `data/skills/<slug>` — a symlink — onto it with one `rename`, so the path never has an instant in which it does not exist; the previous version directory is removed at once, or after the last admitted run holding the slug settles. A run symlinks the workflow's whole skill set into `workspace/.agents/skills/`, so every Action in the run sees every skill's name and description through `skill-filesystem` and loads what it judges relevant. Admission synchronously verifies and holds every projection until that run and subprocess fully settle; deleting an unlinked Skill removes its database row immediately but defers directory removal while any admitted run holds it, and a new admission cannot extend a pending deletion. A preload is not injection: `buildPrompt` puts one `/<slug>` line per preloaded skill before the task text (blank line between), and upstream `tool-skill`'s `agent/pre-step` listener expands the gesture into a `<skill_content>` block with source `skill-invocation` in the same step — exactly what a person typing `/skill-name` in the CLI gets; the trajectory panel labels it 「预载技能：<name>」. Preload costs the whole `SKILL.md` body in the session's first message, so the editors show `estimateTokens` next to each choice. Anything that must apply to every Action belongs in the workflow's `instructions` (`workspace/AGENTS.md`) or the global `defaultInstructions`.
- **The skill directory name is an id-stable ASCII slug, never the library name.** Upstream enforces `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` on skill names, and this repository names entities in Chinese — a Chinese name is dropped with nothing but a `warn` in cordis's in-memory log buffer (no exporter writes it to a file), so the skill silently never reaches the model. `skillSlug()` hashes the entity id so an active run's symlink survives a rename; the same slug is the frontmatter `name` and the name the preload gesture `/<slug>` invokes, while the current Chinese display name is prefixed onto the description the model actually matches on.
- A `models` row's `providerId` is a **dsh provider route**, not a vendor name: `llm-deepseek` registers exactly `deepseek-official`. Adding a model means `upsertModel` in `scripts/seed.ts` plus, for a route no adapter serves yet, a new entry in `runCompositionEntries`. No route writes `models`.

### The harness seam

Every rule here was learned the hard way while replacing opencode with dsh. Read the header comments of `src/server/harness/runtime.ts`, `src/server/harness/rpc/server.ts` and `src/server/engine/action.ts` before touching sessions, events, usage, or cancellation. A change on this seam also runs at least `smoke-harness`, or the PR says why it can skip it: CI has no credential, so only a paid smoke exercises a real model call.

- **One run, one subprocess, one workspace.** `executeRun` creates the run directory, spawns `node --import tsx src/server/harness/runner.ts <cordis.yml>`, and disposes it in a `finally`. There is no build step for server code: the subprocess loads the same TypeScript the Next process does.
- **Runs execute in parallel and are mutually independent.** Nothing serializes runs: cross-run state is keyed by runId on `globalThis` or lives inside the run's own directory, and anything new must follow suit. `startRun` is the only admission gate — at `MAX_CONCURRENT_RUNS` simultaneously running runs it answers 429 instead of queueing, because each run is a whole node+tsx+dsh subprocess; the external caller owns any queue.
- **The RPC plugin is named in the composition by absolute path, not by package name.** The cordis loader resolves bare specifiers from its own location inside `node_modules`, and this repository has no self-referencing symlink there, so a bare name fails at boot. `boot`'s `bareModuleBaseUrl` does not rescue it.
- **Pin every user-level root inside the run directory.** `skill-filesystem` defaults `agentsHome` to `~/.agents`, so a run will happily discover and load the machine owner's personal skills — observed in practice as an agent looping through unrelated skills and then failing to read their resources. The per-run composition pins both `dshHome` and `agentsHome` under the run's home directory; workspace isolation is not automatic. The one file that is meant to live in that home is `<run>/home/AGENTS.md`, written from the global `defaultInstructions` (`createRunWorkspace({ homeInstructions })`) — the machine owner's `~/.dsh/AGENTS.md` never reaches a run.
- **`TMPDIR` is pinned to `<run>/tmp` at spawn, and the spill root to `<run>/home/spill`.** Upstream `sandbox-local` lets `workspace-write` write to `os.tmpdir()`, which honours `TMPDIR`, so `launchRun` injects `TMPDIR=<run>/tmp` next to `DSH_HOME`: bash `mktemp`, Python `tempfile`, Poppler scratch files, `subprocess-local`'s full-output files and the sandbox's own temp root all land inside the run directory, go with it on cleanup, and count in the disk figures; unpinned, they scatter under `/var/folders`. `<run>/tmp` is a sibling of `workspace/`, never inside it. `spill-local` without `root` writes to a process-private directory under `os.tmpdir()`; the composition pins `root` explicitly under `home/` rather than the workspace, because spill files are not artifacts and must not be swept up by `glob` or read by a downstream node as an upstream product.
- **Every composition row is decided in three places, and `catalog.test.ts` keeps them agreeing** ([ADR-0013](docs/adr/0013-explicit-composition-headless-baseline.md)). `catalog.ts` (`PLUGIN_CATALOG`: decision, group, entry id, `mountedByDefault`, `workflowToggle`, one-line reason, customization) is the declaration, `composition.ts` is the executable list, and `docs/harness/NN-*.md` is the argued reason with the package string verbatim. The test asserts the default composition's entries are exactly the rows marked default-mounted, that `mountedByDefault: false` rows appear only under their toggle, that every package string appears in its group's file, and that `docs/harness/README.md`'s upstream version equals `UPSTREAM_VERSION`, the `package.json` pins, and every customization's `upstream.version`. Adding, removing, or re-deciding a row is all three files in one change, then `npm run check`; `composition-boot.test.ts` then really boots it. Three config keys are silently load-bearing: `spill-policy.maxInlineBytes` omitted means the policy is off, not defaulted; `tool-todo.allowParallelInProgress` and `tool-fs-search.sampleOverCapGlobResults` are required, and omitting either fails plugin load and takes the whole run down — the boot test is what catches that before a paid run does.
- **Compaction summary usage arrives on `compaction/summary`, not as a usage chunk.** `compaction-basic` makes the summarize call straight through `ctx.llm.stream()`, never through agent-loop, so the only accounting for it is that event's `usage`; `events.ts` bills it as `node_usage` row `compaction:<seq>` (session-unique, never collides with `turnN-stepM`, idempotent on replay) with variant `compaction` and the event's own provider/model, and the per-session `SUM` folds it into `run_nodes.cost` — the summary is not off the books, except when its commit phase fails: upstream then emits only an errored `compaction/end` and never `compaction/summary`, so that one paid call cannot be billed. `run_events` has a sixth type, `compaction` (`start` / `summary` / errored `end` / `prune`); a `tool/result` whose `surfaceOp.op` is `replace` is a pruned copy of a result already logged, so it is skipped or the call shows two completions.
- **DeepSeek search is off by default because it is off the books.** `web-search-deepseek` is a separate helper model request whose usage never passes `llm/stream` (the upstream source has no usage field), so `node_usage` and the cost page cannot see it: the search trio (`web` / `web-search-deepseek` / `tool-web`, search only, no fetch) mounts only when the effective `toggles.webSearch` is on — the global default is `false` and a workflow may override it in its own settings — and both the global settings page and the workflow settings page say so next to the switch. The other four toggles (`fsSearch`, `strReplaceEditor`, `todo`, `compaction`) default on; only rows the catalog marks `workflowToggle` can be overridden, and `catalog.test.ts` checks every key mounts exactly its rows.
- **Cap the steps of a node.** Upstream `agent-loop` has no step limit, so a looping agent burns tokens until the node's wall-clock timeout. Each session registers an `agent/pre-step` guard from `NODE_MAX_STEPS`; exceeding it ends the turn with no structured output, which fails the node.
- **stdout belongs to the protocol.** The per-run composition must never include a stdout logger; harness stderr goes to `<run>/logs/harness.stderr.log`.
- **Every Action session has `bash`, and every run input is materialized as a workspace file.** The composition mounts the upstream shell chain (`dsh-tool-bash` + `dsh-bash-sandbox` + `dsh-subprocess-local` + `dsh-shell-env`); `bash` is an unscoped built-in like `read`/`write`, and format conversion of inputs happens inside the Action session, never in the Next process ([ADR-0011](docs/adr/0011-bash-in-session-no-platform-preprocessing.md)). Files are copied verbatim; text/json inputs become `inputs/<nodeId>/<label>.md|.json`, and prompts reference paths only — `describeInput` throws on an inlined value rather than resurrect the silent-truncation path ([ADR-0012](docs/adr/0012-inputs-materialize-as-files.md)).
- **One sandbox policy covers bash and write/edit, at two different strengths.** `dsh-sandbox-policy` at `workspace-write` confines file writes of both families to the run workspace plus the system temp dirs, but only bash gets a kernel fence: its argv is wrapped by Seatbelt (`sandbox-exec`) and fails closed when the runner is unavailable, while write/edit go through `dsh-fs-sandbox`'s in-process path check — upstream calls it a policy fence, not a kernel boundary, and it never touches the runner. Reads and network are not confined for either family, and `dsh-user-approval` at `policy: "never"` auto-rejects escalation requests.
- **Pin `@deepseek-ai` versions exactly.** The npm dist-tag `latest` on these packages is stale; every dependency is pinned to the closure's version (`0.1.1-rc.2`), and a bare `npm install @deepseek-ai/...` will fetch the wrong generation.
- **思考强度 reaches the model only through the `agent/request` waterfall.** `AgentOptions` carries just provider/model/maxTokens, and the `GenerateOptions` handed to `llm/stream` is frozen — assigning to it throws mid-turn. The listener is registered on the session's own scope in `composeNodeScope`, so it is filtered to that agent and released with the session.
- **Overwrite the effort unconditionally.** agent-loop resolves the adapter default into the call config before the waterfall runs, so a "only set it when unset" guard never fires.
- **Structured output is a scope-registered tool, not a provider feature.** Each session registers its own `structured_output` with the real schema; two-phase commit on `tools/result` is what makes the captured value authoritative.
- Token usage arrives as one `usage` chunk per step and does not accumulate, so summing is correct — unlike opencode's repeated `message.updated`, there is no double-count hazard here. `outputTokens` already includes reasoning (the adapter takes `completion_tokens` verbatim), so never bill or total reasoning as an extra bucket.
- **Costs are CNY, computed at write time.** `src/server/pricing.ts` carries the official DeepSeek peak/off-peak price table; `node_usage.cost` prices each usage chunk by its own arrival time, `run_nodes.cost` accumulates per node, and an engine-generated `usage` run-event surfaces each Action's spend in the event log. Unknown models cost 0 — a zero on the cost page means "no price entry", never a guessed price. The `node_usage` unique key includes `run_id` because session ids are node ids and repeat across runs of the same workflow.
- **Session events must be written to SQLite as they arrive.** Both SSE endpoints poll the database and there is no in-process pubsub, so `onSessionEvent` writes `run_events` rows live; batching them until the node finishes makes the run page look frozen.
- **A declared artifact that is not on disk fails the node.** The model saying it wrote the file is not evidence; this is the only mechanical backstop the dual-channel result has ([ADR-0008](docs/adr/0008-artifacts-not-values.md)).
- **`cancelled` is a terminal state distinct from `failed`** and leaves `run.error` null; a prompt that throws after cancellation is cancelled, not failed.
- **A run never stays `running`.** Terminal state is written by `executeRun`, by `cancelRun`, by `failWholeRun`, and at process start by `reconcileOrphanRuns` through `src/instrumentation.ts`.
- **A subprocess disposal failure quarantines the run.** If `dispose()` cannot prove the child exited even after its termination escalation, keep the run in `activeRuns` and retain its process handle; file preview, cleanup, deletion, and new-run capacity must remain fail-closed until the Next process restarts and owns teardown. If both session close and process disposal are unconfirmed, keep that session's usage rollup live as well: late chunks must idempotently refresh `run_nodes` and its existing `usage` event until process exit is confirmed.
- Both SSE endpoints poll SQLite; there is no in-process pubsub, and the run stream ends only after three silent ticks past terminal state.
