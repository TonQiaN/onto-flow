# 工作流设置、Tool 与 Skill

修改设置、模型登记、能力集、预载、Tool 契约或 Skill 投影时读取；同时核对 [应用写入约束](application.md) 与 [Harness 接缝](harness.md)。

## 设置与可见性

- **Global settings are one JSON document in a single-row table**, validated whole at the write boundary in `src/server/settings.ts` and read once when a run starts — a change takes effect on the next run, and a running run holds the snapshot it started with. Besides the credential refs, MCP servers, and disabled tools, the document carries `toggles` — the global default of every toggleable composition row, five keys (`webSearch` / `fsSearch` / `strReplaceEditor` / `todo` / `compaction`, `DEFAULT_COMPOSITION_TOGGLES` in `src/lib/workflow-settings.ts`, a partial body fills the rest from the defaults, a non-boolean is 400) — and `defaultInstructions`, the text written to `<run>/home/AGENTS.md`, which upstream `agent-instructions` reads as the user-level `$DSH_HOME/AGENTS.md`, so every Action session gets it unconditionally (factory default `DEFAULT_INSTRUCTIONS`: the four runtime rules that used to be hardcoded in `runner.ts`; ≤ 64 KiB, an empty string is legal). The per-run composition gives `agent-instructions` a batch budget of both instruction limits plus a frame allowance (`INSTRUCTIONS_BATCH_MAX_BYTES` in `src/lib/workflow-settings.ts`), because upstream budgets `$DSH_HOME/AGENTS.md` and `workspace/AGENTS.md` together and, when the batch is over, silently omits the user-level file first. A paid script that temporarily changes this document installs and restores it through `replaceSettingsIfCurrent`; a user save made during the run wins instead of being overwritten by the script's stale snapshot. Credentials appear only as environment-variable names; the value is picked from the Next process environment at spawn time. An MCP `env` key whose name looks like a credential is refused, because that object is written verbatim into the run's composition file.

- **Settings have three tiers: the upper tier declares, the lower one narrows, and Action never toggles a plugin** ([ADR-0016](../../docs/adr/0016-three-tier-settings.md)). The global document is the baseline. A workflow owns `instructions` (written verbatim to `workspace/AGENTS.md`; an empty string becomes `# <workflow name>\n` so the file still exists; ≤ 64 KiB), `settings.toggles` (only the keys it overrides; unknown keys or non-booleans are 400), `settings.mcpServers` (a subset of global registry names by shape `MCP_SERVER_NAME_PATTERN`, not checked against the registry at save time — a name the registry no longer has is silently ignored at admission), a skill set (`workflow_skills`) and a Tool set (`workflow_tools`). An Action owns only what it picks inside those sets: `action_preloads` ⊆ the workflow's skill set and `action_tools` ⊆ its Tool set. Because an Action is still a shared library entity ([ADR-0010](../../docs/adr/0010-nodes-own-their-definition.md) is unimplemented), the ⊆ rule is enforced where the set is known, not on Action save: `parseGraphPayload` answers 400 naming the Action and the skill/Tool, and `resolveWorkflow` throws `WorkflowResolveError` (status 422, `issues[]`, the same shape as graph validation) at admission — `startRun` and the resume-match endpoint both map it. `workflows/[id]` PUT treats a missing `instructions` / `settings` / `skillIds` / `toolIds` as "keep the current value" (the canvas saves only the graph and must not empty the sets) and a present one as whole replacement. The merge is `effectiveToggles(global, workflow)` and `global-enabled ∩ workflow-subset` for MCP; both land in `runs.settingsSnapshot` (`RunSettingsSnapshot`: `global` / `workflow` / `effective`, instruction texts as sha256) in the same transaction as the `runs` row, which is what the run page's 设置快照 panel and the audit of "why did this run have `web_search`" read.

- **A globally disabled tool disappears from the session's tool list**, it does not fail when called. `tools.restrict` narrows the visible set and `tools.guard` covers tools registered after the session opened; the observable evidence is the tool's absence from `request/header`, not an error event. The deny list is one set: `disabledTools ∪ (the workflow Tool set's public names − this Action's visible public names)` (`toolFilterForAction`); every Tool in the workflow set is materialized and registered globally, and visibility is subtracted per session.

- **The plugin panel reports a derivation, not a live tree.** There is no long-lived harness host inside the Next process — every run boots its own subprocess — so "what is mounted right now" has no answer between runs. `/api/settings/composition` reports the composition the next run would boot from the **global** toggles alone (a workflow's overrides are not folded in — that answer lives in each run's `settingsSnapshot`) plus the last run's `cordis.yml` as it actually landed on disk. It also projects `PLUGIN_CATALOG` as `groups`: the ten `PLUGIN_GROUPS`, each row with its decision, entry id (a fixed id or `<prefix>*`), workflow-toggle flag, customization, and a mount state (`会挂载 / 按开关未挂 / 按开关已挂 / 不挂 / 备选 / 库 / 按运行生成 / 自有` — `按运行生成` is a prefix row, MCP servers or Tool plugins, with no instance in the preview composition; `自有` is a row of this repository's own code that is not a composition entry) derived from the same `runCompositionEntries` call with the current settings' toggles. Client code cannot import from `@/server`, so the catalog reaches the settings page only through this route; the page renders the ten groups (1–4 and 10 open, 5–9 collapsed) and never keeps its own grouping — `e2e/settings.spec.ts` asserts the DOM against the API payload group by group.

## Tool、Skill 与模型

- **A Tool is an OntoFlow contract; the cordis wrapper belongs to the platform** ([ADR-0017](../../docs/adr/0017-tool-is-a-contract.md)). A `tools` row is `{ name (display, Chinese), publicName (`^[a-z][a-z0-9_]{0,63}$`, unique, and not one of `TOOL_RESERVED_PUBLIC_NAMES` in `src/lib/tool-names.ts` — the upstream built-in tool names plus `structured_output` / `run_code` / `web_fetch`, because a wrapper registering an upstream name fails the whole boot and a session-level `structured_output` would be shadowed; nor prefixed `mcp__`, the MCP client's public-name namespace, where a collision drops that whole server's tool list at sync time — the name the model calls), description, parameters (object-root JSON Schema), output? (same, or null), timeoutMs? (positive integer or null), code }`, where `code` is an execute module: `export default async function execute(args, ctx: ToolContext)`. `ctx` is the small stable surface in `src/server/harness/tool-contract.ts` — `workspaceDir` / `runDir` / `tmpDir` / `dataDir` / `dbPath` (absolute), `cwd` (the calling session's), `env` (only the whitelisted names: credential refs, the model credential, `ONTOFLOW_DB_PATH` / `ONTOFLOW_DATA_DIR`), `signal`, and `run(command, { cwd?, timeoutMs? })` — and never a cordis Context. `code` may import `node:` builtins and this repository's dependencies (module resolution walks up from the run directory) but must not import `@deepseek-ai/*`; the writer rejects that at save time (`toolCodeProblem` in `src/lib/tool-names.ts`, which the Tool editor calls too — one implementation, both sides, no mirror) because it is a bare plugin in disguise. At admission `materializeToolPlugins` writes every Tool of the workflow's Tool set to `<run>/plugins/` as two files — `tool-<id>.execute.ts` (the code verbatim) and `tool-<id>.ts` (the generated wrapper: `name` / `inject = ["tools", "shell", "sandboxPolicy"]` / `apply` registering `publicName`, the schemas, `timeoutMs` only when non-null, `output.schema` `{}` when the contract declares none, and `render: (_args, value) => [{ type: "text", text: JSON.stringify(value) }]`) — and includes each wrapper by absolute path. Only `src/server/harness/tool-plugin.ts` knows the upstream registration shape; an upstream API drift is fixed there once, and `composition-boot.test.ts` really boots a composition carrying a sample contract Tool. `ctx.run()` goes through the same `workspace-write` sandbox as `bash` (`sandboxPolicy.resolve({ session })` + `ctx.shell.run`, default 60 s, capped at 120 s) and returns `{ stdout, stderr, exitCode, timedOut, sandbox: { mode, enforced, runnerFailed, denied } }`; a `SandboxUnavailableError` is folded into `runnerFailed: true, enforced: false, exitCode: null` rather than thrown, so a careful Tool gates on `enforced && !runnerFailed` (`run_python` does). File and network effects a Tool makes with Node APIs directly are not fenced by anything. External capability still goes through MCP, not through a Tool.

- **The JSON Schema subset is narrower than JSON Schema, and the write boundary is the gate.** A type array (`type: ["integer", "null"]`) is rejected by `objectSchemaProblem` in `src/server/harness/tool-schema.ts` — the shape half of it is `objectSchemaShapeProblem` in `src/lib/json-schema-shape.ts`, which the Tool editor calls too, so the rule has one implementation and no client mirror; the upstream `assertObjectJsonSchema` half stays behind the writer, because `@deepseek-ai` may only be imported under `harness/` — for both `parameters` and `output`, so it never reaches a run; omit the field instead of typing it nullable. Upstream `ctx.tools.register` validates only `output.schema`, not `parameters` — a bad parameter schema that slipped past the writer would surface at the model's first call, not at plugin load — which is why the writer, not the loader, owns this rule. The same subset governs an Action's data-plane schema, which `composeNodeScope` asserts at session creation.

- **A Skill is a directory owned by a workflow's skill set, projected to disk, and preloaded by the upstream slash gesture** ([ADR-0016](../../docs/adr/0016-three-tier-settings.md)). A `skills` row is `SKILL.md`'s body plus `skill_files` (path + bytes; ≤ 32 files, ≤ 1 MiB each, relative `/`-separated paths with no `.`/`..`/empty segments, no control characters, ≤ 200 chars, `SKILL.md` not allowed as a file nor as a top-level directory name, a path cannot be both a file and another file's directory, and duplicates and file/directory conflicts are compared after NFC + case folding because APFS is insensitive to both); PUT replaces the whole file list, so the editor submits it whole. `src/server/skill-library.ts` writes each Skill to `data/skills/<slug>/SKILL.md` plus `data/skills/<slug>/<path>`, writing the new version to `data/skills/.versions/<slug>-<stamp>/` and then swapping `data/skills/<slug>` — a symlink — onto it with one `rename`, so the path never has an instant in which it does not exist, and `createRunWorkspace` digests a skill through its real path so a rewrite during admission cannot mix two versions; the previous version directory is removed at once, or after the last admitted run holding the slug settles. A run symlinks the workflow's whole skill set into `workspace/.agents/skills/`, so every Action in the run sees every skill's name and description through `skill-filesystem` and loads what it judges relevant. Admission synchronously verifies and holds every projection until that run and subprocess fully settle; deleting an unlinked Skill removes its database row immediately but defers directory removal while any admitted run holds it, and a new admission cannot extend a pending deletion. A preload is not injection: `buildPrompt` puts one `/<slug>` line per preloaded skill before the task text (blank line between), and upstream `tool-skill`'s `agent/pre-step` listener expands the gesture into a `<skill_content>` block with source `skill-invocation` in the same step — exactly what a person typing `/skill-name` in the CLI gets; the trajectory panel labels it 「预载技能：<name>」. Preload costs the whole `SKILL.md` body in the session's first message, so the editors show `estimateTokens` next to each choice. Anything that must apply to every Action belongs in the workflow's `instructions` (`workspace/AGENTS.md`) or the global `defaultInstructions`.

- **The skill directory name is an id-stable ASCII slug, never the library name.** Upstream enforces `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` on skill names, and this repository names entities in Chinese — a Chinese name is dropped with nothing but a `warn` in cordis's in-memory log buffer (no exporter writes it to a file), so the skill silently never reaches the model. `skillSlug()` hashes the entity id so an active run's symlink survives a rename; the same slug is the frontmatter `name` and the name the preload gesture `/<slug>` invokes, while the current Chinese display name is prefixed onto the description the model actually matches on.

- A `models` row's `providerId` is a **dsh provider route**, not a vendor name: `llm-deepseek` registers exactly `deepseek-official`. Adding a model means `upsertModel` in `scripts/seed.ts` plus, for a route no adapter serves yet, a new entry in `runCompositionEntries`. No route writes `models`.
