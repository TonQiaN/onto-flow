# 运行、轮次与清理约束

修改图、调度、运行页面、事件/SSE、专用调用入口或清理路径时读取；会话协议、计费与子进程配置另见 [Harness 接缝](harness.md)，三层设置与 Skill 例外另见 [能力约束](capabilities.md)。

## 图、快照与终态

- **Nominal port typing is an edit-time rule, not a TypeScript one and not a runtime one.** Two ports connect only when their `objectTypeId` values are equal ([ADR-0002](../../docs/adr/0002-nominal-port-typing.md), amended by [ADR-0008](../../docs/adr/0008-artifacts-not-values.md)); ids stay bare `string`. Nothing checks at runtime that the artifact holds what its type claims — the only mechanical backstop is that a declared artifact must exist on disk.

- **The workflow graph is not a DAG.** Fan-out is one output port with several edges, synthesis is one input port with several edges, and an edge from an exit port back to an upstream Action is a legal cycle ([ADR-0009](../../docs/adr/0009-exit-ports-and-back-edges.md)). `classifyEdges` decides which edges are back edges by a stable DFS from the entry nodes, and that answer is load-bearing in three places: readiness ignores back edges (a node that waits on one deadlocks its own loop on the first pass), `downstreamOf` ignores them (or the closure swallows the whole cycle), and validation requires every back edge's target to declare a re-entry limit. **A re-entry waits for the whole loop body to settle.** When the back edge is satisfied, the reset is queued and applied only once none of the affected nodes is still executing, and those nodes cannot be scheduled while it is queued; resetting a node that is mid-flight makes the scheduler start its next round under the same node id, replacing the promise the executor is tracking — that execution then finishes into state that already belongs to the next round (its outputs and exit settle onto the wrong one) and its `finally` unhooks the new round, so the run can be declared finished while a session is still in flight. The re-entry count is charged when the reset is applied, not when it is queued; a cancel or a whole-run failure discards a queued one. **A node also has a total-round ceiling, `MAX_NODE_ROUNDS` (100, `src/lib/graph.ts`, same reason and same value as `MAX_REENTRIES`).** `maxReentries` bounds how often one back-edge target is sent back, not how many rounds a node accumulates: nested or overlapping bodies each stay inside their own limit while a node caught between them is reset again and again, until the trajectory panel cannot open (one session directory per round, `MAX_SESSION_FILES` = 128). The check sits where the next round number is assigned and runs over the whole affected set before anything is mutated. Exceeding it takes the same path as re-entry exhaustion and lands on the **target**: its `run_nodes` row becomes failed with the message and the moment, the message goes into the scheduler closure's `firstError`, and from there the ordinary failure path applies — no new node starts, in-flight rounds settle on their own round, pending nodes get their `skipped` round, and the run ends failed. No round row is added (the re-entry is what was refused; no round ever opened) and the node whose success satisfied the back edge stays `success` — blaming the source would rewrite a round that really did succeed. Do not call `failWholeRun()` here: it only writes database rows, so with `firstError` unset and nothing thrown the in-memory scheduling continues, the completion gate still runs, and `writeTerminalState` rewrites the failure back to success.

- **Every output port declares an artifact path, and a branching Action reports its exit.** Ports sharing an `exitName` form one exit; the data-plane result names the exit taken and only that exit's edges activate, the rest go dead and their downstream is skipped. Re-entry bumps the whole loop body's round together — each node to **its own** next unused number, never to "the re-entered node's round + 1", or nested loops push a node back onto a round it already used and collide on the round row's unique key — and round N writes under `rounds/N/` so an earlier round is never overwritten. Every execution of every node is one `run_node_rounds` row, input, output and skipped nodes included ([ADR-0018](../../docs/adr/0018-run-page-frozen-graph-replay.md)); `run_nodes` stays the node's latest-state row and no longer carries the round history.

- **A synthesis port waits for every incoming edge to settle, not for the first one.** Readiness on a port with several edges means all of them are satisfied-or-dead and at least one is satisfied. Treating "any edge satisfied" as ready lets a synthesis node start before its siblings finish and silently read a subset — observed as a six-critic report that only found five verdicts while all six were on disk.

- **A run with output nodes but none reached is a failure, not a success.** An unreached output node on an untaken branch is normal; all of them unreached means the run produced nothing.

- **A specialized invocation's durable business result lives in `run_results`, not in its cleanup-eligible workspace or event log.** A completion gate verifies the final artifact, then the engine writes its exact content and completion evidence in one transaction before marking the run successful. Workspace/event cleanup keeps it readable; deleting the run cascades it. Never put the full result in `runs.imports`, because run-list/detail APIs expose that metadata.

- **A round row has a skeleton and a payload; the wire carries the skeleton and event cleanup takes only the payload.** The skeleton — round, session, start/finish, terminal state, exit, error — is tens of bytes and is what the replay degrades to once the events are gone. `/api/runs/[id]` and every SSE `snapshot` frame carry **only** the skeleton, for `nodes` as well as `rounds` (`listNodeSkeletons` / `listRoundSkeletons` in `src/server/run-rounds.ts`; the round select names the skeleton columns rather than fetching the payload and dropping it, and `run_nodes` has no payload column at all — the payload lives on the round row only, which is the round the drawer wants anyway; `RunNodeRow` in `src/app/runs/lib.ts` is the matching type, and the trajectory route reads the node's latest still-kept round snapshot server-side for its skill-name map), and the drawer asks for one round's `{ inputs, outputs, snapshot }` at a time through `GET /api/runs/[id]/nodes/[nodeId]/rounds/[round]` when its inputs-outputs or snapshot tab opens or the cursor moves to another round — a snapshot carries the whole rendered prompt and every preloaded skill's body, and a looping run copies it per round, so hanging it off a frame that repeats every 500 ms pushes the same large object at the page over and over. `cleanup.ts`'s `events` target deletes `run_events` and nulls `inputs` / `outputs` / `snapshot` on `run_node_rounds` rows — never the rows themselves; only the `runs` target (and `deleteRun`) removes them, by cascade. Blanking eligibility is per **run** (terminal, and `finished_at` older than the cutoff), never "this run has old event rows": a free input→output run writes no `run_events` at all, and so does an Action that fails before its first event, so deriving the run set from events would leave their payloads in the database forever and invisible in the preview. Both the preview and the real pass read the blanked-row counts from the same queries, which is what `dryRun` promises. A blanked column comes back as `null`, the same shape as "this round never had one", so the drawer explains both with one sentence; a blanked snapshot costs the trajectory panel its skill-name mapping and it falls back to slugs, which is the accepted price.

- **A specialized paid invocation pins behavior, not names.** Before admission it compares three digests with the reviewed seed pins in `src/lib/resume-match.ts`: (1) the workflow behavior digest — sha256 of the canonical JSON of `{ instructions, settings.toggles, settings.mcpServers (sorted), skill-set names (sorted), Tool-set public names (sorted) }` (`RESUME_MATCH_WORKFLOW_BEHAVIOR_SHA256`); (2) every participating Action's `{ name, prompt, rule, providerId, modelId, reasoningEffort, maxReentries, onExhausted, preloadSkillNames (sorted), toolPublicNames (sorted) }` (`RESUME_MATCH_ACTION_BEHAVIOR_SHA256`); (3) the validator Tool's contract digest `toolContractSha256({ publicName, description, parameters, output, timeoutMs, code })` from `src/lib/tool-digest.ts` (canonical JSON sorts object keys, so re-ordering a schema's keys is not a change). The workflow description and a Tool's display name are not part of any contract. Exact ports and topology alone cannot prove that an editable shared Action still performs the promised business task. The seed scripts throw and print old/new values when a pin no longer matches; re-pinning is an explicit review step whose PR description lists both values.

- **A run freezes executable definitions at admission.** `resolveWorkflow` captures the graph's Object Types, complete Action/model/port definitions, the workflow's `instructions` and normalized `settings`, its skill set (`ResolvedSkillRef { id, name, slug }`) and full Tool rows, each Action's preloads (`ResolvedActionDefinition.preloads`) and visible Tool public names (`toolNamesByActionId`) in one event-loop turn; `startResolvedRun`, capability materialization, and every later Action node consume that same object instead of querying the shared libraries again. Editing a shared Action, Tool, or workflow setting after admission affects the next run, not an already admitted paid run. The canvas graph is frozen the same way: `buildRunGraph(resolved)` goes into `runs.graph` in the same transaction as the `runs` row, and the run page draws only that ([ADR-0018](../../docs/adr/0018-run-page-frozen-graph-replay.md)) — a run outlives the next edit of the workflow, so following it on the live canvas is only ever right for a run still in flight. Skill directories remain the intentional live-symlink exception described in [能力约束](capabilities.md).

- **One run, one subprocess, one workspace.** `executeRun` creates the run directory, spawns `node --import tsx src/server/harness/runner.ts <cordis.yml>`, and disposes it in a `finally`. There is no build step for server code: the subprocess loads the same TypeScript the Next process does.

- **Runs execute in parallel and are mutually independent.** Nothing serializes runs: cross-run state is keyed by runId on `globalThis` or lives inside the run's own directory, and anything new must follow suit. `startRun` is the only admission gate — at `MAX_CONCURRENT_RUNS` simultaneously running runs it answers 429 instead of queueing, because each run is a whole node+tsx+dsh subprocess; the external caller owns any queue.

- **Session events must be written to SQLite as they arrive.** The run SSE endpoint polls the database and there is no in-process pubsub, so `onSessionEvent` writes `run_events` rows live; batching them until the node finishes makes the run page look frozen. Every row carries `session_id`, written by `events.ts` from `ctx.sessionId` — that is what puts an event on its round in the replay; the column is nullable only for rows written before ADR-0018.

- **A declared artifact that is not on disk fails the node.** The model saying it wrote the file is not evidence; this is the only mechanical backstop the dual-channel result has ([ADR-0008](../../docs/adr/0008-artifacts-not-values.md)).

- **`cancelled` is a terminal state distinct from `failed`** and leaves `run.error` null; a prompt that throws after cancellation is cancelled, not failed.

- **A run never stays `running`, and neither does a round.** Terminal state is written by `executeRun`, by `cancelRun`, by `failWholeRun`, and at process start by `reconcileOrphanRuns` through `src/instrumentation.ts`. Each of those four paths — plus `runner.ts`'s catch around a throwing `runActionNode` — also settles the `run_node_rounds` rows through `engine/rounds.ts`: the still-`running` rows take the matching terminal state, and every node the path bulk-skips gets one zero-duration `skipped` round. `runActionNode` opens its skeleton row (running + startedAt + inputs, snapshot filled in later) as its very first statement, ahead of anything that can throw, so "failed before the session opened" is still a segment on the timeline instead of a node stuck at 等待, and it settles that row through `settleRoundIfRunning` — cancellation can land while the Action is still awaiting `sessionOutput` / `closeSession`, and an unconditional success would overwrite the `cancelled` `cancelRun` already wrote. The reverse order needs the opposite: when the success lands first and the cancel arrives before `runOne`'s post-await check, `closeRunningRounds` finds no `running` row, so `runner.ts`'s cancel branch rewrites that round to `cancelled` **unconditionally**, in the same place it writes `run_nodes`. The two sites are deliberately opposite — a node and its round must agree on the terminal state, or the replay paints a cancelled node over a successful segment.

- **A subprocess disposal failure quarantines the run.** If `dispose()` cannot prove the child exited even after its termination escalation, keep the run in `activeRuns` and retain its process handle; file preview, cleanup, deletion, and new-run capacity must remain fail-closed until the Next process restarts and owns teardown. If both session close and process disposal are unconfirmed, keep that session's usage rollup live as well: late chunks must idempotently refresh `run_nodes` until process exit is confirmed.

- The run SSE endpoint polls SQLite; there is no in-process pubsub, and the run stream ends only after three silent ticks past terminal state.
