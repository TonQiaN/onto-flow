# 02 模型的手脚

> 默认方向：跟上游，去掉要理由。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这组是模型在会话里**做事**用的一切：读写文件（`ctx.fs` 四层栈）、看图（附件存储）、跑命令（`ctx.shell` 与它背后的子进程 seam）、把命令与文件写入圈在工作区里的围栏（沙箱三件与审批）、按模式发现与编辑文件（`glob` / `grep`、`str_replace_editor`）、按需加载技能（`ctx.skills` 三件）、连外部 MCP 服务器、联网搜索（`ctx.web` 三件套）；以及上游同一层里我们没挂的四族：Code Mode、持久 PTY、LSP、匿名 HTTP 抓取。判据是「模型在这一步能调用什么、调用后世界怎么变」——一行只要改变模型可见的工具清单、工具结果或围栏，就归这组。

本项目对这组的取舍建立在三条事实上，下面每一行的理由都能回溯到其中至少一条。**其一，运行中没有人**：审批只能是确定性的拒绝，任何「问人再决定」的路径都不存在。**其二，一次运行一个子进程、一个目录**（ADR-0007）：上游所有默认落在用户 home 或系统临时区的根——`DSH_HOME`、`~/.agents`、`os.tmpdir()`——都必须钉进运行目录，否则运行之间互相可见、机器主人的私有技能会被运行发现（实测出过事）、临时文件逃出清理范围。**其三，用量必须归节点**：一个 Action 的每一笔模型支出都要落到 `node_usage`，任何绕过 `llm/stream` 的辅助模型请求默认不开。

总体结论：与 headless 基线一致的行**全部挂**——文件栈、附件、子进程、shell 链、沙箱三件、审批、`glob`/`grep`、编辑器、技能三件；与基线的差异都在对应行里论证，改变模型可见面或围栏的有六处：审批固定 `never` 而不是 `ask`；`bash` 关掉 `run_in_background`（ADR-0014）；搜索三件套默认关、可按工作流打开（账外支出）；MCP 按全局登记逐台挂、只挂工作流勾选的子集、连接失败不失败整棵树；一切根钉进运行目录；headless 会挂的 Code Mode 运行时不挂。另有两处只改数值不改可见面：`bash` 超时取包默认 120 s 而不是 base 的 60 s，技能目录的 watcher 关闭。持久 PTY、LSP、匿名抓取上游 headless 本来也不挂，本项目同样不挂，但各有本项目自己的理由，不靠「基线没有」一句话带过。围栏的边界要先说清（ADR-0011）：`bash` 与 `write`/`edit` 共用一份 `workspace-write` 策略，文件写入被圈在工作区加临时根；bash 有 Seatbelt 内核围栏、runner 缺席即拒绝执行，write/edit 只有进程内路径检查；**read 与网络在任何模式下都不受限**，这是上游沙箱词汇自己划的边，工作区目录在本项目也只定义协作范围与文件所有权，不是安全边界。

## 逐行

### `@deepseek-ai/dsh-fs`
- **seam 角色**：Service Definition（`ctx.fs`；同时拥有 `fs/*` 政策事件词汇）
- **决定**：挂（库，不是组合行）
- **它给会话带来什么**：不直接可见。`read` / `write` / `edit` 的路径解析、UTF-8 文本读写、原子写入与字面量编辑都经它定义的十二个原语；工具层只渲染它返回的文本与结构化错误码（`FS_NOT_FOUND`、`FS_STALE_VERSION`、`FS_NOT_OBSERVED` 等）。
- **理由**：文件系统栈在上游是四层拆分——工具（`tool-fs`）、政策（`fs-observation-policy`）、提供方约定（本包）、提供方（`fs-local` / `fs-sandbox`）——这一层是让「换 provider 不换工具」成立的契约：ADR-0011 把 `fs-local` 换成 `fs-sandbox`，工具层与政策层一字未改，靠的就是两者都只依赖 `ctx.fs` 的原语与 `fs/*` 事件。它是抽象类，由 provider 包 peer-depend 装载，没有自己的组合行；写进目录是为了让这个 seam 在审查记录里有名字，升级时知道「提供方换了、契约有没有变」要看哪个包的 README。上游明言约定只支持文本、只有十二个原语（无删除、重命名、递归列目录）、没有 I/O deadline；本项目对文件的删除与移动走 `bash`，正是这些限制的自然出路。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-fs-sandbox`
- **seam 角色**：Service Provider（`ctx.fs`）
- **决定**：挂
- **它给会话带来什么**：政策归属方（`sandbox-policy`）贡献一条与具体能力无关的 `sandbox:policy` 运行时上下文；被拒绝的 `write` / `edit` 由 `tool-fs` 渲染成 `[sandbox: file access denied under <mode> mode]` 标记与同轮次升级提示。`read` 在任何模式下直通。
- **理由**：上游 base 挂的就是它（base 里 `fs-sandbox` 行；`fs-local` 不在 base，见组 9）。它继承 `LocalFileSystem` 的全部文本机制，只给 `writeText` / `editText` 加按调用模式的围栏；可写根从 `writableRoots` 派生——与 Seatbelt profile 同一个函数——所以文件围栏与 bash runner 不会漂移，「bash 与 write/edit 共用一份 workspace-write 策略」这句 ADR-0011 的前提在上游是同一来源保证的。它自称「策略围栏，不是内核边界」：在可信代码里检查模型控制的路径，写前重新规范化把 TOCTOU 缩到最小但不消除，对抗性宿主进程不在范围内。本项目接受这个威胁模型：工作区目录只定义协作范围与文件所有权，不是安全边界（ADR-0011）；真正要守住的边界——`data/` 的其它运行目录——由 bash 的内核围栏与 write/edit 的路径检查同时覆盖。上游要求 `ctx.sandboxPolicy` 已组合，否则「后端不会实施约束」，这是 `sandbox-policy` 不可省的原因之一。
- **配置要点**：上游默认（无 config）。`cwd` 默认 `process.cwd()`，而子进程 spawn 时 cwd 就是工作区；且工具层每次调用都传入调用会话的 cwd（`session.header.cwd`，即工作区），所以相对路径的解析根与 bash 一致，无需在组合里另钉。围栏根按会话 cwd 解析，只有没有会话的调用才回退到部署策略的 `workspaceRoot`。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-fs-observation-policy`
- **seam 角色**：策略插件（不注册服务；`fs/write-intent`、`fs/edit-intent` 的单槽决策器与 `fs/observed` 的记录器）
- **决定**：挂
- **它给会话带来什么**：不加提示词、不加 schema。没读过就 `edit`，得到 `FS_NOT_OBSERVED` 与精确消息 `edit requires reading "<path>" first`（`tool-fs` 追加 `read the file, then retry`）；读过之后文件被别人改了，带防护的写/编辑报 `FS_STALE_VERSION`（追加 `re-read the file, then retry`）。`tool-fs` 的 write / edit 指导里那句 `read an existing file first (the default fs-observation-policy requires it)` 就是以它在场为前提写的。
- **理由**：上游 base 挂；`tool-fs` 的 README 明言「加载这些工具的部署也应加载该插件」。它是可选的——省略后 write/edit 退化为无条件覆盖，工具照常工作——所以要说清本项目留它的实际收益：一次运行里扇出的几个 Action 共用一个工作区（ADR-0008 的产物文件都在那里），两个会话同时写同一个文件时，版本防护让「一方胜出、一方陈旧」成为可见的错误，而不是静默互相覆盖；上游写明防护「不与方法耦合、可平稳增删」，恰好意味着去掉它模型看到的指导与实际行为会对不上，而模型并不知道。上游列的限制在本项目里都不成立问题：观察状态不跨会话恢复（每个 Action 都是新会话），直接 `ctx.fs` 读取不发 `fs/observed`（本项目的输入与产物都经 `read` 工具读）。
- **配置要点**：上游默认（无 config）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-fs`
- **seam 角色**：Consumer（`read`、`read_image`、`write`、`edit` 四个工具与其执行器）
- **决定**：挂
- **它给会话带来什么**：四个工具与三段独立注册的指导——`Use the read tool — not shell commands like cat…`、write 指导、edit 指导；限制隐藏 schema 也不移除这些段。`read` 结果是 `<path>…</path>` 加带行号的 `<content>` 窗口，默认最多 2000 行、每行 2000 字符、51200 字节，footer 提示 `offset` 续读。`read_image` 读 PNG / JPEG / WebP / GIF，经附件存储持久化后作为原生图像块返回，只在当前路由的模型声明 `image` 输入时成功，否则精确报错 `model "<model>" does not declare image input; switch to an image-capable model to read images`。
- **理由**：这是所有 Action 的基础工具，也是 ADR-0008 与 ADR-0012 的执行面：连线只生成「去读哪个文件」，输入物化为 `inputs/<节点id>/…` 文件，全部要靠 `read` 读回来；产物靠 `write` 写出，没写出来是唯一的机械兜底。`read_image` 是 ADR-0011 里「视觉模型自己 `pdftoppm` 栅格化后逐页 `read_image`」这条路径的依赖，它只在 `ctx.attachments` 挂载时注册——没有附件存储，这个工具不存在，视觉输入静默无路可走。`read` 的行与字节窗口决定了大输入的读法（模型分页读），这也是 ADR-0012 写明的「每个文字/JSON 输入多一轮 read」代价的来源。上游把 PDF、音频、视频列为「仍延期处理」，正是平台不再代劳预处理、让模型用 bash 自理格式转换的前提（ADR-0011）。
- **配置要点**：上游默认（`readLimit` 2000、`readMaxLineLength` 2000、`readMaxBytes` 51200、`readStreamMinSize` 10 MiB）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-attachment`
- **seam 角色**：Service Definition（`ctx.attachments`）
- **决定**：挂（库，不是组合行）
- **它给会话带来什么**：间接——图片经角色无关的核心 `ImageBlock` 进入模型请求，请求描述公开附件 ID 与实际请求尺寸；会话事件里只保存内容寻址引用，从不保存 base64 或路径。
- **理由**：`tool-fs` 把 `read_image` 注册在 `ctx.inject(["attachments"], …)` 里，没有这个 seam 就没有这个工具。第一版只接受 PNG / JPEG / WebP / GIF——PDF 不是附件，这正是 ADR-0011 让模型自己栅格化再逐页看的原因。上游明言保留策略与垃圾回收尚未实现；对本项目这不是问题，见 `attachment-local`。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-attachment-local`
- **seam 角色**：Service Provider（`ctx.attachments`）
- **决定**：挂
- **它给会话带来什么**：间接——历史图片在重启与 fork 后的持久回放；规范化与请求投影都是确定性的，附件与路由策略不变时之后各轮复用同一份缓存的请求字节。
- **理由**：上游 base 挂。对象存在 `<DSH_HOME>/attachments/v1/objects/<sha256 前缀>/<sha256>`，内容寻址；每张源图 ≤ 20 MiB、≤ 64,000,000 像素、单边 ≤ 8192px，规范化后长边 ≤ 2048px、≤ 4 MiB，每条消息 ≤ 20 张、≤ 200 MiB。本项目不传 `dshHome`，让它跟随子进程的 `DSH_HOME=<run>/home`：图片字节与会话 JSONL 一起落在运行目录，随运行清理一并删除——上游「对象无限期保留、没有 GC」的限制在本项目变成「随运行目录一起删」，运行目录本来就是清理的单位。规范化会把长边缩到 2048px：扫描件逐页栅格化后模型要看清局部，得自己裁剪放大再 `read_image`（ADR-0011 里实测的 PIL 裁剪就是这条路），预生成缩略图给不了。
- **配置要点**：上游默认；根经环境变量 `DSH_HOME` 落在 `<run>/home`，组合里不写 `dshHome`。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-subprocess`
- **seam 角色**：Service Definition（`ctx.subprocess`）
- **决定**：挂（库，不是组合行）
- **它给会话带来什么**：不直接可见；`bash` 与 `glob` / `grep` 的 ripgrep 都经它 spawn，输出的面向模型渲染全在消费方。
- **理由**：这个 seam 拥有唯一一份共享的环境清理定义 `scrubbedParentEnv()` / `SENSITIVE_ENV_PATTERN`：环境里形似凭据的名字（`*KEY*` / `*PASSWORD*` / `*SECRET*` / `*TOKEN*`）与所有 `DSH_*` 在 spawn 前被丢弃，显式 `env` 之后合并。这是 ADR-0006「凭据不进配置、不进日志、不进运行目录」在 shell 一侧的补全：`DEEPSEEK_API_KEY` 确实进了 harness 子进程的环境（供 `llm-deepseek` 按引用名解析），但模型的 `bash` 里 `env | grep KEY` 看不到它——bash spawn 时又清了一遍。argv 从不经 shell 解释，需要 shell 的消费方自己传 `['bash', '-c', command]`，所以「模型控制的值只是 argv 元素」在 ripgrep 那条路上也成立。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-subprocess-local`
- **seam 角色**：Service Provider（`ctx.subprocess`）
- **决定**：挂
- **它给会话带来什么**：间接（经 `tool-bash`）——有界的 stdout / stderr 尾部，超限时 `[output truncated; full output: <path>]` 指向完整流的 spill 文件。
- **理由**：上游 base 挂。它没有任何配置：处置方式、上限、宽限期全来自调用方（`bash-sandbox` 继承 `bash-local` 的 `maxOutputBytes` 64000、`maxSpillBytes` 64 MiB、`graceMs` 3 s）。POSIX 下 detached 进程组、`SIGTERM` → 宽限期 → `SIGKILL`，服务 dispose 时终止所有存活进程并等待退出，另有 Node `exit` 监听器做同步兜底——这是 ADR-0007「取消就是终止进程树」能兜住模型在 bash 里起的子孙进程的依据（重新认父的 daemon 仍可能逃逸，上游写明）。原始流的完整输出 spill 文件由它自己写在 `os.tmpdir()` 下按需创建的 `dsh-subprocess-*` 私有目录里（`0700`，文件 `0600`），上游说「已完成的 spill 文件不删除、在 OS tmpdir 下累积」；本项目经 `TMPDIR=<run>/tmp`（见 `sandbox-local` 行）让这个目录落进运行目录，累积随运行清理。凭据清除是名称启发式，`*PASSPHRASE*` 之类会漏——本项目登记的凭据引用名受设置层校验，但机器环境里其它名字的秘密仍会进 bash，这是「read 与网络不受限」之外另一条要知道的不设防的边。
- **配置要点**：上游默认（无 config）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-shell`
- **seam 角色**：Service Definition（`ctx.shell`）
- **决定**：挂（库，不是组合行）
- **它给会话带来什么**：不直接可见；`tool-bash` 把执行器的输出与沙箱事实渲染成结果 token。
- **理由**：shell 三包（本包 / `bash-local` 与 `bash-sandbox` / `tool-bash`）是上游能力 seam 的规范范例。这一层定义的 `sandboxMode` 能力事实，让 `tool-bash` 不导入任何 provider 就知道该不该公布 `sandbox_permissions` 字段——`bash-sandbox` 替换 `bash-local` 时工具层零改动，与 fs 栈同一种替换方式。`dshEnv` 受信 overlay 与普通 `env` 的合并顺序也定义在这里：执行器先移除继承的受管键再合并 `dshEnv`，普通 `env` 顶不掉受管值。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-shell-env`
- **seam 角色**：注册表插件（`ctx.shellEnv`；`tool-bash` 的 Provider 依赖）
- **决定**：挂
- **它给会话带来什么**：每次 `bash` 调用收到新收集的受信 `DSH_*` 变量——`DSH_HOME`、`DSH_SHELL=1`、`DSH_SESSION_ID`（= 会话 id），以及持久化 seam 能定位时的 `DSH_SESSION_JSONL`；工具描述只教通用的 `$DSH_*` 约定，不点名具体变量，不加常驻提示词段。
- **理由**：`tool-bash` 注入 `bashEnv`，没有它 `tool-bash` 一直等待、永不激活。本项目的会话 id 由节点 id 派生（回边重入的轮次带后缀），所以 `DSH_SESSION_ID` 让模型在 bash 里能知道自己是哪个节点、第几轮；`DSH_SESSION_JSONL` 只是位置提示，不是授权。
- **配置要点**：`dshHome` 钉到 `<run>/home`。上游默认按 `$DSH_HOME` 再 `~/.dsh` 解析，spawn 已注入 `DSH_HOME=<run>/home`，值本来一致；显式写是让组合文件自解释，且不让 shell 里的 `DSH_HOME` 依赖 spawn 环境与组合之外的一致性。
- **定制**：配置 / `dshHome` 钉到 `<run>/home` / shell 里的 `DSH_HOME` 必须与子进程的隔离 home 一致 / `packages/shell/shell-env/README.zh.md`@0.1.1-rc.2
- **可按工作流切换**：否

### `@deepseek-ai/dsh-bash-sandbox`
- **seam 角色**：Service Provider（`ctx.shell`；替代 `bash-local`）
- **决定**：挂
- **它给会话带来什么**：`bash` schema 多出 `sandbox_permissions`（enum `workspace-write` | `danger-full-access`）与 `justification`；被拒绝的调用在普通输出后精确追加 `[sandbox: file access denied under <mode> mode]`，再追加 `[sandbox: escalation available — retry this exact command once with sandbox_permissions … the approval prompt asks the user]`；runner 不可用时整个调用以 `SANDBOX_UNAVAILABLE` 失败，命令不裸跑。
- **理由**：上游 base 挂它（非 win32 时）替代 `bash-local`，ADR-0011 沿用。每条命令的精确 argv `['bash', '-c', command]` 先交给 `ctx.sandbox` 包装再 spawn，内层 Bash 保留 shell 语义、`BASH_ENV` 在 runner 建立约束之后才求值；哪种 runner、有没有 runner 是 provider 的事，没有就 fail-closed。它只限制文件影响、网络不限、拒绝从 stderr 的后端方言推断——这三条是 ADR-0011「围栏强度分两档」与「read 与网络不受限」的原始出处。本项目的 bash 是格式转换（`pdftotext` / `pdftoppm` / Python）的通道，需要写工作区与临时目录，`workspace-write` 正好；`danger-full-access` 只可能经审批升级到达，而审批固定 `never`（下）。升级提示那句「the approval prompt asks the user」会出现在拒绝结果里，但 `never` 的策略上下文已事先告诉模型不要设 `sandbox_permissions`——两段文字都是上游的，前后自洽，模型不会白走一步。
- **配置要点**：`cwd` 钉到工作区，`timeoutMs` 120 s。它没有自己的 Config，原样继承 `bash-local` 的：`cwd` 没有默认值时执行器兜底 `process.cwd()`（工具层本来会传会话 cwd，钉死是 ADR-0007 同类坑的保险）；`timeoutMs` 包默认 120 s，base 覆盖成 60 s，本项目取包默认——一次 `pdftoppm` 多页栅格化或一次 Python 处理常超过一分钟；`maxTimeoutMs` 600 s 上游默认，模型可按调用覆盖到十分钟，再长靠拆节点；`maxOutputBytes` 64000、`maxSpillBytes` 64 MiB、`graceMs` 3 s 上游默认。

### `@deepseek-ai/dsh-sandbox-local`
- **seam 角色**：Service Provider（`ctx.sandbox`）
- **决定**：挂
- **它给会话带来什么**：间接——runner 选择与 profile 不进上下文，模型只经 `bash` 结果看到拒绝标记、`enforcement: full | partial` 事实与 `SANDBOX_UNAVAILABLE`。

- **理由**：这是「模型看描述自行加载」在会话里的实际形态（ADR-0006）。目录只含名字与描述，路由全靠描述——所以本项目把中文显示名前缀进描述、slug 只作 `name`。用户显式 `/name` 注入就是本项目的预载（ADR-0016）：`buildPrompt` 把每个预载技能写成提示正文前的一行 `/<slug>`，`agent/pre-step` 监听器扫描 `source.kind === 'user'` 消息里的手势（正则 `(^|\s)\/([a-z0-9]+(?:-[a-z0-9]+)*)(?=\s|$)`），把同一份渲染以 `skill-invocation` 来源作为用户指令注入，目录尾句告诉模型「遵循该块、不要再经工具重新加载」；轨迹面板把这条注入渲染成「预载技能：<名>」。预载只能选所在工作流技能集里的技能——集合之外的手势在上游只是一行普通文本，所以工作流保存（400）与运行受理（422）两处都校验 ⊆。全局停用 `skill` 工具等于关掉技能——目录随工具可见性一起消失，这是有意的一致性。上游写明「已加载指令正文没有大小上限」：技能正文进工具结果并在压缩前每步重发，编辑器要把 token 量摆在开关旁边（ADR-0016 的代价）。
- **配置要点**：上游默认（`catalogDescriptionMaxLength` 500）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-mcp-client`
- **seam 角色**：桥接插件（把外部 MCP 服务器的工具注册到 `ctx.tools`；每台服务器一个实例，entry id 前缀 `mcp-`）
- **决定**：挂（按全局登记逐台生成；停用的、或不在本工作流 MCP 子集里的服务器直接省略）
- **它给会话带来什么**：每个已发现的 MCP 工具以 `mcp__<serverName>__<rawName>` 出现为原生工具，描述与输入 schema 来自服务器；重新同步替换整个世代，不累积。
- **理由**：上游 base 不挂任何 MCP 行——MCP 是用户 profile 里的事，一台一行；本项目对应的是全局设置里登记的服务器，每台一行，进入运行组合的是「全局 `enabled` ∩ 工作流设置勾选的子集」（ADR-0016：全局登记、工作流收窄；子集里登记表已经没有的名字在受理时静默忽略，生效的名单冻结进 `runs.settingsSnapshot.effective.mcpServers`）。`failOnStartupError` 恒为 `false`（也是上游默认，显式写出）：初始连接或工具同步失败时插件仍激活但不注册工具，运行照跑，模型只是看不到那台的工具——一次付费运行不该被一台外部服务绑架。stdio 的 `env` 拒绝凭据形键名：这个对象会原样写进 `<run>/cordis.yml`，密钥必须走凭据引用名与 spawn 环境白名单（ADR-0006）；上游自己的示例用 `!!js process.env.X` 从环境取值，本项目的 YAML 渲染器只产生 JSON 值、不产生 `!!js`，这条路在本项目根本不存在，所以拒绝是唯一正确的答案。`env` 合并进的是已清理的环境（`scrubbedParentEnv` 之后），与 bash 同一规则。Action 收窄对 MCP 工具同样成立，且要分两层：`restrict` 层只能拿已注册的名字，迟连服务器的工具在会话创建时可能还不在，所以先与已注册面求交；`guard` 层按完整 deny 清单在执行时按名拒绝，会话创建后才注册的被停用工具同样调不动。`toolCallTimeoutMs` 默认 60 s，由 MCP SDK 的请求超时强制——它不是 `timeout-policy` 的预算，MCP 工具定义上没有 `timeoutMs`；`reconnect` 默认开、退避到 30 s、每次中断最多 10 次，单次运行的寿命内这套机制意义有限但无害。这两项本项目一律不写，全取上游默认：设置面没有登记它们的通道，组合规格也不再留字段。
- **配置要点**：`serverName`、`transport` 与传输专属字段来自全局设置；`failOnStartupError: false` 恒定；`toolCallTimeoutMs` 与 `reconnect` 一律不写、取上游默认；stdio `env` 拒绝形似凭据的键名，HTTP `headers` 暂不接受非空值。
- **定制**：配置 / `failOnStartupError` 恒为 `false`；stdio `env` 拒绝凭据形键名 / 单台 MCP 不能绑架整个运行；`env` 会原样落进组合文件 / `packages/mcp/mcp-client/README.zh.md`（默认 `false`）@0.1.1-rc.2
- **可按工作流切换**：是

### `@deepseek-ai/dsh-web-search-deepseek`
- **seam 角色**：Service Provider（`ctx.web` 的搜索提供方；注入 `web`，可选经 `ctx.credentials` 解析凭据）
- **决定**：挂（默认关，可按工作流切换）
- **它给会话带来什么**：一个独立的 DeepSeek 模型收到 `Perform a web search for the query: <query>` 与原生 `web_search` 服务器工具定义——这次请求不属于会话模型上下文；会话模型经 `tool-web` 只看到去重后的 URL、标题、日期与引用 snippet，提供方生成的文本不被当作答案。agent 发起的搜索会向会话追加一条 `web/deepseek-search-llm-request` 事件（含端点与不带密钥的请求体），轨迹里能看到搜过什么。
- **理由**：这是本组与基线的差异之一，也是「用量必须归节点」的直接后果。DeepSeek 没有专用检索端点：一次搜索是一次**完整的 Messages 模型调用**（Anthropic 兼容基址 `https://api.deepseek.com/anthropic/v1`、`model: deepseek-v4-flash`、`maxTokens` 4096、`maxUses` 5），带完整模型轮次的延迟与 token。这笔用量不经 `llm/stream` 的 `usage` chunk——上游源码里没有 usage 字段——所以 `node_usage` 收不到，运行列表的用量汇总显示零而账单不为零，这是账外支出。基线里 base 每种模式都挂它，本项目默认关；工作流明确需要联网检索时打开，并接受该工作流的搜索费用在本站账外。费用上限要一起说：`tool-web` 一次调用最多 4 个查询、每个查询最多 5 次原生搜索，一次 `web_search` 工具调用最多 20 次服务端搜索。凭据复用与模型相同的引用名（不增加密钥），每次搜索都重新解析；它**不**复用 `$DEEPSEEK_BASE_URL`（那是 chat-completions 基址），搜索端点走自己的 `baseURL` / `$DEEPSEEK_SEARCH_BASE_URL`。严格模式：响应里没有 `web_search_tool_result` 块就以 `WEB_PROVIDER_ERROR` 失败，不降级为从模型文本抓 URL。
- **配置要点**：`apiKeyEnv` 取全局设置的模型凭据引用名（默认 `DEEPSEEK_API_KEY`，与 base 相同）；`baseURL`、`model`、`maxTokens`、`maxUses` 上游默认。
- **可按工作流切换**：是

### `@deepseek-ai/dsh-tool-web`

- **决定**：挂（默认关，可按工作流切换）
- **它给会话带来什么**：`web_search(queries: string[])`（1–4 个查询）与仅搜索分支的指导：`Use the web_search tool to discover current information on the web… Use the returned source snippets when available, and cite the relevant URLs as markdown links.`；结果是可选答案后跟 `Sources:` 列表（`- [<title-or-url>](<url>) — <snippet> (<publishedAt>)`），最多 8 条，结尾 `Cite the relevant URLs above as markdown links in your answer.`。

### `@deepseek-ai/dsh-code-runtime`
- **seam 角色**：Service Definition（`ctx.codeRuntime`）
- **决定**：不挂
- **它给会话带来什么**：间接（经 `dsh-tools` 的 Code Mode）——`run_code` 工具、生成的 TypeScript SDK 段与 `code` 模式下的 `tools:code-only` 规则；`code` 模式下模型直呼其它任何工具都解析为 `UNKNOWN_TOOL`。
- **理由**：这是本组与 headless 基线的差异之一，且方向是我们**少挂**：headless 的 patch 明确插入 `code-runtime`（`dsh-code-runtime-worker-thread`）并把 `tools.mode` 接到 `DSH_TOOLS_MODE`，注释的意思是「沿用 Web 界面那个临时的、进程级的 Code Mode 选择开关」。不挂的理由三条。其一，上游自己标注这是**临时的进程级**开关；本项目每次运行一个进程、Action 只做收窄不做扩张（ADR-0015），一个按进程翻转整个工具呈现方式的开关没有合适的落点，等它稳定成按会话的部署配置再评估。其二，Code Mode 会把 `structured_output` 也变成 SDK 绑定：本项目的结构化输出是会话 scope 注册的工具、靠 `tools/result` 两阶段提交确立权威值（组 10），在 `code` 模式下这条路变成 SDK 子分发，需要重新验证，收益不明。其三，worker 线程运行时「是隔离措施，不是安全边界」，程序派生的 OS 进程在 `worker.terminate()` 后仍存活——比 bash 的进程组终止弱，ADR-0007「取消就是终止进程树」兜不住它。本项目不需要它解决的问题——它省的是多工具调用的往返，而 ADR-0008 已经让重活落在文件与 bash 里。
