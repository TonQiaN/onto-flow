# 10 本项目自有

> 默认方向：自有。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这组是本仓库自己写的部分：不是「上游有一行、我们挂不挂」，而是上游没有、本项目为了把一个 headless 会话固定成工作流节点而补出来的代码。判据是**它是否进入运行子进程的组合树，或决定那棵树长什么样**：进树的两行（`ontoflow-rpc` 与按运行生成的 Tool 插件）是组合行，有 entry id；生成 Tool 插件的一行（`tool-plugin.ts`）是平台维护的 cordis 包装，Tool 库里的行是它的数据（ADR-0017）；决定树形的两行（`composition.ts`、`runner.ts`）是上游 profile 与启动器的对应物；剩下两行（结构化输出运行时、`composeNodeScope`）是会话创建窗口内对单个 Action 会话的组合，它们不是插件、不在 `cordis.yml` 里，却决定了 Action 会话与上游 headless 会话之间的全部差别（ADR-0015）。

七行里有四行是对上游代码的定制，三阶各占一格：`composeNodeScope` 与 `tool-plugin.ts` 是包装（上游原样，前者把监听器挂在 agent 公开的 seam 上，后者把 Tool 契约套进 `dsh-tools` 的 `ToolDefinition` 注册形状）；`ontoflow-rpc` 与 `structured.ts` 是 fork（抄上游源码改），fork 与包装依据的上游文件与版本记在目录里，`catalog.test.ts` 在参照克隆存在时核对那些文件真的存在。另外三行没有上游原型可比，只有上游机制可对照——按运行生成的 Tool 插件对照上游的工具插件约定，`composition.ts` 对照 profile 与 bundle patch，`runner.ts` 对照 `dsh` 启动器与 `dsh-headless/startup`。

总体结论：本项目对上游的改动全部收敛在 `src/server/harness/` 一个目录里；进入组合树的只有两类本项目文件（RPC 插件与 Tool 包装插件），都以绝对路径进组合，组合树的其余部分由上游包原样构成（组 1–4）；`runner.ts` 与 `boot.ts` 也在子进程里，但它们是树外的入口，不是树里的行。会话级差别一律在会话 scope 上注册、随会话释放，不改上游任何一个包的行为。所以上游升级时这组要重看的只有目录记的四个上游文件（其中 `packages/core/tools/src/index.ts` 的 `ToolDefinition` 形状一变，只改 `tool-plugin.ts` 一处，库里的 Tool 不动），以及 `composeNodeScope` 依赖的四个 seam：`agent/pre-step`、`agent/request`、`tools.restrict` / `tools.guard`。

## 逐行

### `src/server/harness/rpc`
- **seam 角色**：本项目自有（组合行 `ontoflow-rpc`：stdio 上的 JSON-RPC 服务端插件，`inject = ["agents"]`）
- **决定**：自有
- **它给会话带来什么**：与上游 `dsh-sdk-jsonrpc-server` 一致——每个被接受的 `session/prompt` 把调用方给的 `contentBlocks` 原样作为该会话的一条用户消息交给模型；插件本身不添加系统提示词文本或工具 schema，JSON-RPC 帧、会话通知与服务端内部记录都不增加模型上下文 token。它带进会话的差别全在会话创建窗口里（见下两行）。
- **理由**：这是 Next 进程与运行子进程之间唯一的通道，也是本项目对上游最大的一处 fork。上游原型 `@deepseek-ai/dsh-sdk-jsonrpc-server`（组 9，备选）的 README 自己把三件事列为已知限制：「协议没有逐会话关闭或提示词取消方法：SDK 创建的 agent 会一直存活到进程关闭」、「没有逐提示词结果」、客户端放弃轮次的方式是关闭运行时进程。这三条对一个只跑一个 agent 的 SDK 客户端无妨，对本项目却正好是引擎的三个硬需求：一次运行的多个 Action 在同一个子进程里各开一个会话、就绪节点并行（DESIGN.md，并发上限 10），人取消的是一个节点而不是整次运行（`cancelRun` 从 running 节点读会话 id）；节点结束后会话必须关闭，让同一子进程继续服务后面的节点，而不是让已完成会话的 agent 活到进程结束；节点的数据面结果要读回来（ADR-0008），上游协议给的只有「inbox 准入回执」。这些都做不成包装：上游 `HarnessSdkJsonRpcServer` 的 `createSession` 没有 setup 钩子、`prompt` 没有选项、`handleRequest` 是封闭的方法分派，从外面挂监听改不了它。于是 fork。
  - **协议扩成超集。** 与上游相同的 `initialize` / `session/prompt` / `shutdown` 三方法与 `session.event` / `session.status` 两通知原样保留，传输层直接用上游 `dsh-sdk-protocol` 的 `JsonRpcLineTransport`（组 1）。补三个方法：`session/cancel` 调 `agent.cancel({ kind: "user" })`，取消当前回合并清空 inbox，会话保持存活；它先等挂起的懒创建结束，取消撞上创建窗口时送达新会话而不是丢失。`session/close` 调 `AgentHandle.dispose()`，停循环、注销、等静止后才回答。`session/output` 读该会话结构化捕获的当前状态，未挂 `outputSchema` 的会话恒为未捕获。上游协议没有版本协商，两种实现靠 `serverInfo.name` 区分：上游固定 `deepseek-harness-sdk-runtime`，本项目是 `ontoflow-harness-runtime`。
  - **prompt 懒创建时接受按会话的覆盖。** `agentOptions`（provider / model / maxTokens，来自 Action 的模型行）与 `nodeOptions`（`outputSchema`、`toolFilter`、`skills`、`reasoningEffort`、`maxSteps`）只在本次 prompt 触发创建时生效，对已存在的会话传入即拒绝——同一会话的第二条 prompt 不能悄悄换掉它的组合。这些覆盖经 `ctx.agents.create` 的 `setup` 回调进入会话 scope（下两行）。
  - **不转发 subagent 通知。** 上游订阅 `session/created` 与 `subagent/end` 发 `subagent.started` / `subagent.finished`，类型来自 `dsh-subagent`；本项目不挂 subagent（ADR-0014，组 5），`dsh-subagent` 不在依赖闭包里，这两条订阅连同 `maxTokensAsSuccess` 配置一起去掉，插件的 `Config` 是空对象。
  - **保留的上游纪律。** `initialize` 先等 `loader.await()`，树 settle 后才宣告就绪，MCP 初始工具发现这类异步同级能力对第一条 prompt 可见（组 1 的 `cordis-plugin-loader`）；投递前核对 `ctx.agents.get(agent.id)` 与记录一致，agent-loop 单独 reload 后滞留的 agent 会静默接受 followup；`shutdown` 的响应先写出，再 flush 传输、dispose 根运行时、以 0 退出，并发的多个 shutdown 共享一个退出任务；`deepseek-official` 无适配器时挂兜底 `dsh-llm-deepseek`——本项目组合里 `llm-deepseek` 恒在（组 1），这条兜底实际不触发，其它无适配器的 provider 让 `initialize` 失败。stdout 只承载协议帧，上游同样把「stdout 纯净性由部署保证」列为限制，本项目的保证是 `cordis.yml` 的头注释与组 7 不挂任何 stdout logger。
  - **进程退出的分工与上游相同。** 插件拥有 `shutdown` 退出；EOF 与信号退出归 `runner.ts`。Next 侧 `RunProcess.dispose()` 的收束阶梯——协议 `shutdown` → stdin EOF → SIGTERM → SIGKILL，每级等 3 秒退出边沿——正是对着这个分工设计的；SIGKILL 后仍无退出边沿即抛错，运行进入隔离、保留进程句柄，预览、清理、删除与新准入容量都 fail-closed（ADR-0007）。
  - **两条通知是引擎的两条命脉。** `session.event` 对应上游 `session/event`，逐条转发、不过滤：Next 侧到达即归一落 `run_events` / `node_usage`，两条 SSE 端点只轮询 SQLite，不落库页面就要等节点跑完才看得见。`session.status` 转发 `agent/status` 的 `running` / `idle`：Next 侧 `runTurn` 等「先 running 再 idle」判定一轮结束。上游明说 `running` 只是驱动器的 drain 区间、只有拥有完整区间的调用方才能把它概括成一次运行的结果——引擎是每个会话唯一的提示者，正是那个调用方。
  - **以绝对路径进组合。** Loader 从它自己在 `node_modules` 里的位置解析裸包名，本仓库不是 workspace、没有指回自己的软链，裸名 `ontoflow-rpc` 一律解析失败；`rpcPluginModulePath()` 从 `process.cwd()` 拼出 `src/server/harness/rpc/index.ts`，因为 Turbopack 打包后 `import.meta.url` 不指向源码。组合里它是最后一行，排在 Tool 插件之后。
  - 目录里 `index.ts`（插件壳：命名导出 `name` / `inject` / `Config` / `apply`，Loader 的 `unwrapExports` 靠这四个字段认插件）与 `server.ts`（`OntoflowRpcServer`）都改造自上游，MIT 许可，记在 `THIRD_PARTY_NOTICES.md`；`types.ts` 是超集协议的类型，Next 侧 `runtime.ts` 与子进程共用。`server.ts` 与 `types.ts` 的形态移植自同作者的 agent-workflow-studio。
- **配置要点**：无配置（`Config = Schema.object({})`；`input` / `output` / `exit` 三个钩子只给测试用，生产走进程 stdio 与 `process.exit`）。上游 base / headless 都不挂 sdk 服务端，没有可比的默认值。
- **定制**：fork / 补 `session/cancel`、`session/close`、`session/output`；prompt 懒创建时接受 `agentOptions` 与 `nodeOptions`；去掉 subagent 通知与 `maxTokensAsSuccess`；`serverInfo.name` 改为 `ontoflow-harness-runtime` / 引擎要按节点取消、按节点关闭并读回数据面，上游协议明言没有这三样 / `packages/sdk/server/src/server.ts`（插件壳对应 `packages/sdk/server/src/index.ts`）@0.1.1-rc.2
- **可按工作流切换**：否

### `src/server/harness/rpc/structured.ts`
- **seam 角色**：本项目自有（会话作用域的结构化输出运行时：不是插件，是在会话创建窗口内调用的函数 `attachStructuredRuntime(agentCtx, schema)`）
- **决定**：自有
- **它给会话带来什么**：与上游进程内 subagent 的结构化运行完全一致。系统提示词尾部多一段 order 190 的固定指令：

  ```markdown
  When you have your final answer, you MUST report it by calling the `structured_output` tool with arguments matching its parameter schema exactly. Do not finish with a plain text answer: only the tool call counts as your result.
  ```

  工具清单多一个该会话独有的 `structured_output`，描述为 `Report your final structured result. Call this exactly once, when your answer is complete; the arguments must match this tool's parameter schema exactly.`，参数就是这个 Action 的真实输出 schema；成功回执渲染为 `Structured output recorded.`，之后任何工具调用都得到 ``Error: structured output already recorded: the run is complete, so `<tool>` is not executed``。指令与 schema 不变则该会话内的请求前缀稳定。
- **理由**：这是双通道结果里数据面的实现（ADR-0008）。上游把「模型必须以一次工具调用交出结构化终态答案」这套机制做在 `subagent-in-process-driver` 里，供 spawn / fork 的子 agent 用；本项目不挂 subagent（ADR-0014），却恰好需要同一套机制——一个 Action 会话对引擎而言就是「空对话、经工作区交流、只把最终结果交回」的子 agent，差别只在由人在图上决定而不是由模型在运行时决定（组 5）。所以抄函数、不抄包：那个包的运行时入口经 peer 链拖入 `dsh-subagent`，进而 `agent-presets`、`session-projection`、`jobs`、`sandbox` 等本项目不挂的能力，为百余行自包含代码扩大依赖闭包不成比例（`THIRD_PARTY_NOTICES.md`）。抄过来的东西逐条对得上上游 README「结构化输出」一节，语义没有一处改动：
  - **工具注册在会话 scope 上、用真实 schema。** `tools.register` 从 `agent.ctx` 调用只为该 agent 注册（组 1 的 `dsh-tools`），并发会话各自一份，随会话销毁自动清理，全局层没有残留。schema 由输出端口生成——每个输出端口一个字段、值是该端口产物的实际路径，有具名出口时再加所选出口——数据面只放路由与判定用的少数字段，实质内容仍在文件（DESIGN.md「结构化结果」）。
  - **参数校验走上游同一套 JSON Schema 子集。** `validateJsonSchemaValue` 不过即抛 `ToolArgsError`，变成 `INVALID_ARGS` 错误结果，模型在同一回合内自行重试；schema 本身在进入注册前先经 `assertObjectJsonSchema` 断言（`composeNodeScope`），类型数组这类超出子集的写法在会话创建时失败，而不是在模型调用时。
  - **两阶段提交、以 `tools/result` 为准。** 工具体只把校验过的值以本次 `ToolExecution` 为键暂存并 `concludeTurn()`；捕获值只在该执行的权威最终结果不是错误时提交——后置 waterfall 仍可能把成功翻成错误，暂存不能算数。执行对象的身份唯一标识一次完整管线，adapter 的 callId 可跨步重复，但另一次执行永远命不中同一个暂存项；无论成败，最终通知都删掉自己的暂存。嵌套分派（Code Mode 的 `run_code`）等外层结果再提交的分支原样保留，虽然本项目不挂 code-runtime（组 2），这段代码今天走不到。
  - **终态守卫是单调的。** `tools.guard` 在整条 pre-execute waterfall 之后运行、只能拒绝或弃权，后注册的监听器无法复活派发；捕获之后模型再调任何工具都被拒，加上 `concludeTurn()`，会话在交出结果后立刻收束，不会出现「报告完再改一版产物」。
  - **不重新提示。** 上游：「正常结束却始终未提交必需结构化值的轮次会报告 error；驱动器不会重新提示」。本项目同样：会话回到 idle 后 `session/output` 读不到捕获值，节点即失败，错误信息会提示也可能是步数超过上限被拦下（下一行）；随后 `pickExit` 核对出口合法、`collectArtifacts` 核对声明的产物真的在盘上——文件不存在是唯一的机械兜底，模型说它写了不算证据。
  - 上游 README 注明这个仅运行时存在的工具定义不在随产品发布的工具目录索引里；本项目的 `docs/harness/` 同理不把它当组合行，它出现在这里是因为它决定了模型看见什么。
- **定制**：fork / 抄上游进程内 subagent 驱动器的同一机制，去掉 subagent 依赖，注释译成中文；导出名、指令原文、工具描述、回执、守卫文案与提交规则逐字保留 / 那个包的运行时入口经 peer 链拖入本项目不挂的能力 / `packages/subagent/subagent-in-process-driver/src/structured.ts`@0.1.1-rc.2
- **可按工作流切换**：否

### `src/server/harness/rpc/server.ts#composeNodeScope`
- **seam 角色**：本项目自有（包装：在 `ctx.agents.create({ setup })` 的会话创建窗口内，把一个 Action 的差别注册到该会话自己的 scope 上）
- **决定**：自有
- **它给会话带来什么**：三样加结构化输出，全部只对这一个会话生效。结构化输出运行时（上一行）；步数上限——超过上限的下一步被拒绝，回合当场关闭；思考强度——每一步的模型请求都以 Action 声明的档位发出，记录在 `request/header`；工具收窄——全局停用的工具与本工作流里这个 Action 没勾选的 Tool 从工具清单消失，晚注册的同名工具在调用时被拒并得到「工具 X 不在本 Action 的可见工具面内」。
- **理由**：ADR-0015 的实现。Action 之间的差别只有「收窄」一种，而上游为会话级差别给的正式机制是 agent preset——一份 `agent.cordis.yml` 挂成常驻组合、会话认父过去；preset 解决的是长驻宿主里按会话换整套能力的问题，本项目每运行一个进程、Action 定义住在数据库里并在受理时冻结，没有那个问题。上游 sdk 服务端的 `createSession` 也明写「不做 preset 组合，agent 从全局层读面向模型的行」，本项目沿用这个立场，只在 setup 里加四处注册。选 setup 窗口而不是会话创建后再注册，是上游对这个钩子的约定决定的：setup 在 agent 发布前运行，是「受信任、仅用于组合的同进程代码」，任一步抛出整次创建回滚，不会发布半成品会话；注册在 `agentCtx` 上的一切随 `AgentHandle.dispose()` 撤销，`session/close` 之后没有残留。四处注册各对着上游一条查实的缺口。
  - **步数上限（`agent/pre-step`）。** 上游 agent-loop 自己列在已知限制里：「没有内置轮次预算」，限制失控轮次的策略必须从既有扩展点执行。没有它，一个空转的 agent 会烧 token 直到节点的墙钟（Next 侧 15 分钟）。监听器在 `payload.step` 超过 `maxSteps`（引擎给 40）时返回 `{ kind: "reject" }`；上游对 reject 的约定是已领取的批次不保留、轮次以无步骤关闭——会话因此没交出结构化输出，节点失败，这正是要的结果，也是它不是一句「温柔提醒」的原因。它注册在会话 scope 上，所以子 agent 没有上限（ADR-0014 的第三条理由）。
  - **思考强度（`agent/request` waterfall）。** 上游 `AgentOptions` 只有 provider / model / maxTokens，思考强度在 `LlmCallConfig` 上；`dsh-llm` 把它定性为「每会话状态，绝不是可静默调整的每次调用旋钮」，并规定改它的正式路径是 `agent/request` 提议替换、`prepareCall()` 校验并填入适配器默认值、循环把生效值记进 `request/header`。交给 `llm/stream` 的请求在分发前深度冻结，监听器与适配器只能读，改它在回合中途抛错。所以档位只能从这个 waterfall 进入，且必须无条件覆盖：agent-loop 在 waterfall 运行前已把适配器默认值（`llm-deepseek` 省略时为 `high`）解析进调用配置，「只在未设置时才设」的守卫永远不触发。监听器注册在会话 scope 上，按 agent scope 过滤分发、随会话释放，并行的兄弟会话各用各的档位。档位词汇 `off` / `low` / `high` / `max` 直接取自 `llm-deepseek`：`off` 序列化为 `thinking.type: disabled`，不支持的值在网络 I/O 前以 `UNSUPPORTED_REASONING_EFFORT` 失败。
  - **工具收窄（`tools.restrict` + `tools.guard`，两层 deny）。** deny 清单由引擎合成：全局设置的 `disabledTools` ∪（工作流 Tool 集的全部公名 − 本 Action 可见的公名），见 `capabilities.ts` 的 `toolFilterForAction`；可见集 `action_tools` ⊆ 工作流 Tool 集在工作流保存与受理两处校验（ADR-0016）。上游 `restrict` 是 agent 作用域的可见性掩码，注册时对全局工具面做快照，未知名字与空筛选直接拒绝、多个掩码取交集，且上游明言「这是实时可见性组合，不是权限边界」。两条约定各逼出一层：deny 清单可能点名当前不在线的工具（迟连 MCP 服务器的桥接工具），所以先与已注册面求交再 `restrict`，交集为空就跳过；求交后的快照会被会话创建后才注册的被停用工具击穿，所以再用 `guard` 按完整 deny 清单在执行期拒绝——`agent.ctx` 上的守卫只对该 agent 生效，与 `restrict` 同随会话释放。可观察证据于是有两种：被 `restrict` 掉的工具不在 `request/header` 的工具清单里，模型根本看不见；被 `guard` 拦的工具留下一条错误结果。`allow` 原样透传、保持 fail-loud，它是定义面的契约，不该被静默放宽。
  - **运行时技能通道已裁掉。** RPC 协议曾有 `nodeOptions.skills`（经上游 `ctx.skills.register` 以 `source: "runtime"` 注册进会话 scope），从没有生产调用方；ADR-0016 又把预载定为经上游 `renderSkillContent()` 与 `skill-invocation` 来源的显式调用注入，这条通道于是没有归属，按仓库「不留无人用的路径」的立场随第一批删除。技能全部经工作区 `.agents/skills/` 的 symlink 由 `skill-filesystem` 发现（组 2）；预载不经 RPC，是 `action.ts` 的 `buildPrompt` 在提示正文前写的 `/<slug>` 行，由上游 `tool-skill` 在同一步展开——会话创建窗口里没有任何与技能有关的注册。
  - 四处注册需要的服务都经 `ctx.get` 取用而不是注入：插件只 `inject` 了 `agents`，属性代理受 inject 声明门控。`outputSchema` / `toolFilter` 要求 `tools` 已挂，`outputSchema` 另要求 `systemPrompt`，`skills` 要求 `skills` 服务；缺任何一个，会话创建失败，而不是静默少一项。
- **定制**：包装 / 会话 scope 上注册 `agent/pre-step` 超步拒绝、`agent/request` 无条件覆盖 `reasoningEffort`、`tools.restrict`（deny 与已注册面求交）+ `tools.guard`（完整 deny） / 上游 agent-loop 没有步数上限、`AgentOptions` 没有思考强度、`restrict` 的创建期快照会被晚注册的工具击穿 / 所依 seam 的上游文件：`packages/core/agent/README.zh.md`（`agent/pre-step`、`agent/request`）、`packages/llm/llm/README.zh.md`（`LlmCallConfig`）、`packages/core/tools/README.zh.md`（`restrict` / `guard`）@0.1.1-rc.2
- **可按工作流切换**：否（Action 层永远不开关插件；deny 清单里的全局停用项归全局设置，Tool 勾选归 Action）

### `<run>/plugins/tool-*.ts`
- **seam 角色**：本项目自有（按运行生成的 cordis 插件；组合行 `tool-<Tool id>`，以绝对路径进组合）
- **决定**：自有
- **它给会话带来什么**：本工作流 Tool 集里的每个 Tool，作为一个原生 Function Calling 定义进入工具清单——公名、描述与参数 schema 原样呈现给模型，返回值经包装的 `render` 以 `JSON.stringify` 变成一个文本块进入工具历史。只有把它列为可见的 Action 看得见它，别的 Action 的清单里没有它。
- **理由**：Tool 是模型在 Action 执行时可调用的自定义能力（CONTEXT.md），而 dsh 的能力单元是插件，所以每次运行把 Tool 物化成插件文件是上游形态决定的，不是本项目的选择。本项目的选择在三件事上；文件本身由下一行的 `tool-plugin.ts` 生成，Tool 作者不写也不看它。
  - **物化时机与来源。** 运行受理时从 `resolveWorkflow` 冻结的工作流 Tool 集（`workflow_tools` 全量行，ADR-0016：声明即物化，不看图上哪个 Action 勾选了）写进 `<run>/plugins/`，不回读共享库；受理后编辑 Tool 影响下一次运行。每个 Tool 两个文件：`tool-<id>.execute.ts` 是库里 `code` 列原样落盘的 execute 模块，`tool-<id>.ts` 是生成的包装、也是组合里的那一行。文件名与 entry id 从数据库 id 派生（`tool-<id>`，经 `assertSafeId`）：展示名允许中文，不能拼进裸 YAML 路径与 Loader 的模块名。目录的 `entry` 因此记 `idPrefix: "tool-"` 而不是固定 id，与 MCP 行的 `mcp-` 同理。
  - **全局注册、会话收窄。** 包装从普通插件上下文 `ctx.tools.register`，即落在全局层（`dsh-tools` README），也就是工作流 Tool 集对子进程里每个会话都可见；每个 Action 会话再经上一行的 deny（工作流 Tool 集公名 − 本 Action 可见公名）把自己看不见的摘掉。这是「Tool 是能力，评委不该看见归档工具」（ADR-0016）在运行期的实现——不是把集合切成每 Action 一棵子树，而是集合进全局、会话各自收窄；代价是集合里任一包装加载失败，整个运行在任何节点开跑前倒下（组 1 的 `dsh-app-boot`）。包装本身能否加载由 `composition-boot.test.ts` 真 boot 一个带样例契约 Tool 的组合钉住；execute 模块的语法错误则推迟到首次调用，以工具错误结果呈现给模型，不拖倒运行。
  - **加载与执行环境。** 包装由 Loader 以绝对路径 import，execute 模块由包装经 file URL 懒 import 一次；两个文件内部的 `import` 由 Node 从 `<run>/plugins/` 逐级向上解析，`data/` 在仓库根之下，所以 `node:` 内置模块与本仓库的依赖都够得着——opencode 时代「不能 import 仓库里任何东西」的规则已随引擎更换消失；`@deepseek-ai/*` 则在写入口被拒（那是又在写裸插件）。spawn 时注入的 `ONTOFLOW_DB_PATH` / `ONTOFLOW_DATA_DIR` 仍在子进程环境与 `ctx.env` 白名单里，但归档类 Tool 走 `ctx.dbPath` / `ctx.dataDir`（生成时写死的绝对路径），不再读进程环境。execute 模块是子进程内的普通 Node 代码：Seatbelt 围栏包的是经 `ctx.shell` / `subprocess` 派出的命令 argv，`fs-sandbox` 的路径检查只覆盖 write / edit 工具（组 2）；Tool 自己用 Node API 做的文件与网络效应两者都不管——Tool 作者写什么它就做什么。要围栏只有一条路：`ctx.run(cmd)`，它就是包装替 Tool 走的那条 seam（下一行）。这也是 Tool 与 MCP 的分工：外部能力走 MCP（ADR-0017）。
- **配置要点**：entry 无 `config`（Tool 插件没有 `Config`）；哪些 Tool 进运行由工作流设置的 Tool 集决定，哪些 Action 看得见由 Action 的可见子集决定，都不是组合开关。
- **可按工作流切换**：否（Tool 集归工作流、可见子集归 Action，都不是插件开关）

### `src/server/harness/tool-plugin.ts`
- **seam 角色**：本项目自有（包装：把 Tool 契约套进 `dsh-tools` 的 `ToolDefinition` 注册形状的生成器；`renderToolPlugin` 是纯函数，`materializeToolPlugin` 落盘）
- **决定**：自有
- **它给会话带来什么**：上一行的全部——它就是那两个文件的作者。模型看到的公名、描述、参数 schema、返回值文本块，以及 `timeoutMs` 是否被 `tool-call-timeout-policy` 强制，都由这里的生成决定；Tool 库的行只提供数据。
- **理由**：ADR-0017 的实现。Tool 作者面对的是 `src/server/harness/tool-contract.ts` 的一个稳定小面——`{ name(展示名), publicName(`^[a-z][a-z0-9_]{0,63}$`), description, parameters, output?, timeoutMs?, code }`，`code` 是 `export default async function execute(args, ctx: ToolContext)`，`ctx` 只有 `workspaceDir / runDir / tmpDir / dataDir / dbPath / cwd / env / signal / run()`，不暴露 cordis Context。上游每升一版会动的东西——`ToolDefinition` 的 `output` 必填、`render` 的 `(args, value)` 签名、JSON Schema 子集、`inject` 的服务名——全部只出现在这一个文件里。
  - **契约字面量、路径字面量、白名单字面量。** 包装里所有来自库或设置的值都经 `JSON.stringify` 进入源码：`CONTRACT`（公名、描述、两个 schema、超时）、`PATHS`（工作区、运行目录、临时目录、`data/` 根、数据库文件，生成时就是绝对路径）、`ENV_KEYS`（全局设置的凭据引用名、模型凭据名、`ONTOFLOW_DB_PATH` / `ONTOFLOW_DATA_DIR`，只写键名）、execute 模块的 file URL。键名在生成时写死、值在调用时从子进程 `process.env` 取——凭据值既不进包装文件也不进组合配置（ADR-0006）。公名不合法、Tool id 不安全、白名单键名形状非法都在生成时抛错，即受理期，不等到 boot。
  - **注册形状对上游逐项对齐。** `name` 取公名（展示名是中文，不能进工具清单）；`parameters` 原样交给上游；`timeoutMs` 只在非 null 时给，声明了才由 `tool-call-timeout-policy` 强制（组 3）；`output` 是上游必填项（`packages/core/tools/src/index.ts`），契约未声明时给无约束 schema `{}`（上游子集允许注解空 schema 表示任意 JSON）；`render` 一律 `(_args, value) => [{ type: "text", text: JSON.stringify(value) }]`——那条曾经写进 AGENTS.md 的「`render` 签名是 `(args, value)` 而不是 `(value)`」的坑，现在只有这一处会踩。`execute` 返回 `undefined` 时折成 `null`，上游只接受无损 JSON。上游 `register` 只校验 `output.schema`、不校验 `parameters`，所以 type 数组这类子集越界由写入口的 `objectSchemaProblem` 拦下（两个 schema 都查），不是「插件加载时拖倒整个运行」。
  - **`ctx.run()` 是与 bash 同一道围栏。** 包装 `inject = ["tools", "shell", "sandboxPolicy"]`，`run(cmd, { cwd?, timeoutMs? })` 先 `ctx.sandboxPolicy.resolve({ session })` 拿本会话的 `workspace-write` 策略，再 `ctx.shell.run(ctx.shell.resolve({...}))` 派出命令——与 `bash` 工具走的 `bash-sandbox` → `sandbox-local` 链完全相同（组 2），超时默认 60 s、上限 120 s（与 bash 同一上限）。返回 `{ stdout, stderr, exitCode, timedOut, sandbox: { mode, enforced, runnerFailed, denied } }`：`enforced` 定义为「执行器报告了 enforcement 且 `runnerFailed` 不为 true」；`bash-sandbox` 在围栏 runner 不可用时 fail-closed 抛 `SandboxUnavailableError`，包装把它折成 `runnerFailed: true, enforced: false, exitCode: null` 的结果而不是异常，命令没有跑、由 Tool 自己裁决——种子里的 `run_python` 以 `enforced && !runnerFailed` 为门禁，否则返回 `ok: false`。`aborted` 折成 `AbortError` 抛出，与上游取消语义一致。`cwd` 取 `exec.agent.session.header.cwd`（调用会话的工作区），`signal` 取 `exec.signal`，长时间工作要把它传下去。
  - **三个种子 Tool 都是契约形态。** `save_purchase_plan` 经 `ctx.dbPath` / `ctx.dataDir` 定位数据库与备份目录；`validate_resume_match_result` 经 `ctx.workspaceDir` 定位产物；`run_python` 经 `ctx.run()` 跑脚本。没有裸插件通道。专用调用入口钉住校验 Tool 的是六个契约字段的摘要 `toolContractSha256`（`src/lib/tool-digest.ts`，规范 JSON 键排序），不是包装文件的字节——上游升版重生成包装不该让库里的 Tool 失去权威身份。
- **配置要点**：无配置；生成器的输入是 `ToolPluginRow`（契约字段加数据库 id）、`RunWorkspace` 与 `envKeys`。`tool-plugin.test.ts` 断言生成内容（字面量、白名单、file URL、两个文件），`composition-boot.test.ts` 真 boot 一次带样例契约 Tool 的组合。
- **定制**：包装 / 按契约生成 `ctx.tools.register` 的 name / parameters / output / timeoutMs 与 render，`execute` 组装 `ToolContext` 并经 `sandboxPolicy` + `shell` 提供 `run()` / 上游 `ToolDefinition` 形状一动库里每个 Tool 都可能在加载那一刻坏掉，收敛到一处 / `packages/core/tools/src/index.ts`（`ToolDefinition`、`output` 必填）@0.1.1-rc.2
- **可按工作流切换**：否

### `src/server/harness/composition.ts`
- **seam 角色**：本项目自有（每运行组合的生成器；上游 profile + bundle patch 的对应物）
- **决定**：自有
- **它给会话带来什么**：间接地，一切——它决定子进程里挂哪些插件、各自什么配置，也就决定了模型每一步看见的提示词段、工具清单与围栏。它自己不贡献任何模型可见文本。
- **理由**：ADR-0013 的可执行面。上游的组装是分层 patch：profile 按序叠 bundle（`dsh-base` → `dsh-headless`），再叠 profile 的 `cordis.patch.yml`、home 级的那份，最后 `--patch` overlay；每条 patch 按 id 替换整个 `config` 或 `insert` 新行，`!!js` 表达式在挂载时求值（`dshHomePath`、`process.env`）。本项目不叠任何一层：`runCompositionEntries` 直接给出平铺的 entry 清单，`writeRunComposition` 把它渲染成 `<run>/cordis.yml`。理由已在 ADR 里：每次运行一个短命子进程、没有 profile home，「整行替换 config」对程序化生成很不友好；显式清单让 `docs/harness/` 有明确身份——它就是与上游 base 的差异审查记录。这里补几条生成器层面的事实。
  - **输入只有两类。** 运行目录事实（工作区、会话根 `<run>/sessions`、spill 根 `<run>/home/spill`、临时根）与受理时已经合成好的设置面（模型路由的凭据引用名 / baseURL / 模型目录、生效的 MCP 服务器 = 全局启用 ∩ 工作流子集、本次运行的 Tool 包装插件 = 工作流 Tool 集全量、生效开关 = `effectiveToggles(全局, 工作流覆盖)`）。合成在 `runner.ts` 完成，生成器只收结果；组合是「由全局设置与工作流设置推导，受理时冻结」（CONTEXT.md）：运行持有它启动时的快照，三层各自的输入与合成结果另落 `runs.settingsSnapshot`，网页保存只影响下一次运行。
  - **渲染即安全边界。** entry id 与模块名各有形状断言，config 值经 JSON 序列化（JSON 是 YAML 子集）裸插值，值为 `undefined` 的键整个省略——键必须真正缺失，上游 schema 的 `required` 与默认值才生效。没有 `!!js`，也不需要：上游用表达式取的 `DSH_HOME`、`cwd`、环境变量，这里都是生成时已知的常量。MCP 的 `env` / `headers` 会原样落进文件，所以形似凭据的 `env` 名在设置写入边界被拒（组 2 的 `mcp-client`）；模型凭据只以引用名进组合，值由 spawn 环境注入（ADR-0006）。
  - **开关是唯一的可变项。** `CompositionToggles` 五键（`webSearch` 默认关、其余默认开；`src/lib/workflow-settings.ts`）各控制目录里标了 `toggle` 的行：搜索三件套、`tool-fs-search`、`tool-str-replace-editor`、`tool-todo`、压缩三件（组 2、3）；`catalog.test.ts` 对每个键验开与关都恰好只动它那些行。全局设置给默认值，工作流设置只写要覆盖的键（ADR-0016），且只允许覆盖目录里标为 `workflowToggle` 的行，骨架、沙箱、审批、记录永远不可切换。
  - **顺序是机制，不是文档。** 上游 base 注明「行顺序不承载加载语义，激活由服务可用性驱动」，本项目仍按 provider 在前、consumer 在后排列，并把每处顺序依赖与必须钉死的路径记在 `composition.ts` 的行内注释里；组文档只引用不复制。
  - **三处钉死。** `catalog.test.ts` 核对默认组合的每个 entry 都对应目录里一行默认挂载的行、反之亦然，开关行只在开关开时出现；`composition-boot.test.ts` 真起一个子进程 boot 默认组合与开搜索的组合并完成 `initialize`（不调模型、不需凭据），裸名不是直接依赖、必填配置缺失、provider 顺序不对都在这里现形；`/api/settings/composition` 报告下一次运行会挂什么与最近一次运行真实落盘的 `cordis.yml`，是上游 `--dump-config` 的对应物——本项目没有长驻宿主树，「现在挂了什么」在没有运行时不成立。
  - 形态移植自同作者的 agent-workflow-studio；entry 形状、YAML 渲染与设置驱动的 entry 生成在同目录的 `entries.ts`。
- **可按工作流切换**：否（生成器本身；它生成的行各自按目录标记）

### `src/server/harness/runner.ts`
- **seam 角色**：本项目自有（运行子进程入口；上游 `dsh` 启动器 + `dsh-headless/startup` + `headless-runner` 的对应物）
- **决定**：自有
- **它给会话带来什么**：无直接影响。它决定的是子进程「要么整棵树激活、要么以 1 退出」，以及树激活之后谁来给会话喂消息——不是 argv 里的任务，而是 stdio 上的 RPC 帧。
- **理由**：上游 headless 的启动链有三段，本项目只保留最里面的 `boot()`。启动器 `dsh` 解析 `--profile` / `--patch` / 配置 dump，加载分层 `.env`（继承环境 > 项目 `.env` > 用户 `.env`），解析 profile 目录与 bundle 层，监视用户 patch 文件热重组，向树提供 `cmdlineArgs` 与 `appExit`；`dsh-headless/startup` 从 `cmdlineArgs` 解析任务位置参数并发布 `headlessStartup`；`headless-runner` 等 Loader settle、读 `agentDefaultModel`、经 `ctx.agents` 建一个 agent、把任务当普通用户消息提交、等静止、flush 会话、把最后一条非空 assistant 文本写到 stdout、按 `turn/end` 原因请求退出（completed → 0，否则 1）。这三段在本项目里各有明确的替代物或明确的不要。
  - **`.env` 不读。** 环境由父进程用上游 `scrubbedParentEnv()` 洗刷（形似凭据的名字与 `DSH_*` 一律丢弃）后按白名单显式注入：凭据引用名对应的值、`DSH_HOME`（`<run>/home`）、`TMPDIR`（`<run>/tmp`）、`ONTOFLOW_DB_PATH`、`ONTOFLOW_DATA_DIR`。`.env.local` 是 Next 进程读的，子进程看不见它；凭据只以引用名进组合、值在 spawn 时挑出（ADR-0006）。缺失的引用名整项省略，让上游在请求时以 `MISSING_CREDENTIAL` 响亮失败，而不是拿空串去认证。
  - **profile / patch / HMR 不要。** 组合路径是 argv 里唯一的参数，必须是已存在的文件，没有内置回退；`bootComposition` 调 `boot(binName, 绝对路径, 无 patch, 无 prepare, bareModuleBaseUrl)`，`bareModuleBaseUrl` 是 `boot.ts` 自己的 URL，让配置虽住在 `data/` 下、裸包名仍从本仓库的 `node_modules` 解析。`hmr` 与 `dsh-cmdline` 都不挂（组 7）；`installFailLoud("ontoflow-harness")` 把启动期与之后的未处理 Loader 拒绝变成一行 stderr 加 `exit(1)`，父进程把这个未经 dispose 的退出记为崩溃（`onCrash`），运行失败。
  - **任务不在 argv、答案不在 stdout。** 树激活后入口什么都不做——没有 `agentDefaultModel`，默认 provider / model 由 `initialize` 参数给出（`deepseek-official` / `deepseek-v4-flash-vision-exp`），每个会话再由 Action 的模型行覆盖；消息经 `session/prompt` 进来，结果经 `session/output` 与工作区产物出去，stdout 只承载协议帧，harness 自己的 stderr 落 `<run>/logs/harness.stderr.log`。退出码也不再对应某一轮的 `turn/end` 原因：一个节点失败是数据库里的事实，子进程继续服务并行的兄弟会话；进程退出归三个边沿——stdin EOF → dispose 根 → 0，SIGTERM → 0，SIGINT → 130——加上 RPC 插件拥有的 `shutdown` → 0，与上游「插件回答 shutdown，app bin 处理 EOF 与信号」的分工一致。
  - **没有构建步骤。** 子进程以 `node --import tsx` 加载与 Next 相同的 `src/`；入口路径由 `defaultRunnerEntry()` 从 `process.cwd()` 拼出（Turbopack 打包后 `import.meta.dirname` 是 `undefined`），这是「一切命令从仓库根运行」这条规则在子进程侧的根据。冷启动是 tsx 编译加整棵树装配，并行准入的 16 路同时 spawn 会把 `initialize` 拖过常规的 30 秒，所以那一个请求单独给 120 秒。
  - 形态移植自同作者的 agent-workflow-studio。
- **可按工作流切换**：否

## 什么算改造、什么不算

目录只把上面六行记为「自有」。围绕它们还有一圈代码容易被误认为对上游的改造，这里划清：

| 东西 | 是什么 | 不是什么 |
|---|---|---|
| `ontoflow-rpc`（`src/server/harness/rpc`） | fork 的插件：抄上游 sdk 服务端改，进组合树 | 不是包装——上游服务端没有可挂监听的 seam |
| 结构化输出运行时（`structured.ts`） | 从上游抄来的函数，在会话创建窗口内由 `composeNodeScope` 调用 | 不是独立插件，不在 `cordis.yml` 里，也不替换上游任何一行 |
| 步数上限 / 思考强度 / 工具收窄（`composeNodeScope`） | 包装：上游原样，我们的 waterfall 监听与 restrict / guard 挂在会话 scope 上 | 不是 fork，不是 preset，不改 `agent-loop` / `dsh-tools` 的任何行为 |
| Tool 插件（`<run>/plugins/tool-*.ts`） | 按运行生成的插件：库里的 execute 模块原样落盘，加一份由 `tool-plugin.ts` 生成的包装，以绝对路径进组合 | 不是对上游插件的定制；Tool 代码不是插件，作者永远不写 `name` / `inject` / `apply` |
| Tool 包装生成器（`tool-plugin.ts`） | 包装：上游 `dsh-tools` 原样，我们把契约套进它的 `ToolDefinition` 注册形状，并经 `sandboxPolicy` + `shell` 给 Tool 一个 `run()` | 不是 fork，不改 `dsh-tools` 的任何行为；也不是 Tool 本身——Tool 是它的数据（ADR-0017） |
| `composition.ts`（连同 `entries.ts`） | 上游 profile + bundle patch 的对应物：程序化、平铺 | 不是对任何上游包的改动；每一行的配置差异各归它那组的文档 |
| `runner.ts`（连同 `boot.ts`） | 上游 `dsh` 启动器与 `dsh-headless/startup` 的对应物 | 不挂 `dsh-headless`、`dsh-cmdline`；`dsh-app-boot` 原样用（组 1） |

不在这组的：`runtime.ts` 与 `launch.ts` 是 Next 侧的协议客户端与 spawn，占的是上游 `dsh-sdk-client` 的位置（组 9 记为备选，本项目直接用 `dsh-sdk-protocol` 的传输）；`workspace.ts` 是运行目录与工作区（ADR-0007），不碰组合；`trajectory.ts` 只读会话 JSONL（组 4）；`src/server/engine/` 是编排层，消费 RPC、不进子进程。配置一阶的定制（沙箱模式、持久化根、persona 留空之类）不算自有，记在各组的「定制」小节。

## 待核对

- `structured.ts` 保留了上游为 Code Mode 嵌套分派准备的 `pending` 提交路径；本项目不挂 code-runtime（组 2），这段代码今天走不到。保留是为了与上游逐字对照，是否在下次上游升级时裁掉，需要人定。
- 「Tool 用 Node API 直接做的文件与网络效应不受围栏约束」核对到的范围：Seatbelt 由 `sandbox-local` 包在经 `subprocess` 派出的 argv 上，`fs-sandbox` 是替换 `fs-local` 的工具提供方、只管 write / edit 工具的路径。没有在上游源码里逐行核对是否还存在对进程内工具体的其它围栏。
