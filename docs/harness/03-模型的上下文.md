# 03 模型的上下文

> 默认方向：跟上游，去掉要理由。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这一组回答的是：模型每一步请求里，除了它自己的对话与工具 schema，还看见什么；这些东西怎么被控制在预算之内。具体是五件事——工作区指令怎么进入历史（agent-instructions）、超大工具结果怎么离开上下文（spill 三件套与 output-retention）、上下文逼近窗口时怎么先剪后摘（token-meter、compaction 三件套）、空转与挂住的调用怎么被打断（repeat-tool-reminder、timeout-policy、timeout）、模型怎么给自己记账（tool-todo）。判据只有一条：这一行改不改变模型在一个 headless 会话里的工作方式。改变的，默认与上游 base 一致：base 挂的九个组合行我们全部挂，配置值逐项取 base 的值，唯一的差异是把 spill 的落点钉进运行目录；四个随之进闭包的库与 seam 定义（spill、compaction、output-retention、timeout）不是组合行，一并记在这里。不改变模型工作方式的——只为浏览器输入框、tmux、agent preset 服务的七行——base 与 headless 也不挂，我们同样不挂。

本项目与"人在目录里起 dsh"的差别决定了这组行在这里的分量。无人值守：向人澄清的上下文（time-context 的时区、session-reference 的提及）没有回答者。有界：每个 Action 是全新会话，步数上限 40（组 10）、bash 单条 120 秒（组 2）、节点有墙钟——所以压缩很少触发，但一旦触发就是节点能否收束的差别；提醒与超时是步数上限之前更便宜的止损。内容在文件里（ADR-0008、ADR-0012）：摘要丢掉的细节模型可以重读，spill 落盘的完整结果模型可以回读，这两条兜底在本项目的代价都比在对话式会话里低。每轮全新会话、轮次之间经文件传递（ADR-0009）：跨会话引用与上一轮记忆都没有对象。

目录把 token-meter、compaction-basic、tool-result-pruner 三行标在 `compaction` 开关下、tool-todo 标在 `todo` 开关下，都可按工作流切换（ADR-0016，`CompositionToggles` 五键）。依赖方向已经守住：compaction-basic 需要 token-meter，pruner 没有 compaction-basic 时不起作用，所以三件套挂在同一个开关上同进同出；`composition-boot.test.ts` 有一次四个默认开的开关全关的 boot，证明关掉的行没有别的行 inject 它们。

## 逐行

### `@deepseek-ai/dsh-agent-instructions`
- **seam 角色**：Consumer（上下文插件；可选消费 `ctx.fs`，监听 `agent/pre-step` 与第一方 `read`/`write`/`edit` 的 `tools/result`）
- **决定**：挂
- **它给会话带来什么**：第一次请求的历史里多一条持久的 user 角色消息，用 `<system-reminder>` 框住从 `$DSH_HOME/AGENTS.md` 到项目根再到会话 cwd 的 `AGENTS.md` / `CLAUDE.md` 链，宽泛在前、具体在后；此后每次成功的 read/write/edit 触到更深的目录，那里新出现的指令文件以「Additional instructions from」追加，改动与消失各有一条通知。上游明言它绝不请模型压缩指令文本，超预算只会整份省略宽泛文件、截断最具体文件并给出可见通知。
- **理由**：这是工作流级共同指令抵达模型的唯一通道。runner 把工作流级指令物化为 `workspace/AGENTS.md`，Action 会话的 cwd 就是工作区，于是每个 Action 都无条件读到同一份——对应"人在项目文件夹里起 dsh"的体验（ADR-0013），也是 ADR-0016 三层设置里"工作流 AGENTS.md"这一层的落点。它与 Skill 的分工由此清楚：Skill 是模型看描述自选的能力，AGENTS.md 是必须遵守的规范。两处钉住让它在本项目里安全：一、`$DSH_HOME` 在 spawn 时注入为 `<run>/home`，那里没有 AGENTS.md，机器主人的 `~/.dsh/AGENTS.md` 不会混进来；二、工作区里放了一个空的 `.git` 目录，`projectRootMarkers` 默认 `['.git']`，向上发现走到工作区就停——否则 `data/` 若处在某个 Git 仓库里，指令链会越出运行边界，把仓库自己的 AGENTS.md（本仓库那份就是写给编码 agent 的）读进业务 Action 的上下文。上游列的"symlink 跨信任边界"限制在这里不成立：工作区内容全部由本站物化，不加载陌生仓库。发现按目录、候选名固定为 `AGENTS.md` / `CLAUDE.md`（及 `.local` 变体）：Action 在工作区子目录里写出这两个名字的文件，被 read/write/edit 触到后就成为那个目录的附加指令——这是上游语义，不是本项目的功能。输入文件不会撞上这条规则：输入节点叫 AGENTS / CLAUDE（含 `.local`）时，`runner.ts` 物化 `inputs/<节点>/` 下的文字与 JSON 文件给文件名加 `输入-` 前缀避开。
- **配置要点**：`maxBytes: 135168`（= 65536 + 65536 + 4096，必填项，上游没有默认值；见「定制」）；`dshHome` 不配，跟随子进程 `DSH_HOME=<run>/home`；`projectRootMarkers` 与候选文件名取上游默认。与 headless 的差异只在环境：projectRoot 由工作区内的空 `.git` 钉住，`$DSH_HOME/AGENTS.md` 是全局设置的默认指令（ADR-0016），`workspace/AGENTS.md` 是工作流指令。
- **定制**：配置 / `maxBytes` 135168（全局默认指令上限 + 工作流指令上限 + 帧余量）/ 上游预算是整批的：`$DSH_HOME/AGENTS.md` 与 `workspace/AGENTS.md` 合在一起算，超限先整份省略前者；两份各 64 KiB 的写入口上限合计超过 base 的 65536 时全局默认指令会被静默丢掉，预算盖过两份之和后超限只可能在编辑期出现 / 上游文件 `packages/context/agent-instructions/src/config.ts@0.1.1-rc.2`
- **可按工作流切换**：否

### `@deepseek-ai/dsh-spill`
- **seam 角色**：Service Definition（`ctx.spillStore`）
- **决定**：挂（不是组合行；spill-local 的 peer，随它进入闭包）
- **它给会话带来什么**：不直接影响模型。它定义"把某个工具过大的文本整份存起来，换回一个不透明的定位信息与取回指引"这件事；落点、命名与取回方式由 provider 决定，seam 本身没有取回与删除 API，也不做访问控制。
- **理由**：它的消费方是 spill-policy（任何工具的超大纯文本结果）与 tool-fs-search（glob/grep 超上限时的完整结果集），两者只认这个 seam，换 provider（例如将来把 fs 与 subprocess 搬到 E2B 远程沙箱，组 9）不动它们。bash 的长输出不经它：subprocess-local 有自己的"完整输出保存到文件"机制，落在 `os.tmpdir()` 下的进程级私有目录，经 spawn 注入的 `TMPDIR=<run>/tmp` 已在运行目录内（组 2）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-spill-local`
- **seam 角色**：Service Provider
- **决定**：挂
- **它给会话带来什么**：过大的工具文本落成 `<root>/session-<hash>/<random>-<name>` 的本地文件，排他创建、权限仅限所有者；模型看到的是这条路径，加"用 `read`（offset/limit）或 `grep` 这个路径"的取回指引。
- **理由**：headless 会话同样挂它，spill-policy 与 glob/grep 的落盘都靠它。唯一动的是 root。上游省略 root 时在 `os.tmpdir()` 下延迟建一个进程级私有（0700）目录——那是为多用户共享机器上"别的本地用户读不到、也塞不进 symlink"设计的默认值；本项目每运行一个子进程、整个运行目录本就私有，需要的反而是"落点在运行目录内"：上游自己声明这个后端不做生命周期清理、靠外部，钉进运行目录后运行删除就是那个外部清理，磁盘统计与文件预览也只认运行目录。钉到 `<run>/home/spill` 而不是工作区内部，因为它不是产物：不该被 glob 扫进，也不该被下游当成上游写的文件。取回靠 `read`，上游任何沙箱模式都不限制读，所以落在工作区之外仍读得到。`TMPDIR=<run>/tmp` 本已把 `os.tmpdir()` 拉进运行目录，不钉 root 也不会跑出去，但显式钉住不依赖这个巧合，读组合文件时一目了然。
- **配置要点**：`root: <run>/home/spill`；上游默认省略（`os.tmpdir()` 下的进程级私有目录），base 也不配 root。
- **定制**：配置 / root 钉到 `<run>/home/spill` / 不钉 root 时默认在 `os.tmpdir()` 下建进程级私有目录，落点跑出运行目录 / 上游文件 `packages/spill/spill-local/src/store.ts@0.1.1-rc.2`
- **可按工作流切换**：否

### `@deepseek-ai/dsh-spill-policy`
- **seam 角色**：Consumer（`tools/post-execute` 转换器；不注册服务）
- **决定**：挂
- **它给会话带来什么**：任何工具的最终纯文本结果超过 `maxInlineBytes` 时，模型看到的是有界的首尾预览加一句 `(Omitted N bytes. Full formatted result stored at: <路径>. Use read with offset/limit, or grep this path to search within it.)`，整条替换不超过上限；不超限的结果、嵌套调用、`read` 的结果、被 block 的反馈、含非文本块的结果原样通过。存储失败保留内联结果，不把成功调用变成错误。
- **理由**：这是通用兜底。bash 与 glob/grep 在获取时就各自做保留与落盘，而 MCP 工具、本项目的 Tool 插件这些没有自己做保留的工具，全靠它把结果压回预算内（`web_search` 只对来源条数做保留，正文同样归它）。对本项目尤其要紧的两点：一、Tool 插件是用户在库里写的代码（ADR-0017），`output.render` 想返回多少就返回多少，没有这一行，一个把整份表格渲染成文本的 Tool 会把整个上下文塞爆；二、它把 `read` 排除在外，是因为 read → spill → read 会成环，而 read 自带 offset/limit 分页——这正是模型回读 spill 文件的方式。50000 是 base 的值，单位是 UTF-8 字节而不是 token，中文约合一万六千余字；预览大小与工具结果预算的关系上游已经调过，没有证据要改。它从不成为节点失败的原因。
- **配置要点**：`maxInlineBytes: 50000`，与 base 相同。必须显式写：上游省略该键等于整个策略禁用。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-output-retention`
- **seam 角色**：库
- **决定**：挂（不是组合行；spill-policy 与 tool-fs-search 的 peer 依赖）
- **它给会话带来什么**：不直接影响模型。提供 `TextRetainer` / `ItemRetainer`：按字节或按条目保留 head / tail / headTail，并给出精确的省略数，供工具生成"保留了什么、省了多少"的通知。
- **理由**：spill-policy 的首尾预览、glob/grep 的第一页都用它裁；挂了那几行它就在闭包里。值得记的是它的两条边界：`truncated` 只表示预算裁剪，从不表示上游不完整（权限失败、二进制跳过留在工具自己的字段里）；文本按字节计数并在切口处保住完整码点、首尾分开解码——中文预览不会在半个字处断开。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-token-meter`
- **seam 角色**：Service Provider（单例 `ctx.tokenMeter`；没有独立的 seam 定义包）
- **决定**：挂
- **它给会话带来什么**：不直接影响模型。它不加提示词、不加 schema、不发模型调用，只回答"当前请求有多大"：从持久日志按会话折叠出压力，同一规范 envelope 内复用 provider 报回的真实用量，只对增量用"4 字符≈1 token"的固定启发式估算。
- **理由**：compaction-basic 的必需依赖，没有它压缩后端装不上。上游自己标注这个启发式对 CJK 与 JSON schema 严重低估；对本项目的含义是中文产物读进上下文时增量估算偏小、压缩触发偏晚，但锚点仍是 provider 用量，每完成一步就校正一次，偏差不累积。它 peer 依赖 session-projection，但那三个投影单元（tokenUsage / contextPressure / contextBreakdown）是可选子 fiber，注册表不在时静默跳过——我们不挂 session-projection（组 4），meter 照常工作，只是没有那三个投影；本站的用量统计走 usage chunk 落 `node_usage`，不需要它们。无配置项，上游明言任何配置键都会被拒。
- **配置要点**：上游默认（无配置项），与 base 相同。
- **可按工作流切换**：是

### `@deepseek-ai/dsh-compaction`
- **seam 角色**：Service Definition（`ctx.compaction`、`compaction/*` 事件、检查点来源构造）
- **决定**：挂（不是组合行；compaction-basic、token-meter 与 pruner 的 peer）
- **它给会话带来什么**：定义"判定历史过大、把较早范围摘成一个表层节点"的契约与事件形状；seam 本身不改写任何东西。
- **理由**：随 provider 进闭包。值得记的是它的表层约定，因为本站的轨迹视图读的就是这份 JSONL：成功压缩只有一处表层变更——一条带 `surfaceOp: replace` 的 user/message 检查点；`compaction/start`、`compaction/summary`、`compaction/end` 只进日志不进表层，被遮蔽的原始事件仍留在日志里，回放确定。`src/server/harness/trajectory.ts` 把 start → summary → 替换检查点 → end 合成一条「上下文已压缩」记录，摘要正文、替换后的检查点与那次调用的用量都在这条记录里，前缀凭空变短由此有据可查；`compaction/prune` 与紧随其后的替换 `tool/result` 同样合成一条剪枝记录。events.ts 则把 start、summary、带 error 的 end 与 prune 落成 `run_events` 的 compaction 事件（prune 之后带 `surfaceOp: replace` 的 `tool/result` 是裁剪副本，原始结果已落库，不再落第二条 tool 事件）。上游没有面向模型的压缩工具，人用的 `/compact` 命令在组 6 不挂。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-compaction-basic`
- **seam 角色**：Service Provider
- **决定**：挂
- **它给会话带来什么**：每步派生请求前检查压力；越过 `floor(容量 × 0.8)` 时先让 pruner 改写超大工具结果并重新计量，仍超就用一次独立的 `llm/stream` 调用把最旧的完整单元摘要成一条 `<compacted-summary>` 检查点，逐字保留最近约 16% 容量的尾部，切口对齐到工具调用/结果配对平衡处；provider 报上下文溢出时绕过阈值，直接做一次最大平衡缩减再重试。摘要失败不替换、带着完整历史继续。
- **理由**：与 headless 会话一致的兜底。本项目的会话形态让它很少触发——每个 Action 是全新会话、步数上限 40、实质内容在文件里而不在提示里（ADR-0008、ADR-0012）——但一旦触发它就是节点能否收束的差别：读一份几十页 PDF 的 `pdftotext` 输出、几轮对大文件的 grep，都能把一个会话推到窗口边缘，没有压缩的结局是 provider 报 `CONTEXT_WINDOW_EXCEEDED`、节点失败。摘要丢细节在这里代价最低：产物在工作区文件里，摘要里保留着路径，模型可以重读（ADR-0008），与人在 CLI 里被压缩后"再看一眼文件"完全相同。三件事本项目要明白。一、摘要是一次真实的付费调用：逐字回放会话前缀加一段固定指令，输出上限 8192 token；它不经 agent loop，用量不以 usage chunk 到达，而是挂在 `compaction/summary` 事件上——events.ts 从 `assistant/chunk` 收 usage 的路径收不到它，所以 `src/server/engine/events.ts` 另从该事件读 usage 与事件自带的 provider/model，落成 `node_usage` 一条明细（messageId 取 `compaction:<seq>`，重放不重复），随节点累计进 `run_nodes.cost`；摘要不是账外支出，这一点与搜索三件套不同（组 2）。例外：摘要在提交阶段失败（中止、表层被并发改动、commit 抛错）时上游只写带 error 的 `compaction/end`、不写带 usage 的 summary 事件，那一次已付费的调用无法计费——上游事件模型的限制，成本页会少算。因为逐字回放前缀，provider 的 KV 缓存命中，实际输入成本以 cache-read 为主。二、摘要路由默认空对，回退到会话最新一次请求的 provider/model，也就是 Action 自己的模型，不会跨到别的路由。三、容量来自 llm-deepseek 适配器对该路由的声明；拿不到容量时自动检查只警告一次、带着完整历史继续，溢出恢复仍会尝试。上游的摘要指令是一段面向"AI coding assistant"的固定英文结构（Files and Code、Errors and Fixes 那套），只能子类覆盖 `summarize()` 才能换；对业务型 Action 不贴切但无害，是已知的上游形态，不 fork。
- **配置要点**：上游默认（`thresholdRatio` 0.8、`retainRatio` 0.16、`maxTokens` 8192、`compactionRetries` 1、`maxOverflowRetries` 1、`auto` true、摘要 provider/model 空对），base 同样不配。
- **可按工作流切换**：是

### `@deepseek-ai/dsh-compaction-tool-result-pruner`
- **seam 角色**：Service Provider（`ctx.toolResultPruner`；compaction-basic 经可选 `ctx.get` 读取）
- **决定**：挂
- **它给会话带来什么**：只在压缩触发条件成立后起作用：文本超过 8192 码点的 `tool/result` 被改写成前 4096 码点、`[... tool result middle pruned ...]`、后 1024 码点；原事件留在日志里，非文本块保持原位；不发模型调用。低于压力阈值的步骤绝不剪枝。
- **理由**：它是压缩的第一阶，无模型的那一步：多数时候把几个大工具结果剪掉，压力就回到阈值以下，摘要那次付费调用根本不用发。对本项目这是直接的省钱项——工具结果（bash 输出、read 分页）正是会话里体积最大的东西。没有 compaction-basic 时它不起任何作用，所以它只随 compaction-basic 一起有意义。组合里它排在 compaction-basic 之后，与 base 的行序相同；上游声明行序不带装载语义，compaction-basic 是按需 `ctx.get` 它。
- **配置要点**：`thresholdChars` 8192、`headChars` 4096、`tailChars` 1024，与 base 相同，也是上游默认。
- **可按工作流切换**：是

### `@deepseek-ai/dsh-repeat-tool-reminder`
- **seam 角色**：Consumer（`tools/post-execute` 监听；不注册工具）
- **决定**：挂
- **它给会话带来什么**：同一工具以完全相同的规范化参数连续调用到第 3 次，模型收到一条简短提醒（分析上次结果、换方案或结束）；第 5、8 次收到详细版，列出工具名、连续次数与参数前 500 字符。不否决、不改写：提醒作为带来源的合成 user 消息追加在那一步的工具结果之后，被拒绝的调用也计数，穿插的其它工具调用不打断链。
- **理由**：无人值守下最便宜的止损。上游 agent-loop 没有步数上限，本项目在会话 scope 上补了 40 步的硬上限（组 10），但硬上限只会让节点失败；提醒在第 3 次就介入，给模型一次自我纠正的机会，把"空转到步数耗尽后失败"变成"第 3 步收到提示后换路"。两个上游细节对本项目正好：一、被 pre-execute 拒绝的调用也计数——Action 级收窄分两层（ADR-0015）：`tools.restrict` 让工具从清单上消失，模型看不见就不会调；`tools.guard` 按全局停用清单在执行时按名拒绝，兜住会话建立后才注册的工具（迟连的 MCP 服务器）。模型反复撞一个被 guard 拒绝的工具正是这条链要打断的循环；二、链按 agent 分键、用户提示重置链，每个 Action 会话一条提示，链从零开始，跨会话不串。已知边界：只认精确匹配，改一个字符就逃过；超过 8 次不再提醒，之后交给步数上限。
- **配置要点**：`thresholds [3, 5, 8]`、`argumentsPreviewChars 500`，与 base 相同；`include` / `exclude` 取上游默认，都为空，跟踪全部工具。上游 README 的示例把 `todo_write` 列进 exclude，那是示例不是默认值，base 也没有排除它。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-call-timeout-policy`
- **seam 角色**：Consumer（`tools/execute` 环绕包装；不注册工具、不接受配置）
- **决定**：挂
- **它给会话带来什么**：对在 `ToolDefinition` 上声明了 `timeoutMs` 的工具，设一个与调用方取消融合的协作式截止；先到时把结果换成 `Error: tool call timed out after <ms>ms`（结构化 `TOOL_TIMEOUT`），并挡掉迟到的大结果。不超时的调用零开销，未声明预算的工具原样通过。
- **理由**：零配置、零风险——它不发明预算，只强制执行工具自己声明的那份：tool-web 的 `searchTimeoutMs`（我们给 60 秒，组 2）、tool-fs-search 给 `glob`/`grep` 声明的 `timeoutMs`（上游默认 30 秒，组 2），以及本项目的 Tool 插件若在定义上声明了 `timeoutMs`。没有它，这些声明只是字段，一个挂住的搜索会一直吃到节点墙钟。MCP 工具不经它：mcp-client 的 `toolCallTimeoutMs` 是交给 MCP SDK 请求本身的 `timeout` 选项，桥接出来的 `ToolDefinition` 上没有 `timeoutMs`（目录一句话理由、组 2 的 mcp-client 行与 `composition.ts` 的行注释同此口径）。它是协作式而非硬终止：截止只经 `exec.signal` 通知，忽略信号的工具不会被停下——所以 bash 的超时不靠它，靠 bash-sandbox 自己的 `timeoutMs`（120 秒，组 2）与进程组终止；上游明言 bash/read/write/edit 有意不声明。
- **配置要点**：上游默认（无配置项），base 同样一行裸挂。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-timeout`
- **seam 角色**：库
- **决定**：挂（不是组合行；timeout-policy、llm、llm-retry、subprocess-local 等二十余个包的 peer）
- **它给会话带来什么**：不直接影响模型。提供 `deadline` / `idleWatchdog` / `timeoutOf`：把上游取消与本地超时融合成一个 AbortSignal，并在事后分辨"超时"与"被取消"。
- **理由**：只做时序与分类，不负责终止——每个能力自己接终止路径（bash 杀进程组、web 关套接字），上游有意不做"超时服务"。它在闭包里是必然的；值得记的是它定的口径：第一个中止原因决定分类，上游每个能力对"超时"与"取消"的区分都是这一套——bash 的 `BASH_TIMEOUT`、tool-web 与 `glob`/`grep` 的 `TOOL_TIMEOUT` 在结果里能与按节点取消区分开，靠的就是它。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-todo`
- **seam 角色**：Consumer（注册工具 `todo_write`）
- **决定**：挂
- **它给会话带来什么**：一个 `todo_write(todos: [{ content, status }])` 工具，每次整表替换，结果是一句 `Updated todo list: N pending, N in progress, N completed.`；schema 是每个请求的固定开销，整表随每次调用进入历史直到压缩。列表属于调用它的那一个会话，没有 subagent 或共享 scope。
- **理由**：headless 会话里有它，而它不需要有人在：它是模型的自我组织工具，读者是模型自己——下一步看自己上一步写的计划。上游的工具描述让模型在多步任务开始前列步骤、随做随标，对"读几份输入、转换、写产物、报结构化结果"的 Action 形态正合适；简单单步任务模型按描述不会用它。事件 `todo/write` 进会话 JSONL；本站轨迹视图不单独投影这个事件（列在 trajectory.ts 的不展示清单里），但 `todo_write` 的工具调用记录照常显示，参数本身就是整表，计划在轨迹面板里看得到。它 peer 依赖 session-projection，但 `todos` 投影单元是可选子插件，注册表不在时工具照常注册，只是没有投影，本站不需要。`allowParallelInProgress` 是必填项，同时改工具描述与校验，取 base 的 `true`：上游的 `false` 是"单活跃项纪律"，给人盯着的交互式会话用；无人值守的 Action 只需要模型能如实标记它正在并行推进的几件事（例如同时读几份输入），不该因为标了两个 in_progress 而收到错误。
- **配置要点**：`allowParallelInProgress: true`，与 base 相同。
- **定制**：配置 / `allowParallelInProgress` = true / 必填项，取上游 base 的值；多步任务允许同时几项进行中 / 上游文件 `packages/todo/tool-todo/src/index.ts@0.1.1-rc.2`
- **可按工作流切换**：是

### `@deepseek-ai/dsh-time-context`
- **seam 角色**：Consumer（`agent/pre-step` 前置监听，注入带来源的 user 消息）
- **决定**：不挂
- **它给会话带来什么**：每个合格的步骤前注入三行——采样时间戳、本次请求的浏览器时区、距上一条可见消息的时长——累积到压缩遮蔽为止。
- **理由**：上游 base 与 headless 都不挂，只有 Schedule 的 Web overlay 挂；不挂就是跟上游。更要紧的是它在本项目里会帮倒忙：浏览器时区来自 Web 宿主绑定到 `user-rpc` 消息来源的采样，本项目的会话经 ontoflow-rpc 创建、没有浏览器，来源永远是 `unavailable`，而上游在这种情况下给模型的指令是"要求用户澄清"——无人值守的 Action 会被要求向不存在的人澄清时区。`refreshIntervalMs` 省略时每步注入一条，对 40 步的会话就是 40 条无用消息。需要日期的 Action 由 prompt 直接给日期，或在会话里 `bash date`（bash 是每个会话都有的内置，ADR-0011）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tmux-context`

- **决定**：不挂
- **它给会话带来什么**：进程位于真实 tmux pane 时，每轮第一个步骤注入 session / window / pane 与布局的两行读数。
- **理由**：上游 Web 与 headless 组合都不含它。运行子进程由 Next 进程 spawn，不是人在终端里起的会话；即便 Next 本身跑在某个 tmux 窗格里，那个窗格的位置对 Action 也没有任何意义，挂上只是每轮多跑一条 shell 命令。它是给"人在 tmux 里开着 agent、想让 agent 知道自己在哪个窗格"的场景。

### `@deepseek-ai/dsh-persona`
- **seam 角色**：Consumer（在 agent scope 内占 `deployment:persona` 段落）
- **决定**：不挂
- **它给会话带来什么**：为某一个 agent 遮蔽部署级 persona，或（`complete: true`）把这段 persona 变成唯一的系统提示段落。
- **理由**：它只能在 agent scope 内、经 agent preset 的组装挂载——在 scope 外挂会与 system-prompt 注册表自己的 `deployment:persona` 相撞报错。本项目不用 preset（ADR-0015），Action 之间的差别在会话创建窗口收窄；而我们的部署级 persona 本就留空（组 1：headless 给的是 "You are a coding agent powered by {{model}}…"，我们去掉，一切规范以文件进入），没有需要按 Action 遮蔽的东西。Action 的身份与任务在 prompt 与 rule 里，进的是首条 user 消息，不是系统提示。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-agent-tool-presentation`
- **seam 角色**：Consumer（在 agent scope 内调用 `ctx.tools.presentAs()`）
- **决定**：不挂
- **它给会话带来什么**：为某一个 agent 选工具呈现形态——`native`（全部 schema）、`code`（只有 `run_code` 加生成的 SDK）或 `both`。
- **理由**：同样是 preset 专用行（ADR-0015 不用 preset），而且它有意义的前提是 Code Mode 可选：code-runtime 不挂（组 2），选 code 会停在 pending、preset 拒绝挂载。我们不给 tools 行配 `mode`，全部会话按 schema 默认走 native；headless 把 `tools.mode` 交给 `DSH_TOOLS_MODE` 环境变量，我们连这个开关都不接——与 headless 基线的这处差异，理由记在组 2 的 code-runtime 行。
- **可按工作流切换**：否
