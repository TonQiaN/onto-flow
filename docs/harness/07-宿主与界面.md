# 07 宿主与界面

> 默认方向：不挂：不影响 agent。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这一组是上游为了"把一个 harness 进程做成一个产品"而存在的行：浏览器客户端与它的宿主半边、把 base 叠成 web / headless 两种产品形态的 bundle、生成的远程反射与 RPC 网关、宿主级的存储与实体登记、用户设置文档、启动器与应用之间的命令行交接、热加载、以及让模型改自己运行时的自指工具集。判据只有一条，而且是上游自己在每个包的「模型体验」一节写下的：这些行**不向模型请求贡献任何内容**——不注册工具、不注入提示词、不写会话事件（少数几行有间接影响，逐行注明）。它们服务的对象是坐在浏览器前的人、一个长驻的宿主进程、或一台开发机上的热重载循环。

本项目三个事实让这一组整体落在「不挂」：**运行中没有人在**（一个 Action 会话从受理到收束不需要任何人点选目录、看清单、改设置）；**宿主是 Next 进程**（REST 路由、设置文档、运行目录、插件面板全部在 Next 侧，每次运行只起一个短命的 harness 子进程，ADR-0007）；**运行受理时定义已冻结**（组合、设置、Action 定义在受理那一刻定型，热加载与模型自改运行时都与"运行快照"直接冲突）。于是这一组没有"去掉要给理由"的举证负担，但有另一种负担：上游 base 里确实挂着这一组的几行（`hmr`，`typert` / `typert-loader` / `typert-gateway`，`agent-default-model`，以及挂 `dsh-settings-file` 的 `settings`），headless 参照会话里它们也是 active 的，只是对模型而言是空转；文档要写清每一行在参照会话里是什么状态、我们不挂之后少了什么、以及那件事在本项目由谁接管。

有两个词在这一组里与上游同名不同义，读上游 README 时要留心：上游的 **Workspace** 是宿主登记的用户目录实体（带标题、带会话归属），本项目的**工作区**是运行目录下全部 Action 共用的会话 cwd；上游的 **settings** 是 `$DSH_HOME/settings.yaml` 热加载文档，本项目的**设置**是 SQLite 里的单行 JSON 文档、运行受理时冻结进组合。词汇以 CONTEXT.md 为准，这里不另造名字。

## 逐行

### `@deepseek-ai/dsh-client-*`
- **seam 角色**：Consumer（浏览器半边）；`dsh.client` 名册整体是 web-app bundle 的一部分
- **决定**：不挂
- **它给会话带来什么**：无。上游每个客户端包的「模型体验」一律写"无，这里没有任何内容进入模型请求"：模块装载器、连接层、运行时对象、slot 与 UI 功能包都只在浏览器与宿主之间搬运已经组合好的消息。
- **理由**：这一族是 `packages/client` 下的 40 个包（`web`、`connection`、`runtime`、`modules`、`hmr`、`locale` 与 34 个 `ui-*`），加上住在 `packages/extensions` 的浏览器半 `ui-cordis`，npm 名一律 `@deepseek-ai/dsh-client-<name>`。它们是**双面包**：node 半扫描 Loader 树、把浏览器半经 `/plugins/<id>/client.js` 下发，浏览器半在页面里由 `client-web` 的启动内核挂成 cordis 树。没有 `dsh-host-webserver` 时 node 半没有路由可注册，没有页面时浏览器半根本不会被取走——挂了也是一堆没人服务的行。上游 base 不挂任何客户端包，只有 web-app bundle 的 `dsh.client` 名册才挂它们，因此 headless 参照会话里本来就没有这一族；这是我们与参照会话**零差异**的一行。本项目的界面是 Next 的 App Router 页面（工作流画布、运行页、系统健康页、五个库页），运行详情从运行目录的会话 JSONL 投影（组 4），不经浏览器 RPC。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-host-*`
- **seam 角色**：宿主插件族：`directory-picker` 是 Service Definition（`ctx.directoryPicker`），`-native` / `-browse` / `-auto` 是它的 Provider；`webserver`（`ctx.webServer`）、`apiproxy`（`ctx.apiProxy`）、`plugin-inventory`（Remote `pluginInventory/list`）、`frontend-static`（占 webserver 的回退席位）是宿主侧服务
- **决定**：不挂
- **它给会话带来什么**：无。八个包的「模型体验」全部为"无"：HTTP 载体、SPA dist 服务、Loader 清单的只读投影、目录选择——没有一样进入模型请求。
- **理由**：这一族只在 web-app bundle 里出现（`webserver`、`api-gateway` 行挂的是 `dsh-host-apiproxy`、`plugin-inventory`、`directory-picker`，`frontend-static` 由 web-app 的 `web-runtime` 粘合插件挂上），base 与 headless 都没有，因此仍是与参照会话零差异的一行。每一个都在本项目有明确的替身，且替身都在 Next 侧：`webserver` 与 `apiproxy` 对应 `src/app/api/` 下的路由与 `handle()`；`plugin-inventory` 对应 `/api/settings/composition`——但两者语义不同，上游报的是一个活着的 Loader 树"调用当下"的条目与 fiber 阶段，我们报的是**推导**（下一次运行会挂什么）加最近一次运行真实落盘的 `cordis.yml`，因为没有长驻宿主树，"现在挂了什么"在没有运行时不成立；`directory-picker` 对应的是"没有人选目录"——运行目录由 Next 在受理时创建（ADR-0007），工作区是运行的产物而不是操作者的选择。上游 `webserver` 自己也声明不提供 TLS、认证与来源策略，`connection` 的 `/api` 信任栅栏是可达性策略而非认证；本项目同样没有认证（根 AGENTS.md：no middleware, no auth），但暴露面在 Next 的 3592 端口而不是每个子进程各开一个。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-web-app`
- **seam 角色**：bundle（浏览器表层的 patch 层）+ `web-runtime` 粘合插件
- **决定**：不挂
- **它给会话带来什么**：这是本组少数**有**模型可见效果的行：`surfaceContext: true` 时它注册全局提示词段 `app:web-surface`（告诉模型本地 URL、"this page"指什么、不要另起服务器）与 `harness:source` 段（Harness 源码在磁盘的位置），并向受管 bash 环境加入 `DSH_WEB_URL` 变量；每个会话固定多一行源码说明、一段提示词与两行受管环境变量。`surfaceContext: false` 时三者都不注册。
- **理由**：不挂它首先是因为它描述的世界不存在——没有页面、没有 URL、没有"当前页"，那段提示词会把模型引向一个不存在的 GUI。其次是它的 patch 做的事与本项目的两条决定正面相反：它把 base 的 agent 面（`tool-bash`、`tool-fs`、`skill-filesystem`、`compaction-basic`、`agent-instructions`、`tool-todo` 等）全部 `disabled: true`，再让每个会话去挂一个 agent preset；本项目的 Action 级差异在会话创建窗口收窄、不用 preset（ADR-0015），这些行在我们的清单里是平铺的挂载行（组 2、3）。它还带来 `storage`、`workspace`、`api-remotes`、`cordis-host-runner` 等本组其它不挂的行。web-app 与 headless 是同一 base 之上的两个同级表层，上游自己说 headless 不挂本包；我们以 headless 会话为参照（ADR-0013），本行与参照零差异。它有一个值得记的副作用：Web 模式的 `deepseek-official` 重试默认值是"首次请求后最多再重试五次"，上游注明这是共享默认、非 Web profile 省略 `retryPolicy` 时行为相同——我们的 `llm-retry` 行走的就是这个共享默认（组 1）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-headless`
- **seam 角色**：bundle（一次性运行器的 patch 层）+ `headless-runner` / `headless-startup` 两个插件
- **决定**：不挂
- **它给会话带来什么**：上游「模型体验」写"无影响"：runner 把任务作为普通用户消息提交，提示词与工具由 base 与 headless patch 的其它行提供。但它的 **patch** 改了模型可见的东西：persona 设为"You are a coding agent powered by the {{model}} model. Your working directory is {{cwd}}."，并把 Code Mode 的 worker（`code-runtime-worker-thread`）挂为核心执行能力、`tools.mode` 读 `DSH_TOOLS_MODE`。
- **理由**：这是**体验基线而不是组合行**（ADR-0013）：一个 Action 会话应当与人在工作区里敲 `dsh --profile headless "<task>"` 得到的会话体验一致。它做的事——从 `ctx.agentDefaultModel` 取模型、经 `ctx.agents` 创建一个全新的持久化 Agent、把任务作为用户消息提交、等停稳、flush 会话、把最后一条非空 assistant 文本写到 stdout、经 `ctx.appExit` 退出——在本项目被拆成两半各自接管：会话由 `ontoflow-rpc` 按 `session/prompt` 懒创建，provider/model 由每个 Action 的定义经 RPC 显式给出（不经 `agentDefaultModel`），结果不走"最后一条文本"而走会话 scope 上的 `structured_output` 两阶段提交与 `session/output`（ADR-0008，组 10），退出由 `runner.ts` 自己拥有（stdin EOF / SIGTERM 收束为 0，SIGINT 为 130）。它也**挂不上**：`headless-startup` 注入 `cmdlineArgs`、runner 经 `ctx.appExit` 退出，两者都由 `dsh` 启动器在任何条目挂载前提供，上游明说"在 `dsh` 启动器之外启动 headless profile 会在激活时明确报错"；我们的 runner 不是那个启动器。patch 里与参照会话有三处差异，各在其组记账：persona 我们固定为空串、规范全走文件（组 1 `system-prompt`，组 3 `dsh-persona`）；Code Mode 不挂（组 2 `code-runtime`，上游自己标注 `DSH_TOOLS_MODE` 是临时开关）；`hmr` 它 `disabled: true`，我们根本不挂（本组下文）。stdout 的用法也不同：headless 把答案打到 stdout，我们的 stdout 是协议帧（本组 `logger-console` 一行）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-base`
- **seam 角色**：bundle（每个 profile 的第一层 patch）
- **决定**：不挂
- **它给会话带来什么**：上游「模型体验」写"通过插入的行间接产生影响"：它选定无 persona 的提示词基座、工具集合与 DeepSeek 适配器，自身不贡献任何模型可见文本。
- **理由**：不叠、逐行审，是 ADR-0013 的正文。两个具体原因：其一，patch 的语义是**按 id 整行替换 `config`**、没有深合并，上游 README 自己列为已知限制（"profile 覆盖必须重述该行需要保留的每个字段"）；对程序化生成的每运行组合，这意味着每一行都要重述一遍，叠 base 只多一层要维护的间接性。其二，base 是给"一个人、一个长驻进程、一个 `$DSH_HOME`"设计的：它用 `!!js dshHomePath('sessions')` 钉持久化根、用 `!!js process.cwd()` 钉工作区根、用 `!!js process.env.DSH_PERMISSION_MODE` 决定沙箱与审批，还挂着 `settings-file`、`session-telemetry-otel`（指向 deepseeksvc.com、靠环境变量关）、`llm-pi-ai`（休眠双胞胎）、`session-projection`、`jobs-local`、`subagent` 家族与 `tool-ralph`。这些在本项目里要么归 Next 侧（路径与开关全部由 `composition.ts` 从运行目录事实与设置文档生成），要么是组 5、6、8 明确不挂的行。反过来看差异：我们默认清单里的行几乎全是 base 里有的行，不在 base 里的只有三类——按设置逐台生成的 MCP 行、按运行物化的 Tool 插件行、以及 `ontoflow-rpc`（组 10）；base 里有而我们没挂的行按组分别记账（组 5–8 的全部行，加上本组的 `hmr`、`typert` / `typert-loader` / `typert-gateway`、`agent-default-model`、`settings`）；config 值不同的行在各自的组写「配置要点」（例如 `bash-sandbox` 的 `timeoutMs` 上游 60 秒、我们 120 秒；`approval` 上游按 `DSH_PERMISSION_MODE` 决定 `ask`、我们固定 `never`）。base 的行集合本身是升级时逐组重审的 diff 基准（docs/harness/AGENTS.md）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-api-gateway`
- **seam 角色**：Service Definition 与 Provider 同包（Host 入口提供 `ctx.typertGateway`，`/client` 入口提供 `ctx.remote`）
- **决定**：不挂
- **它给会话带来什么**：无。上游「模型体验」写"无，因为该包分发应用调用，不注册任何提示词、工具或会话事件"。
- **理由**：它是浏览器客户端与宿主之间的 Typert 一元 RPC 分发器：把生成的 `InvocationDescriptor` 解析成对某个 Cordis 服务方法的调用，传输交给 `connection`，业务选择交给 `api-remotes`。本项目的线协议是 `ontoflow-rpc`——stdio 上的换行分隔 JSON-RPC（`dsh-sdk-protocol` 的传输，组 1；服务端是 fork，组 10），Next 侧直接调 `session/prompt`、`session/cancel`、`session/close`、`session/output`，不需要一层"从描述符找服务方法"的反射分发。**上游 base 挂它**（`id: typert-gateway`），headless 参照会话里它是 active 的，但没有 `connection` 时它不在任何 `/api` 上注册拦截器，纯粹空转；上游 README 自己写"Connection 可用时"才注册。我们的差异只是少了一个空转的服务。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-api-remotes`
- **seam 角色**：Consumer（双侧 BFF：Host 入口是 Agent/Session 查找策略，Client 入口挂载生成的 `/remote` 贡献）
- **决定**：不挂
- **它给会话带来什么**：无。上游「模型体验」写"无，因为该 BFF 只选择 Remote 应用方法和身份策略，不注册任何模型接口"。
- **理由**：它随 `api-gateway` 一起不挂，而且它比网关更明确地属于 web-app（只有 web-app patch 挂它，base 没有）。它的 Host 入口做的是"复用 live Agent、恢复冷会话、对并发恢复去重、保留 subagent ownership fence"——全部是长驻宿主里跨会话查找的策略；本项目每次运行一个进程、每个 Action 一个会话、会话 id 就是节点 id、运行结束进程消失，没有"冷会话"可恢复，也没有第二个客户端来查。它转发的 Host 事件名单（`agent-presets`、`commands`、`credentials`、`llm`、`settings` 的事件）里，本项目会用到的只有 `llm`——而我们直接经会话事件流拿到它们（`onSessionEvent` 实时落 `run_events`）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-typert-*`
- **seam 角色**：`registry` 是 Service Definition（`ctx.typert`）；`loader` 是 Consumer（扫 Loader 条目、注册生成的宿主产物）；`generator` 是构建时库；`protocol` 是库（装饰器与协议类型）
- **决定**：不挂
- **它给会话带来什么**：无。四个包的「模型体验」全部为"无"；registry 明言"所有模型可见投影均由 `cordis_inspect` 等消费方负责"。
- **理由**：Typert 是上游给浏览器 RPC 生成的运行时反射：`generator` 在构建时把源码类型变成 Zod schema 与 `TYPERT` 贡献，`loader` 在运行时逐个解析 Loader 条目的 `package.json`、导入 `./typert` 子路径注册进 `registry`，`gateway` 再据此分发。没有浏览器客户端，这条链的终点不存在。**上游 base 挂 `registry` 与 `loader`**（`id: typert`、`typert-loader`），参照会话里它们 active：loader 会对树上每个条目做一次包解析与可选导入，缓存到进程结束。我们的差异是少做这一遍扫描——我们的组合里有以绝对路径进入的行（`ontoflow-rpc`、Tool 插件），它们没有 `package.json` 与 `./typert` 出口，本来也无物可注册。`protocol` 出现在本项目 `package.json` 的依赖里，是因为已挂的 `dsh-session`、`dsh-agent` 等 peer 依赖它：它只提供 `@Remote` 一类装饰器，把标记存在模块私有的 `WeakMap` 里、不注册任何 Cordis 服务，没有 registry 时完全惰性。**装进 node_modules 不等于挂载**，本组多行如此，下面不再重复。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-storage`
- **seam 角色**：Service Definition（`ctx.storage`：具名后端注册表 + 数据形式挂载点）；后端 `storage-json` / `storage-sqlite` 与领域形式 `storage-domain` 是它的 Provider 与 Consumer（后端两行记在组 9）
- **决定**：不挂
- **它给会话带来什么**：无。上游「模型体验」写"`ctx.storage` 是主机侧注册表；中心不注册工具、不注入提示词，也不写入会话事件"。
- **理由**：这一族持久化的是"会话事件日志以外的应用数据"——今天只有 `workspace` 的实体记录，上游注明"未来的会话伴随元数据"也走这里。只有 web-app patch 挂它（`storage` + `storage-json` 根在 `dshHomePath('storages')` + `storage-domain` 路由到 `json`），base 与 headless 都没有，与参照会话零差异。本项目的应用数据有自己的家：五个库、运行、事件、用量、设置在 `data/ontoflow.db`（Drizzle + better-sqlite3），运行内的东西在运行目录。即便将来要给运行存伴随元数据，也是加一张表而不是在每个短命子进程里各开一个 JSON 单元文件——上游自己列的限制"没有跨进程写锁、两个进程写同一根目录时最后写入者胜出"正是并行运行会踩的坑（ADR-0007 要求运行互不可见）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-workspace`
- **seam 角色**：Service Definition 与实现同包（`ctx.workspaceRegistry`）
- **决定**：不挂
- **它给会话带来什么**：无。上游「模型体验」写"没有。`ctx.workspaceRegistry` 只向宿主侧消费方提供 workspace 记录……此包不注册工具、不注入提示词、不写入会话事件"。
- **理由**：上游的 Workspace 是**用户目录实体**：`realpath` 规范化的路径、标题、持久的 workspace 顺序、按新到旧的候选会话索引、全局归档集合，第一次启动时还要遍历全部已持久化会话按 cwd 分组。它服务的是 Web 侧边栏"工作区 → 会话"的导航，只在 web-app patch 里挂，且硬依赖 `storageDomain` 与 `sessionPersistence` 两个服务。本项目的"工作区"是另一个东西：运行目录下的 `workspace/`，由 Next 在受理时创建、是全部 Action 的会话 cwd、随运行删除而删除（ADR-0007）；"哪些会话属于哪次运行"由 `runs` / `run_nodes` 表回答，不需要按 cwd 反推。两个词同名不同义，见本文开头。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-settings`
- **seam 角色**：Service Definition（`ctx.settings`：namespace 注册与"schema 默认值 → 组合 `base` → 用户文档"三层解析）
- **决定**：不挂
- **它给会话带来什么**：间接。上游「模型体验」写"消费方插件从各自 namespace 解析影响模型的值（例如默认模型路由）；效果由各消费方自己的接口文档说明"。
- **理由**：这是本组最需要说清"不挂之后消费方怎么办"的一行，因为我们**已挂的行在消费它**：`llm-deepseek`、`agent-loop` 与（搜索开关打开时的）`web-search-deepseek` 都经 `installSettingsSection` 注册自己的分节；`shell` 只依赖它的类型与 namespace 词汇，不注册分节。上游 README 把答案写在第一段："不挂载提供方时消费方行为不变：仍只按 entry 配置解析，因此任何组合有无 settings 都能工作"——注册是 `ctx.inject(['settings'], …)`，服务永不出现时回调永不触发，消费方一直用它 `cordis.yml` 行里的 config。这正是本项目要的语义：设置是 SQLite 里的**单行 JSON 文档**，在写入口全量校验、运行受理时读一次、冻结进 `cordis.yml`（根 AGENTS.md 与 ADR-0016 的"运行快照冻结三层"）；一次改动作用于下一次运行，正在跑的运行持有它开始时的快照。挂上 `ctx.settings` 就是把"用户文档覆盖组合行、且热生效"的第三层引进子进程，与冻结快照直接矛盾。上游 README 还列了一条与我们相关的限制：`redactSecrets` 不是可证明的协议边界，机密能经 union/transform 抵达时会原样返回——本项目凭据只以引用名进入（ADR-0006），不经这条路。`dsh-settings` 在我们的 `package.json` 里是因为已挂行 peer 依赖它的 `installSettingsSection` 与 `settingsNamespace`，装进来的是库，不是行。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-settings-file`
- **seam 角色**：Service Provider（`ctx.settings` 的文件提供方：YAML/JSON 文档 + chokidar 热发布 + 写锁下的读-改-写）
- **决定**：不挂
- **它给会话带来什么**：间接，同 `dsh-settings`：它只存储并发布分节，效果经消费方产生。
- **理由**：**上游 base 挂它**（`id: settings`），默认值 `path` 为 `$DSH_HOME/settings.yaml`、`watch: true`、`debounceMs: 100`；参照会话里它 active，且是 Web 的 Models 页写模型选择、`llm-deepseek:` 分节覆盖适配器行的落点。我们不挂它有三层原因，一层比一层具体。语义层：它的存在意义是"外部编辑热发布、`update()` 热提交"，而本项目没有任何东西会在运行中改设置——设置页写的是数据库文档，作用于下一次运行。隔离层：`$DSH_HOME` 被 spawn 时注入为 `<run>/home`，挂了它就是每个子进程各监听一个永远不会出现的 `<run>/home/settings.yaml`，并发运行各开一个 chokidar watcher——与 `skill-filesystem` 关 `watch` 的理由相同（组 2）。安全层：它能把带 `role('secret')` 的分节字段写进磁盘文档——`web-search-deepseek` 分节的 `apiKey` 就是这样的字段——而本项目的凭据只以引用名进入组合、值只经环境白名单注入，永远不落文件（ADR-0006）。差异的结果：模型设置（凭据引用名、端点覆盖）由设置文档进入 `llm-deepseek` 行的 config，路径是 `readSettings()` → `runCompositionEntries()` → `cordis.yml`，没有第二个来源。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-agent-default-model`
- **seam 角色**：Service Definition 与实现同包（`ctx.agentDefaultModel`：进程级默认 `{provider, model}`，settings 分节可叠加用户选择）
- **决定**：不挂
- **它给会话带来什么**：间接。上游「模型体验」写"通过提供给入口的提供方／模型选择间接影响；模型可见请求由请求组装与适配器负责"。
- **理由**：它解决的问题是"多个入口（headless 的 runner、Web 的 ApiProxy）共用一个部署默认模型、并让 Models 页保存的选择覆盖它"。**上游 base 挂它**，值为 `provider: deepseek-official`、`model: deepseek-v4-flash`；`headless-runner` 注入它来创建那个唯一的 Agent。本项目没有"尚无会话级模型选择的 Agent"这种情况：每个 Action 的模型是它定义的一部分，在受理时随 `resolveWorkflow` 冻结，经 RPC 的 `agentOptions` 逐会话显式传入（`AgentOptions` 只有 provider/model/maxTokens，思考强度另经 waterfall 盖上，组 10）；`initialize` 里带的默认 provider/model 只是兜底，不是共享状态。上游 README 自己说"该服务只拥有一项进程级默认值；每个会话的选择仍由入口负责"——我们的入口就是 RPC，进程级默认无处可用。顺带记一个值的差异：我们的默认模型是 `deepseek-v4-flash-vision-exp`（`entries.ts`），比 base 的 `deepseek-v4-flash` 多了视觉模态，扫描件走逐页栅格化时必需；模型清单归 `models` 表与 `scripts/seed.ts`，不归这一行。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-cmdline`
- **seam 角色**：库（启动器在条目挂载前提供 `ctx.cmdlineArgs` 与 `ctx.appExit`；`parseCmdline` 是 commander 适配器）
- **决定**：不挂
- **它给会话带来什么**：无。上游「模型体验」写"本包在任何会话存在之前解析进程自身的命令行"。
- **理由**：它是 `dsh` 启动器与它引导的应用之间的交接协议：启动器只认 `--profile`、`--patch`、配置 dump，其后一切原样交给配置树，由应用自己的插件（`headless-startup`、`web-startup`）注入 `cmdlineArgs` 解析并发布服务，由 flag 配置的行再注入那个服务。本项目的子进程没有应用参数可解析：`runner.ts` 只取 `argv[2]` 作为运行目录内 `cordis.yml` 的路径，没有 flag、没有 `--help`、没有内置回退；一切本该经命令行进入的值（工作区、会话根、临时根、模型、开关）都已经被写进组合文件与环境白名单。`ctx.appExit` 的角色（"有边界的进程退出请求，接到启动器的关停控制器"）由 runner 自己承担。它不是 base 的组合行——base 里没有它，是启动器代码提供的值——所以参照会话里它存在但不是"行"。不挂它的直接后果是 `dsh-headless` 挂不上（本组上文）。
- **可按工作流切换**：否

### `@deepseek-ai/cordis-plugin-hmr`
- **seam 角色**：cordis 插件（提供 `hmr` 服务：监视源码与配置文件、追踪 Node 模块图、按需重载受影响的插件条目）
- **决定**：不挂
- **它给会话带来什么**：无。它监视文件、清模块缓存、重载条目，不触碰任何模型请求。
- **理由**：**上游 base 挂它**（`id: hmr`，`root: ['.']`），但 headless 与 web-app 两个 bundle 都把这一行 `disabled: true`（headless 的注释："共享的模块重载 HMR 行保持关闭"；web-app 的注释是 TODO，等它的重载生命周期测过再开）。启动器随后在没有 `hmr` 服务时挂一个 `root: []` 的**只监视配置**实例，用来让 `cordis.patch.yml` 的编辑在长驻表层上热生效（`watchUserPatches`）。参照会话因此有一个 hmr 服务，但它不重载模块、只看两个 patch 文件。我们连这个也不要：每次运行一个短命进程、组合在受理时冻结、没有 patch 文件（ADR-0007、ADR-0013），"热替换"没有对象；而 hmr 要求运行时暴露 Node 内部模块装载器、并依赖 `timer` 与 `loader`，每个并发运行各开一套 watcher 也与 `skill-filesystem` 关 `watch` 的理由相同。开发期改了 `src/server/harness/` 下的 TypeScript，下一次运行的子进程经 `node --import tsx` 加载的就是新代码；Next 自己的 HMR 只影响 Next 进程，炸不到在跑的运行（ADR-0007）。
- **可按工作流切换**：否

### `@deepseek-ai/cordis-plugin-logger-console`
- **seam 角色**：cordis 插件（内置 logger 服务的 console 导出器：把日志渲染到进程的 stdout）
- **决定**：不挂
- **它给会话带来什么**：无。日志导出器不进入模型请求。
- **理由**：这一行不挂不是"用不上"，是**挂了就坏**：本项目子进程的 stdout 是 `ontoflow-rpc` 的协议帧（`dsh-sdk-protocol` 的换行分隔 JSON-RPC），任何一行日志混进去都会让 Next 侧的传输解析失败。上游在同一问题上的立场与我们一致：`dsh-sdk-jsonrpc-demo` 的 README 写"stdout 只承载 JSON-RPC 帧……配置必须省略 stdout logger"，base、headless、web-app 三个 patch 都不挂它（它只出现在一个测试 fixture 里）；参照会话里也没有它。我们把这条规则钉在两处：`composition.ts` 的头注释，以及每份 `cordis.yml` 第一行的中文说明。不挂它的代价要说清楚。子进程 stderr 上只有直接写 stderr 的东西：`app-boot` 的 fail-loud 守卫（`ontoflow-harness: fatal load failure: …`）与 boot 阶段整棵树的加载失败诊断，父进程把它们追加到 `<run>/logs/harness.stderr.log`。经 `ctx.logger` 走的那些不在其中：`@deepseek-ai/cordis` 4.0.1 内置的 logger 服务在构造时只注册一个进程内的环形缓冲导出器（1000 条），`app-boot`、loader 与本项目的 runner 都不再注册任何导出器，于是上游插件用 `ctx.logger.warn` 报的告警——例如 `skill-filesystem` 对不合规技能名、缺 frontmatter 的技能文件打的那一行——留在缓冲里、随子进程消失，不出现在任何日志文件里。要看到这类告警，出路是在组 10 给子进程加一个只写 stderr 的导出器，而不是挂本行。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-cordis-host-runner`
- **seam 角色**：Service Provider（`ctx.dynamicCordisRunner`：模型定义的动态包在 host 侧的定义注册表、`node:vm` 沙箱、run 往返与浏览器广播）
- **决定**：不挂
- **它给会话带来什么**：无直接内容。上游「模型体验」写"本包不注册任何工具，也不注入提示词"，它的拒绝经调用它的 `cordis_*` 工具结果到达模型；但一个**运行中的** host 半可以注册工具、提示词段与监听器，从第一个变化的 schema token 起使前缀复用失效。
- **理由**：它是 `tool-cordis` 的运行时：模型 `cordis_define` 一个包、`cordis_run` 时 host 半在 vm 里求值、浏览器半投递给每个打开的页面。三条事实各自足以不挂。第一，**信任立场**：上游明说"vm 沙箱隔离全局变量，但不是安全边界……应当像对待 bash 访问一样对待动态包"，而它给动态包的是能触达 `ctx.fs`、`ctx.web`、`ctx.bash` 的 façade——等于让模型在运行中间给自己加能力。第二，**与运行快照冲突**：运行受理时 `resolveWorkflow` 冻结了 Action、Tool 与 Action→Tool 的所有权，Tool 是契约（ADR-0017），一个 Action 能看见哪些工具由 `tools.restrict` 在创建期钉死、`guard` 覆盖之后才注册的工具（组 10）——即便挂了它，模型动态注册的工具也会被 guard 拒绝，挂它只是造一个"定义成功、运行成功、调用被拒"的死胡同。第三，**无人值守挂死**：上游列为已知限制——带浏览器半的包"在没有页面连接的地方会挂起……headless 与 ACP 部署会把这次 run 一直挂到提问的轮次被取消"，且"挂起的 run 请求没有超时"；本项目的会话正是无人值守的，这种请求只会烧到节点的墙钟超时。上游自己也只在 web-app patch 里挂它，base 与 headless 没有，与参照会话零差异。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-cordis`
- **seam 角色**：Consumer（五个面向模型的工具：`cordis_inspect` / `cordis_define` / `cordis_run` / `cordis_stop` / `cordis_undefine`；注入 `tools`、`systemPrompt`、`dynamicCordisRunner` 与 `cordisInspect`）
- **决定**：不挂
- **它给会话带来什么**：可见时会话模型看到五个工具的 schema（每次请求固定 schema 成本），`cordis_inspect` 的报告与提交的包代码进入工具调用历史；`cordis_run` 之后运行中的包可以改后续请求的前缀。
- **理由**：随 `cordis-host-runner` 一起不挂——上游写明"只装这些工具而不装 runner 的组合永远不会激活它们"。上游 base、headless、web-app 三个 patch 都不挂它；它只出现在随发行版交付的 `cordis` agent preset 与几个 examples 里，参照会话里没有。除了 runner 一行已经说透的三条理由，还有一条只属于工具本身：`cordis_inspect` 是"当前进程运行时的只读报告"——服务、全部存活 fiber、已注册工具、动态包、反射支持的 API 参考——这是一份给正在开发 harness 自己的 agent 看的自省面，本项目的 Action 是业务任务，没有理由让它读到 `ontoflow-rpc` 与同进程里其它 Action 会话的内部结构。
- **可按工作流切换**：否
