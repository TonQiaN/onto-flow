# 05 委派与自编排

> 默认方向：不挂：编排归图。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这一组是上游里让模型**自己起 agent、自己写编排、自己开后台、自己设定时**的一切：subagent 家族（委派与继续执行）、workflow 与 ralph（模型写的编排脚本与固定的全新 agent 循环）、goal 三件套（同会话持久目标与 Goal Round 续行）、jobs 三件套（后台作业注册表）、schedule（会话内定时提醒）、实验性 Agent Teams。上游 headless 会话里这一组几乎全在：base 挂了 subagent 与两个进程内 provider、`subagent` / `subagent_fork` 两个委派工具、控制与上报工具、workflow 引擎与 `workflow` / `ralph` 工具、goal 与它的驱动器和工具、`jobs-local` 与 `job_*` 工具；组合行里不在 base 的只有 schedule（上游以可选 overlay 挂到 Web）与两个 experimental 包（`private: true`，不进发布 closure）。另外三行——`dsh-subagent-in-process-driver`、`dsh-workflow`、`dsh-jobs`——是库或 Service Definition，本来就不是组合行，由各自的 provider 带入。所以这一组与参照物的差别是最大的，理由必须写透。

判据只有一条：**编排只有一个来源——人画的工作流图**（ADR-0014）。扇出、汇总、回边都是图的形状（ADR-0009），每个 Action 是一次有界的前台会话：一条首消息、一个步数上限、一个墙钟、一次 `structured_output`、若干产物文件，然后会话关闭。这一组的每一行都让模型在会话里再开一条会话，或者把自己的会话拖过回合的边界，而本项目有四件事是靠「一个 Action 恰好一个会话」成立的，上游源码都能查实：一、工具收窄注册在 Action 会话自己的 scope 上（`tools.restrict` + `guard`，ADR-0015），而上游进程内子 agent「获得全新的扁平注册作用域：父级所有权不会导入父 agent 的工具限制，也不会建立权限子集」——评委 Action 起一个子 agent，子 agent 就看得见整条工作流的 Tool 并集与全局停用的工具；二、`node_usage` 以 `(runId, sessionId, messageId)` 唯一，会话 id 就是节点 id（重入轮次是 `节点id#N`），子会话是引擎不认识的新 id，它的 `session/event` 到达 Next 时找不到对应的事件槽，事件与用量整段丢弃，费用不归任何节点；三、轨迹面板按 `<nodeId>` / `<nodeId>#N` 枚举 `session.jsonl`，子会话在运行详情里不存在；四、`agent/pre-step` 步数守卫是会话 scope 上的监听器，子 agent 没有上限，上游 agent-loop 本身也没有。第五件事是词汇：上游的 `workflow` 是模型写的脚本、Goal Round 与 Ralph Round 是同一会话内的续行周期，与本项目的「工作流」「轮次」同名异义（CONTEXT.md 已把三者列为避免词），两套并存会让「运行为什么这样跑」没有单一答案。

结论：本组二十行一律不挂，没有一行可按工作流切换。它们在组合里留下的痕迹只有三处：`dsh-tool-bash` 的 `enableRunInBackground=false`（组 2，把 `run_in_background` 从 schema 整个移除，因为没有 jobs 它注定报错）；`package.json` 里的 `@deepseek-ai/dsh-jobs`（`tool-bash` 的 peerDependency，只被 `import type` 用来声明 `ctx.jobs` 的类型，没有 provider 就没有 `ctx.jobs`，不是挂载）；以及组 10 的结构化输出运行时——它 fork 自本组 `subagent-in-process-driver` 的 `structured.ts`。代价按 ADR-0014 记：一个 Action 内部没有并行，也没有后台作业——「并行读三十页」表达为图上的扇出，长命令靠 `bash` 的 120 秒超时与拆节点。

## 逐行

### `@deepseek-ai/dsh-subagent`
- **seam 角色**：Service Definition（`ctx.subagents`：provider 注册表、一次性 `start` 与可继续 `startContinuable` / `followup` / `interrupt` / `reportFrom`、持久描述符事件 `subagent/descriptor`、继续执行管理器与结算通知）
- **决定**：不挂
- **它给会话带来什么**：本身不给模型工具。它面向父级的唯一直接贡献是结算通知——子 agent 结束时父级收到一条用户角色消息 `Background subagent <child-id> finished and will do no further work unless you send it more.` 加子级的收尾内容；每个进程内子 agent 的运行时上下文另带一条 `subagent:delegation` 声明，告诉它权限范围已在启动时固定。
- **理由**：这是整个家族的根，四条查实的理由都落在它身上。第一，收窄失效的机制在上游 README 里写得很直白：进程内子 agent 经 `applyChildComposition` 「先加入父级的 agent-preset 组合，再应用子 agent 自己的 persona 和工具限制」，而「未组装 preset roster 的部署不加入任何组合、也不需要加入；其面向模型的行位于宿主组合中，子 agent 已能通过工具注册表的全局层解析到它们」——本项目正是没有 preset 的部署（ADR-0015），宿主组合的全局层就是整条工作流的 Tool 并集加全部内建工具，Action 的 `restrict` + `guard` 只活在自己的会话 scope 里，子 agent 一个也继承不到；`tool-subagent` 的 `toolFilter` 是部署配置，上游明言「不是从父级派生的权限上限」。第二，计费：子会话是新的 session id，本站的用量归属只认节点 id，子 agent 花的每一分钱都不归节点，也不进运行事件。第三，轨迹与步数：运行详情按节点 id 找会话文件，子会话看不见；步数守卫在父会话 scope 上，子 agent 的循环只受墙钟约束。第四，它不是孤立的一行：它的可选 peer 有 `agent-presets`、`session-persistence`、`session-projection`、`session-projection-cache`、`jobs`、`sandbox`、`sandbox-policy`、`user-approval`——挂不挂由组合决定，但少了就少一截功能：投影与缓存在组 4 不挂，而 `listChildren()` 「要求已挂载 `sessionProjections` 注册表」，没有它就响亮失败；一次性后台委派要 `jobs`，本组不挂。挂 subagent 意味着把组 4 的两行与本组的 jobs 三件套一起拖进来。上游给子 agent 的委派策略（沙箱覆盖快照、审批钉 `never`）倒不是问题——本项目的审批本来就是 `never`——说明拒绝它的理由不在安全，在归属：本项目要的「子 agent」是画布上的下游 Action，有自己的会话、计费、轨迹、步数上限与收窄，而且人在编辑期就看得见它。
- **上游 base**：挂（`id: subagent`，无 config）；headless 不改。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-subagent-spawn-in-process`
- **seam 角色**：Service Provider（`spawn`：在当前进程创建一个全新的子 Agent，空对话开始）
- **决定**：不挂
- **它给会话带来什么**：子 agent 逐字收到独立任务、默认继承父级的模型与工作区、看不到父级任何对话消息；父级经 `dsh-tool-subagent` 只收到子 agent 的最终输出或结束原因。
- **理由**：随 subagent 一起不挂。值得单独记一笔的是 spawn 的形状——空对话、经工作区交流、只把最终结果交回——正是本项目「下游 Action」的形状，差别只在谁决定、何时决定：spawn 由模型在运行时决定，图由人在编辑期决定。同一个形状本项目要它出现在画布上而不是会话里。它声明的四项能力 `{ outputSchema, depthLimit, toolFilter, persona }` 里，`outputSchema` 的实现就是组 10 结构化输出运行时的原型（见 `subagent-in-process-driver`）。
- **上游 base**：挂（`providerName: spawn`）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-subagent-fork-in-process`
- **seam 角色**：Service Provider（`fork`：以父级已完成轮次的连续前缀为种子创建进程内子 Agent）
- **决定**：不挂
- **它给会话带来什么**：子 agent 先看到父级截至最后一个 `turn/end` 的已配平历史，再看到新任务；父级进行中的轮次被排除；提供方与模型相同时子 agent 可复用继承前缀的 KV Cache。
- **理由**：随 subagent 一起不挂，另有一条只属于它的理由：fork 是「把上下文经会话历史复制给另一个 agent」，与双通道结果直接相悖——本项目的上下文面在工作区文件里，下游按需读文件，实质内容不沿连线复制进下游提示（ADR-0008），循环的每一轮也是全新会话、经文件传递而不靠会话记忆（ADR-0009）。上游自己也把 fork 钉在 `one-shot`，理由是可继续子级的 `report` 工具与提示段会插在继承历史之前、让继承整体失效。README 明言「初始内容只传递对话历史。子 agent 仍会获得全新的扁平注册作用域；它不继承父 agent 的工具限制或权限」——收窄失效的问题在 fork 上一样成立。
- **上游 base**：挂（`providerName: fork`）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-subagent-in-process-driver`
- **seam 角色**：库（spawn 与 fork 共用的运行驱动器，无 ctx 键；导出 `startInProcessRun` 与 `attachStructuredRuntime`）
- **决定**：不挂
- **它给会话带来什么**：不直接。经两个 provider 给子 agent 装深度检查、persona、工具限制与结构化输出运行时——`structured_output` 工具、一段 order 190 的系统提示、`tools/result` 观察器只在权威最终结果成功后提交暂存值、单调守卫阻止二次调用、`concludeTurn()` 结束轮次；「正常结束却始终未提交必需结构化值的轮次会报告 `error`；驱动器不会重新提示」。
- **理由**：不作为运行时依赖——它的 peer 链要 `dsh-subagent`，进而要 `agent-presets`、`session-projection`、`jobs`、`sandbox` 等本项目不挂的能力，而它对本项目有用的只有 `src/structured.ts` 一个文件：那正是数据面（ADR-0008）需要的全部机制，会话 scope 内用真实 schema 注册的一次性工具、终态守卫、以 `tools/result` 为准的两阶段提交，连「不提交结构化值就是失败、不重新提示」这条纪律也一致。本项目把这个函数抄过来、去掉 subagent 依赖、在会话创建窗口内调用（ADR-0015），记为组 10 的 fork 行 `src/server/harness/rpc/structured.ts`，上游文件 `packages/subagent/subagent-in-process-driver/src/structured.ts`。所以这一行是本组唯一「不挂但被 fork」的行；上游那个文件一变，组 10 的 fork 记录就要重审。
- **上游 base**：不是组合行（两个 provider 的内部依赖）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-subagent`
- **seam 角色**：Consumer（面向模型的委派工具；每个实例把一个 provider 绑到一个 `toolName`）
- **决定**：不挂
- **它给会话带来什么**：`subagent` / `subagent_fork` 的 schema，加一段 `tool:<toolName>` 系统提示段，指示模型「同时启动相互独立的可继续委派、在它们运行时继续工作，并且仅当下一步动作依赖结果时选择前台」。前台成功只返回子 agent 的最终文本；可继续模式启动时返回 `started subagent <childId>`，结果永不经本工具返回。
- **理由**：这是模型看得见的入口——schema 与提示段一起消失，模型连「我可以委派」这个念头都不会有。上游默认的 `continuable` 模式与 Action 的「有界前台任务」正面冲突：可继续子 agent 在 inbox 接受时就结算，父轮次不等它；Action 交出 `structured_output` 后会话即关闭，运行结束子进程 dispose，孤儿子 agent 随进程终止，它做的事既没进产物也没进账。一次性后台路径则要注册一个 Task，依赖本组同样不挂的 jobs。`maxDepth` 默认 3 且「工具在达到上限时仍然可见」，只是每次启动都被拒——限制深度并不能把它变成一个安全的挂载。本项目要并行就画扇出，要评审就画回边。
- **上游 base**：两行——`tool-subagent`（`provider: spawn`、`toolName: subagent`、`backgroundMode: continuable`）与 `tool-subagent-fork`（`provider: fork`、`toolName: subagent_fork`、`backgroundMode: one-shot`）；schema 默认 `enableRunInBackground: true`、`maxDepth: 3`。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-subagent-control`
- **seam 角色**：Consumer（全局 `send_message` 与 `interrupt_agent`；可单独加载的 `./list-agents` 子插件注册 `list_agents`）
- **决定**：不挂
- **它给会话带来什么**：父到子的后续消息成为子 agent 的下一个 FIFO 轮次、本次调用不返回回复；中断只停当前轮次、已排队消息保留；`list_agents` 按目录列出可继续 child（`running` / `idle` / `ready`），一次性 child 有意排除。
- **理由**：随 subagent 一起不挂。单独记两点：`list_agents` 「其目录读取在调用时还要求会话存储与投影注册表」，`dsh-session-projection` 在组 4 不挂，所以即便挂了 subagent，这个工具也会以 `SUBAGENT_CONTROL_PROJECTIONS_UNAVAILABLE` 响亮失败；另外它的三个工具名与 `experimental-tool-agent-team` 的 scoped 定义同名，上游要求同时挂载时禁用这一方——这种同名覆盖是显式清单（ADR-0013）要避开的隐式行为。
- **上游 base**：两行——`tool-subagent-control` 与 `tool-subagent-list-agents`（`@deepseek-ai/dsh-tool-subagent-control/list-agents`），均无 config。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-subagent-report`
- **seam 角色**：Consumer（子级作用域的 `report` 工具与 `tool:report` 提示段；以可继续子级设置贡献注册，不是全局工具）
- **决定**：不挂
- **它给会话带来什么**：只存在于可继续子 agent 内部：子级在结束前调用一次 `report` 给出自足答案，父级收到以 `Background subagent <child-id> reported:` 开头的用户角色消息。根 agent、一次性子 agent 与远程子 agent 都看不到它。
- **理由**：随 subagent 一起不挂。它与本项目的对照值得记下：上游子到父的返回通道是一条消息进父级历史，「本包不设上限」；本项目 Action 之间的返回通道是产物文件加数据面（ADR-0008），下游读文件而不是读消息，实质内容从不进提示。它还「有意不受子级全局 `toolFilter` 影响，因此委派允许列表无法移除唯一的返回通道」——一个收窄拿不掉的工具，恰是「Action 只收窄、从不扩张」的模型不接受的东西。
- **上游 base**：挂，无 config（`reportDelivery` 默认 `next-step`）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-workflow`
- **seam 角色**：Service Definition（`ctx.workflowEngine`：脚本、运行、结果、错误与 `workflow/*` 事件契约）
- **决定**：不挂
- **它给会话带来什么**：不直接；经 `dsh-tool-workflow` 与引擎间接——脚本里的每次 `agent()` 都是一个子 agent 请求，父级只收到最终 JSON 值。
- **理由**：词汇冲突是根本。上游的 workflow 是「由模型编写、可扇出 subagent 的编排脚本」：JavaScript 正文加 `agent()` / `parallel()` / `pipeline()` / `phase()` / `log()` 钩子，运行时才存在；本项目的工作流是人画的图，编辑期就固定，CONTEXT.md 已把「上游 dsh 的 workflow 工具」列为工作流一词的避免词。两套并存时「运行为什么这样跑」没有单一答案（ADR-0014 第四条）：图上看不见脚本里的扇出，运行详情、计费、轨迹也看不见——脚本里的每个 `agent()` 都走 `ctx.subagents`，落进本组第一行的全部问题。上游 README 自己列的限制——「仅支持前台收集」「没有日志化或恢复」「没有 token 预算词汇」「运行由持有方负责，不由服务跟踪」——恰好是图已经给每个节点提供的东西：会话记录、轮次、用量、终态。
- **上游 base**：不是组合行（Service Definition 由 provider 带入）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-workflow-worker-thread`
- **seam 角色**：Service Provider（每次运行一个 Node worker thread 执行脚本；子 agent 留在宿主，经带类型的宿主／worker 协议访问 `ctx.subagents`）
- **决定**：不挂
- **它给会话带来什么**：脚本每次 `agent()` 把提示词原样发给 subagent provider，可选模型与结构化输出 schema；phase 与 log 只进观察器事件；父级不直接增加 token。
- **理由**：随 workflow 一起不挂。上游明言「worker 内的 `node:vm` 是塑造 API 的机制，不是安全边界」「它不是安全沙箱」，脚本的信任前提「与模型已有的 bash 访问相同」——这一点对本项目无所谓，bash 本就不受限于网络与读（ADR-0011）；拒绝它的理由仍是归属而不是安全。它的并发与总量上限（`maxConcurrentAgents` 按 CPU 并行度、`maxTotalAgents` 1000）在本项目对应的是图的扇出宽度与运行级的 `MAX_CONCURRENT_RUNS`，不需要脚本级的第二套预算。
- **上游 base**：挂（`provider: spawn`）；schema 默认 `maxConcurrentAgents: 0`（按可用 CPU 并行度解析）、`maxTotalAgents: 1000`、`maxItemsPerCall: 4096`、`syncTimeoutMs: 5000`、`disposeGraceMs: 5000`。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-workflow`
- **seam 角色**：Consumer（`workflow` 工具与 `tool:workflow` 提示段）
- **决定**：不挂
- **它给会话带来什么**：三个参数 `meta` / `script` / `args`，schema「较大的固定 token 开销」；提示段规定「只有用户明确要求工作流／大型编排时才使用该工具；一两项委派优先使用普通 subagent 调用」；成功返回 `workflow "<name>" completed (<count> agents).` 加脚本的最终 JSON；父级轮次阻塞到整个工作流结算。
- **理由**：随 workflow 一起不挂。上游的提示段已经把它限定为「用户明确要求」——运行中没有人提这种要求，Action 的 prompt 是工作流作者写的，作者要扇出就画在图上；剩下的只是每个请求白付的大段 schema。「取消会丢弃局部输出并返回错误」——在本项目里等于一个节点的全部子工作既不进产物也不进账。
- **上游 base**：挂，无 config（`toolName: workflow`、`maxResultChars: 50000`）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-ralph`
- **seam 角色**：Consumer（`ralph` 工具：基于 `ctx.workflowEngine` 与 `ctx.subagents` 的固定前台工作流，把一个不可变目标依次交给多个全新子 agent）
- **决定**：不挂
- **它给会话带来什么**：`ralph({ objective, maxRounds? })`，等待整个运行完成；每个 Ralph Round 一个全新子 agent，只收到目标、当前 Round 与上限、「共享工作区是权威状态」的指令和上一份有界结构化交接；提示段规定只在直接的人类明确要求 Ralph loop 或全新 agent 迭代执行时才用；父级只看到终态结果与 Round 数。
- **理由**：这是本组与本项目最像的一行，也因此最要写清。Ralph Round = 全新子会话 + 工作区为长期记忆 + 有界结构化交接——与本项目的循环「每一轮全新会话、上一轮的产物与评审意见经工作区文件传给下一轮」（ADR-0009）几乎同构。差别在谁决定与谁看得见：Ralph 由模型在一次工具调用里决定轮数，「完成由 worker 自行声明：没有独立的评估器或验证器判断目标是否实际完成」，中间 Round 在父级看不见；图上的循环由人画出回边、由被回流的 Action 声明重入上限与耗尽时的收束方式，判定由出口端口承担——review-fix 的两端是两个 Action，评审那一端是独立会话、独立计费、独立可查。同构的能力本项目在图层面已经有，而且有评委，不需要会话里再来一套；CONTEXT.md 已把 Ralph Round 列为「轮次」的避免词。它还要求 provider 「支持结构化输出，并报告 `inheritsParentContext: false`」，也就是依赖 spawn。
- **上游 base**：挂（`subagentProvider: spawn`、`maxRounds: 64`——schema 默认 256，base 收紧到 64）；`maxHandoffChars` 与 `maxResultChars` 默认 16384。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-goal`
- **seam 角色**：Service Definition（`ctx.goals`：事件溯源的同会话目标状态，`goal/change` 事件带完整快照；续行启用是进程本地、从不持久化的权限）
- **决定**：不挂
- **它给会话带来什么**：「Goal 变更不会注入模型上下文」；模型经 `tool-goal` 读写，驱动器在调度时渲染目标与 Round 状态。
- **理由**：goal 假设一条长命、可 resume / fork 的会话：一个目标在同一会话里跨多个 Goal Round 推进，「续行启用状态绝不持久化。新缓存与每次触发 `agent/session-start` 时都停用续行……之后必须通过显式 resume 变更重新启用」，而那个 resume 上游要求「人类直接发起的顶层轮次」授权。本项目的会话在 Action 交出结果后即关闭，运行里没有人，goal 没有存活空间。第二，Goal Round 与本项目的轮次是两套循环词汇（CONTEXT.md 避免词）：Goal Round 是同一会话内的续行周期，历史随 Round 累积直到压缩；本项目的轮次是全新会话，这正是 ADR-0009 为了不让上下文随轮数膨胀而做的选择。第三，「只有 Round 数量预算」「没有独立评估器：记录完成或阻塞的调用方拥有最终决定权」——图上的评审 Action 就是评估器。轨迹投影已把 `goal/change` 列入审阅过的忽略事件。
- **上游 base**：挂，无 config（`defaultMaxGoalRounds` 默认 256）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-goal-round-driver`
- **seam 角色**：Consumer（agent seam 的同会话续行驱动器：把 phase 为 active 且已启用续行的目标变成连续的 Goal Round）
- **决定**：不挂
- **它给会话带来什么**：每个已准入 Round 是一段保留的用户角色 `<goal_round>` 块，点明完整目标与 `round/maxGoalRounds`，要求「在完成前提供证据」；不创建新 agent，不复制对话前缀。
- **理由**：随 goal 一起不挂。它的触发点是「对应的活跃 agent 实例处于 idle 状态」时排入下一 Round——而 Action 会话的 idle 就是回合结束、引擎读取结构化结果并关闭会话的时刻，驱动器若在同一个 idle 检查点排入 `<goal_round>`，就是与引擎抢同一条会话的下一步。上游也明言「只在同一会话执行：此包有意不 spawn 新 agent、不 fork 会话前缀，也不实现 Ralph 风格的独立尝试」，取消后会暂停 goal 并等待「用户授权 resume」——无人可授权。
- **上游 base**：挂，无 config（该插件没有可调配置）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-goal`
- **seam 角色**：Consumer（`get_goal` / `create_goal` / `update_goal` 与固定的 goal 策略提示段）
- **决定**：不挂
- **它给会话带来什么**：模型「可以推断长期运行的 goal 意图，而无需精确命令短语」创建目标；提示段说明何时创建、resume / fork 后如何 rearm、`complete` 只在目标实际达成、`blocked` 只在同一阻塞条件持续至少 3 个 Goal Round 之后。
- **理由**：随 goal 一起不挂。两点补充：`create_goal` / `edit` / `pause` / `resume` 要求当前轮次里有人类直接发出的消息或 steering 事件，「非人类轮次和 subagent 会在执行时被拒绝」，而「Goal Round 权限需要驱动器……只挂载这个包不会创建这些轮次」——它离开驱动器与人都不成立；提示段「注册与过滤相互独立：某个范围可能隐藏工具，却保留指引」，挂了再用收窄藏起来仍会每请求白付提示 token，所以只有不挂这一种干净的选择。
- **上游 base**：挂，无 config（`blockedAfterConsecutiveRounds` 默认 3）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-jobs`
- **seam 角色**：Service Definition（`ctx.jobs` 后台任务注册表约定：owner 隔离、`start` / `read` / `kill` / `wait`、完成通知；生产方经 `JobKindMap` 扩展 kind）
- **决定**：不挂
- **它给会话带来什么**：不直接。生产方是 `tool-bash` 的 `run_in_background`、`tool-subagent` 的一次性后台委派与 `tool-terminal`；模型经 `tool-jobs` 看见 job id、输出、状态与完成通知。
- **理由**：Action 是有界前台任务，后台作业只会让模型用步数轮询（ADR-0014 的代价段）。机制上：作业属于 owner Agent 的 scope，「所有者的 dispose 会取消该对象的任务，等待生产方完全停稳，并移除其快照」——Action 会话关闭时未收集的作业随之取消；完成通知要么唤醒一轮（一次用户没要求的模型请求）要么注入 inbox，模型再花步数 `job_output` 去收；步数上限是 Action 唯一的循环预算，花在等命令上没有意义。长命令的正确形态是 `bash` 的 120 秒超时加拆节点（组 2）。两个痕迹：`@deepseek-ai/dsh-jobs` 出现在 `package.json` 只因 `tool-bash` 把它列为 peerDependency——`tool-bash` 只 `import type` 它来声明 `ctx.jobs`，没有 provider 注册就没有 `ctx.jobs`，这不是挂载；而没有 `ctx.jobs` 时 `run_in_background` 调用会以 `background jobs unavailable` 报错，所以 `tool-bash` 配置 `enableRunInBackground=false`，把 `run_in_background` 从 schema 整个移除、工具描述改为「后台执行不可用」，模型不会走进那条报错分支。
- **上游 base**：不是组合行（`jobs-local` 注册 `ctx.jobs`）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-jobs-local`
- **seam 角色**：Service Provider（进程本地 `LocalJobRegistry`：内存记录、按 kind 签发 `<kind>-N` id、只交出快照）
- **决定**：不挂
- **它给会话带来什么**：不直接；经生产方与 `tool-jobs` 间接。
- **理由**：随 jobs 一起不挂。「任务只存在于进程本地：记录会随 harness 进程终止而消失」——每次运行一个短命子进程（ADR-0007），后台作业的寿命上限就是这个进程，而进程在运行收束时 dispose。「组合中未加载 `tool-jobs` 的 agent 根本无法启动后台工作」：注册表与控制器缺一个都不成立，所以这三行只能一起挂或一起不挂。
- **上游 base**：挂（`id: jobs`，无 config；`maxConcurrentJobsPerOwner` 默认 10）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-jobs`
- **seam 角色**：Consumer（`job_output` / `job_list` / `job_kill`、完成通知、后台工作提示段；同时是 `ctx.jobs.start()` 所要求的任务控制器）
- **决定**：不挂
- **它给会话带来什么**：提示段「Track every background job id you start… do not busy-poll or sleep on one」；完成通知 `background job <id> (<kind>: <label>) finished [status: ...]. Read its output with job_output.`，默认 `wakeup` 模式下空闲 owner 被唤醒开一轮，每个 owner 最多连续唤醒 3 轮。
- **理由**：随 jobs 一起不挂。它决定了 `run_in_background` 能不能用——控制器不在，`start()` 在生产方执行前就拒绝——这正是 `tool-bash` 关掉该参数的直接原因。唤醒预算暴露了无人值守的坑：「已花掉的唤醒预算不会随时间恢复：只有用户撰写的输入才能补充，因此预算耗尽的无人值守 agent 要等到其他原因开启下一轮时才收走剩余通知」，而 Action 的会话没有下一轮。
- **上游 base**：挂，无 config（`waitTimeoutMs` 30000、`maxWaitTimeoutMs` 600000、`completionDelivery: wakeup`、`maxConsecutiveWakes` 3）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-schedule`
- **seam 角色**：Consumer（单包：版本化 `schedule/change` 事件与折叠、`schedule_create` / `schedule_list` / `schedule_delete` 工具、live 根 agent 的 timer owner；有意不公开服务）
- **决定**：不挂
- **它给会话带来什么**：三个工具只装到插件加载后创建的 live 根 agent；到期提醒以 `[SCHEDULE REMINDER]` 用户角色 framing 排成一个普通的后续轮次，「绝不会中途引导或中断当前对话」。版本 1 接受 `after_seconds`、绝对时间 `at`、至少 5 分钟的 `every_seconds`。
- **理由**：调度归外部调用方。一次运行从受理到收束是连续执行，节点靠上游产物就绪触发，不靠时钟，运行本身没有「等到某个时刻」的语义；提醒「只有在原会话 live 时才能准时运行；cold 会话不会收到外部通知」，而 Action 会话在回合结束后关闭、子进程随运行 dispose，`after_seconds` 之后没有会话接收那条 follow-up；`every_seconds` 最短 5 分钟，比多数 Action 的整个寿命还长。要按时刻跑工作流，是发起运行的人或程序的事——`startRun` 只是受理门，队列与定时归外部调用方。
- **上游 base**：不挂；上游只在 `examples/web-schedule/cordis.yml` 作为可选 overlay 与 `time-context` 一起插入 Web 组合，headless 没有。
- **可按工作流切换**：否
