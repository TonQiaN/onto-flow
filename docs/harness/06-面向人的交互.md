# 06 面向人的交互

> 默认方向：不挂：运行中没有人。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

上游把「模型停下来等一个人」与「人绕过模型直接操作会话」两类能力都做成了 seam 与插件：向人提问（`user-questions` 与它的工具）、等人评审计划（`plan-mode`）、人在会话中途切换权限档位（`permission-presets`）、人敲斜杠命令（`commands` 与三条 `command-*`）、给人看列表用的会话标题（`session-title` 家族）、与人对话取得凭据（`authorization`），外加一个上游自带的展示用技能（`skill-badge`）。这组的判据只有一条：一行的价值要成立，必须有一个人在**运行期间**坐在界面前——回答、批准、敲命令、看标题。

本项目的运行是无人值守的。人只在事前（编辑工作流、Action、设置）与事后（看运行详情、Agent 轨迹、产物）出现；运行期间人唯一能做的是中止（已取消终态），没有任何通道把模型的问题送到人面前，也没有通道把回答送回会话——宿主是 Next 进程，`ontoflow-rpc` 的协议里没有「问人」与「命令」这两种帧（ADR-0007）。缺信息、要判定、要分阶段，这些在本项目都有图上的表达：输入节点把人给的东西物化成文件（ADR-0012），出口端口与回边承担判定与循环（ADR-0009），评审由下游 Action 或运行结束后的人做。

与 headless 基线的关系值得说清：上游 headless 会话本身也是无人值守的——把任务当一条用户消息提交后就等 agent 停稳；headless 不提供命令适配器，也不注册 `user-questions` 的提供方（上游唯一的提供方在 Web 宿主 `dsh-host-apiproxy` 里）。所以 base 里这组的行在 headless 会话里大多处于「挂着但没人用」的状态：命令注册表没有入口，`/feedback` `/goal` `/compact` 无处可敲，`ask()` 没有提供方。会到达模型的差别只有两处：`plan-mode` 让 `exit_plan_mode` 常驻工具清单，`session-title-first-prompt-llm` 让每个会话多发一次付费辅助请求。整组不挂之后，本项目的会话比基线少一个永远调用失败的工具、少一笔标题费用，其余行对模型体验没有任何差别。十四行全部不挂，没有一行可按工作流切换；「人」的角色由本项目自己的界面在运行前后承担。

## 逐行

### `@deepseek-ai/dsh-user-questions`
- **seam 角色**：Service Definition（`ctx.userQuestions`）
- **决定**：不挂
- **它给会话带来什么**：自身不改变请求前缀；间接地经 `tool-ask-user`，把提供方给出的人类回答以紧凑 JSON 交回模型，等待人回答期间不消耗 token。
- **理由**：上游 base 挂它（无配置），但 seam 的提供方只有 Web 宿主注册，headless 里 seam 挂着而没有提供方，`ask()` 立即抛 `NO_PROVIDER`、不降级。对本项目，两条路径都走不通。其一，只挂 seam 不挂提供方：唯一的消费方 `tool-ask-user` 一旦挂上就会激活，给模型一个每次都以「no user-questions provider is registered」失败的工具——多一份固定 schema token，还让模型在拿不到信息时走进一个注定失败的分支，白白消耗步数守卫的配额。其二，由 `ontoflow-rpc` 注册一个桥到 Next 侧的提供方：运行期间没有人，回答不会来；上游明言该工具不声明 `timeout-policy` 预算、取消只随本轮的 `exec.signal`，于是会话会一直挂到节点墙钟超时才失败，前面的用量已经花出去——这就是目录一句话里「挂死到墙钟超时」指的情形。更根本的是，「问人」在本项目是图的事而不是会话的事：Action 缺的信息由上游产物或输入节点提供，拿不到就按自己的规则收束到某个出口端口，让下游或运行结束后的人处理；把提问塞进会话等于给图加了一条看不见的、不受轮次与出口约束的边。上游另有「只有运行时根 agent 能提问」的限制，本项目不挂 subagent（ADR-0014），此限制无关。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-ask-user`
- **seam 角色**：Consumer（注入 `tools`、`userQuestions`）
- **决定**：不挂
- **它给会话带来什么**：`ask_user_question` 工具——模型给出一组带稳定 id 的问题（可带选项、多选、标题），拿回 `{ "answers": [{ "id", "selected", "custom"? }] }`；工具可见时每次请求都多一份固定 schema token，等待人回答不增加 token。
- **理由**：随 `user-questions` 一起不挂；它注入 `userQuestions`，seam 缺席时根本不会激活。值得单独记的是上游的挂载位置：它不在 base，而在随 CLI 发布、由 Web 组合的 agent preset（`standard` / `code` / `cordis` 三份 `agent.cordis.yml`；`minimal` 没有）与 ACP 示例里；headless 不组合 preset roster——也就是说上游 headless 会话本来就看不到这个工具，我们不挂与基线一致，不需要额外理由。「把推荐项放首位并加 `(Recommended)`」是写进工具 schema 给模型的约定，「`header` 短标题」是给渲染器的；没有渲染器，两者都没有意义。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-plan-mode`
- **seam 角色**：Consumer（注入 `tools`、`systemPrompt`；执行期机会性地取 `userQuestions`，组合了 `commands` 时另注册 `/plan`）
- **决定**：不挂
- **它给会话带来什么**：激活时在提示词顺序 50 处注入部署方配置的 `section` 原文；无论是否激活，`exit_plan_mode` 都常驻工具清单以保持 schema 稳定；plan mode 内调用它会经 `userQuestions` 把计划交人评审，批准返回 `{ approved: true }`，拒绝是带评审反馈的失败调用，放弃审阅也是一次失败调用。
- **理由**：进入 plan mode 只有两条路——人敲 `/plan`，或界面调 `ctx.planMode.set()`；退出只有人评审批准或 `/plan off`。没有人就没有进入，更没有退出。上游 base 挂它、headless 不禁用，所以 headless 会话确实看得到 `exit_plan_mode`，而在未激活状态调用它必定失败：挂了它，本项目得到的只是这一个死工具与它每步的 schema token；不挂，工具清单比基线干净一个。上游自己声明 plan mode「只引导不强制」，「先探索再动手、不许写文件」这类约束在本项目有更硬的表达——沙箱策略与审批策略是强制的（ADR-0011）；「先规划再实施」则是图上的两个 Action，中间隔着出口端口与回边（ADR-0009），评审由下游 Action 或运行结束后的人做，不需要会话内的软状态。base 的 `section` 是一段长英文规划指令，上游要求非空，但内容是部署选择，本项目没有对应物。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-permission-presets`
- **seam 角色**：Consumer（注入 `shell`、`approval`、`sessions`）兼面向人的服务 `ctx.permissionPresets`；组合了 `commands` / `sessionProjections` 时另注册 `/permissionPresets` 命令与 `permissions` 投影
- **决定**：不挂
- **它给会话带来什么**：不直接改变模型请求；它切换的 `sandbox/mode` 与 `approval/policy` 经 `dsh-user-approval` 与 `dsh-tool-bash` 的提示词、切换通知与工具结果到达模型，`permissionPresets/preset` 事件本身只写日志。
- **理由**：它解决的问题是「一个坐在界面前的人在会话中途把权限从 workspace-write 切到 danger-full-access」。本项目的沙箱姿态是组合里钉死的全局决定：`sandbox-policy` 固定 `workspace-write`，`approval` 固定 `never`（ADR-0011），受理时随运行快照冻结，Action 从不开关插件（ADR-0015、ADR-0016），运行期间也没有人去切。上游 base 的预设表是 `read-only`（read-only + ask）、`workspace-write`（workspace-write + ask）、`danger-full-access`（danger-full-access + never），默认档由组合的沙箱与审批默认值推断。本项目的组合是 workspace-write + never，这对取值不在表里：按上游源码，组合默认匹配不到任何预设又没有显式 `defaultPreset` 时，插件在加载期直接抛错——原样挂上会把整棵树拖垮，要挂就得先改它的表。这从反面说明它与本项目不兼容：我们要的恰恰是它的表里没有的那一对。它还拥有 `permissionPresets` 设置命名空间、依赖上游的设置文档，而本项目的设置是 Next 侧的单行 JSON（组 7）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-commands`
- **seam 角色**：Service Definition（`ctx.commands`，面向交互式 UI 适配器的命令注册表）
- **决定**：不挂
- **它给会话带来什么**：无。命令的发现、执行与直接输出都在 UI 命令平面，`CommandResult` 从不作为用户消息提交；只有命令生产方显式经 `Agent` 安排的工作（例如 `/plan <message>` 的 steer）才会成为模型可见的消息。
- **理由**：注册表需要一个适配器把人的输入分发进来，上游只有 Web 客户端有适配器——headless、ACP、JSON-RPC 都没有；base 虽挂它，headless 会话里它是一个没有入口的注册表。本项目的入口是 `ontoflow-rpc`，协议里没有命令帧，挂它不会产生任何行为差别。唯一可能让人误以为需要它的场景是技能预载（ADR-0016）：预载「等同于人在命令行里敲 `/技能名`」。但上游的 `/name` 手势不是 `ctx.commands` 的命令——它由 `tool-skill` 扫描已认领的用户消息、经 `renderSkillContent()` 以 `skill-invocation` 来源注入 `<skill_content>`。引擎把 `/slug` 写进会话的用户消息即可，不经命令平面；这就是目录一句话里「由引擎代敲」的含义（预载的实现在第二批）。挂了它，`plan-mode`、`permission-presets` 会顺带注册 `/plan`、`/permissionPresets`，而这些生产方都不挂，注册表也就空着。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-command-feedback`、`@deepseek-ai/dsh-command-goal`、`@deepseek-ai/dsh-command-compact`
- **seam 角色**：三者都是 Consumer（注入 `commands` 与各自的领域服务：无 / `goals` / `compaction`）
- **决定**：不挂（三行）
- **它给会话带来什么**：无——三条命令的斜杠输入与直接输出都不进模型请求。`/compact` 被受理后会以独立的 `compaction/*` 标记对替换一段较早历史；`/goal` 带图片创建或编辑目标时会追加一条普通用户消息。
- **理由**：共同的一条是随 `commands` 不挂——没有适配器它们连被人调用的入口都没有；上游自己也写明这三条命令在 headless、ACP、JSON-RPC 里不可用，所以不挂与基线一致。各自还有一条：
  - `command-feedback`：`/feedback <text>` 把自由文本追加为 `feedback/record`，确认文本会点名匿名用户 id（首次可能在 `$DSH_HOME` 下创建 `.anonymous-user-id`）并披露会话共享策略（经 `ctx.get` 读遥测服务）。它是遥测的反馈门：上游 `feedback-only` 模式下记录反馈会释放会话前缀用于上传。本项目运行内容不出本机（组 8），反馈的去处是本项目自己的界面。
  - `command-goal`：`/goal` 是 `dsh-goal` 的人工控制面（创建、编辑、暂停、恢复、清除目标）。goal 三件套不挂（组 5，ADR-0014）：本项目的循环是图上的轮次，不是同会话内的 Goal Round，人也不在会话里 resume。
  - `command-compact`：`/compact` 让人在未到自动阈值时手动摘要一次。自动压缩 `compaction-basic` 已挂（组 3）、按阈值自动触发；手动触发无人可按。它注入 `compaction`、只依赖其 `compactNow`，与后端无关，挂不挂都不影响自动压缩。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session-title`、`@deepseek-ai/dsh-session-title-first-prompt-llm`、`@deepseek-ai/dsh-session-title-all-prompts-llm`、`@deepseek-ai/dsh-session-title-llm`
- **seam 角色**：`session-title` 是 Service Definition（`ctx.sessionTitle`）兼确定性回退；`first-prompt-llm` 与 `all-prompts-llm` 是 Service Provider（注册表最多接受一个，二选一）；`session-title-llm` 是两个提供方共用的库，不是插件。
- **决定**：不挂（四行）
- **它给会话带来什么**：主请求无——`session/title` 只写日志，不进会话接口、系统提示词、工具 schema 或请求前缀。模型提供方另发一次独立的辅助请求：固定的标题指令加一个装着用户消息的 JSON 数组，DeepSeek 适配器对这个 purpose 关闭思考。
- **理由**：标题是给人看会话列表用的。本项目的会话 id 就是节点 id（重入时是 `nodeId#N`），运行详情与 Agent 轨迹按节点名与轮次列，没有「一堆无名会话要靠标题分辨」的问题。上游 base 挂 `session-title`（`fallbackMaxWords` 5、`fallbackMaxBytes` 40、`maxTitleBytes` 80，三项必填、库无默认）与 `first-prompt-llm`（`targetWords` 5、`targetCjkCharacters` 10、`maxInputBytes` 4096、`maxOutputTokens` 64、`timeoutMs` 60000）。`first-prompt-llm` 在每个全新非 fork 会话的首条用户消息后自动发一次辅助请求；本项目每个 Action 每轮都是全新会话，于是每个节点每轮都多一次付费调用，只为生成一个没人看的标题——这是本组唯一会进账单的行。`all-prompts-llm` 更甚，每条新提示词后都可能再发一次，上游 base 也不挂它。这次辅助请求带 `purpose: 'session-title'`、有意不带 agent-loop 的请求身份，本项目的用量归集靠会话的 usage 事件，这笔支出能否落到节点账上没有验证过——与搜索三件套是同类的账外支出风险（组 2），不挂就不存在。只挂 `session-title` 不挂提供方，得到的是首条消息前五个词的截断回退，同样没人看。`session-title-llm` 是库，随两个提供方一起不进依赖。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-authorization`
- **seam 角色**：Service Definition（`ctx.authorization`）
- **决定**：不挂
- **它给会话带来什么**：无——授权是配置期与人的对话，flow、notice、prompt 都不会抵达模型请求，也不进请求前缀。
- **理由**：它解决的是「有些凭据配不了、只能取」的那段对话及其生命周期——打开这个页面、粘贴那个码、选一个账号；交互随请求传入，无头调用方传入一个直接拒绝的实现。本项目的凭据只以引用名进入组合，值由 spawn 时的环境白名单注入（ADR-0006），没有任何在运行期「取凭据」的路径；运行期间也没有人能打开页面或粘贴码。上游 base 同样不挂它；上游唯一的 flow 注册方 `llm-pi-ai` 以 `ctx.inject(['authorization'], …)` 作用域式依赖它，seam 缺席时静默不注册 flow。`llm-pi-ai` 本身是备选（组 9），将来即便挂它走 OpenAI 兼容网关，走的也是 `apiKeyEnv` 引用名，不需要 flow。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-skill-badge`
- **seam 角色**：Service Provider（向 `ctx.skills` 贡献内置技能 `dsh-badge`）
- **决定**：不挂
- **它给会话带来什么**：经 `tool-skill` 间接——启用后技能目录里多一条 `dsh-badge`，正文是官方「powered by dsh」Markdown 片段与随包的 PNG。
- **理由**：这是宣传素材，不是能力；它是本组唯一不涉及「人在运行中」的行，服务的是产物读者眼里的外观。上游 base 以 `disabled: true` 包含它、要人显式启用，本项目的清单是平铺的显式清单，没有就是没有（ADR-0013）。更要紧的是来源：本项目模型看到的技能目录全部来自工作流的技能集，经 Skill 库投影到 `data/skills/<slug>/` 再以 symlink 链进工作区的 `.agents/skills/`（ADR-0007、ADR-0016），一个上游内置技能会绕过库与运行快照直接出现在目录里，破坏「模型看见的技能都能在库里查到」的前提。
- **可按工作流切换**：否

## 待核对

- 目录里 `dsh-user-questions` 的一句话理由是「问了会挂死到墙钟超时」。按上游源码，seam 挂着而没有提供方时 `ask()` 立即抛 `NO_PROVIDER`，挂死只在本项目自己注册了桥到 Next 侧的提供方时才发生；本文按两种情形分别写了，一句话理由是否要改措辞由维护者定。
- `session-title-first-prompt-llm` 的辅助请求有意不带 agent-loop 的请求身份，它的 usage 是否会被本项目按会话归集到节点未经验证；不挂时无关，一旦有人想挂回来先验这一条。
