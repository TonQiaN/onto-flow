# 08 遥测与身份

> 默认方向：不挂：内容不出本机。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这组是上游里**唯一目的是把会话内容、身份或反馈送出当前进程**的行：送到一个 OTLP collector、送到模型厂商、或者存进一份等人来看的宿主侧记录。它们的共同特征是上游 README 的「模型体验」一节全部写着「无」——四行里没有一行向模型请求贡献一个 token，挂与不挂，模型在会话里看到的、做到的一模一样。所以这组的判据不是「模型的手脚会不会少一只」，而只有一个问题：**有没有字节离开本机，离开之后谁能把它们关联起来。**

本项目的结论是四行全部不挂，而且这个「不挂」是结构性的，不是一个开关值。三件事撑着它：其一，组合是显式平铺清单（ADR-0013），遥测那一行根本不存在，`DSH_TELEMETRY_MODE` 无论设在哪里都没有对象；其二，本项目的宿主是 Next 进程，`ontoflow-rpc`（组 10）把子进程的 `session/event` 原样转给它，引擎到达即落 `run_events` 与 `node_usage`，权威转录在 `<run>/sessions/*.jsonl`（组 4）——上游遥测 seam 要做的「捕获会话流再交给后端」这件事，本项目已经对着自己的数据库做完了，第二份捕获只会多出一条内容外流的通道；其三，运行中没有人在（组 6），反馈类的行没有生产者。四个包里除了 `@deepseek-ai/dsh-anonymous-user-id`，其余三个都不在依赖闭包里：想挂它们先要改 `package.json`，再改目录、组合与本文，不是翻一个配置。

真正离开本机的只有模型请求本身——提示、工具 schema、工具结果发往 DeepSeek，那是引擎（ADR-0006），不是遥测。随 chat 请求一起走的还有 `dsh-llm-deepseek` 加在 HTTP 头上的三个传输元数据：`x-deepseek-harness-user-id`、`x-deepseek-harness-session-id` 与压缩摘要调用上的 `x-deepseek-harness-compact`（外加 `dsh-llm` 的 `user-agent` 归因头）。第一个的来源正是本组的 `@deepseek-ai/dsh-anonymous-user-id`，它是库，随组 1 必挂的模型路由进闭包，与本组任何一行挂不挂无关；因为 `DSH_HOME` 钉在 `<run>/home`（ADR-0007），这个身份是**每次运行新铸一个**的随机 UUID，细节见该行。

## 逐行

### `@deepseek-ai/dsh-session-telemetry`

- **seam 角色**：Service Definition（`ctx.sessionTelemetry`）。上游 capability-seams 把它标为 seam：唯一的 Service Provider 是 `@deepseek-ai/dsh-session-telemetry-otel`，Consumer 一栏为空——这个服务的输出离开进程，进程内没人注入它；唯一读它的是 `dsh-command-feedback`（组 6），以 `ctx.get` 可选地取 `sharing` 披露拼进 `/feedback` 的确认文本。
- **决定**：不挂
- **它给会话带来什么**：无。它只观察会话流，把每条事件深拷贝、过一遍 `sessionTelemetry/record` 脱敏 waterfall、交给后端的 `emit()`；绝不向模型请求贡献任何内容，对 KV cache 也无影响。
- **理由**：
  - 这是遥测的「捕获半边」，它决定了一旦有后端、什么会被交出去。实时模式下它挂在 `session/created`、`session/event`、`session/flush`、`session/disposed` 与 `agent/error` 上，每条逻辑记录的 `body` 是完整的 `event.data`：用户与 assistant 的消息内容、工具参数与工具结果（也就是命令输出与文件内容）、`request/header` 里的整份系统提示与工具 schema、todo 文本、压缩摘要、以及作为本地路径的会话 `cwd`。seam 自身**不带任何脱敏规则**：没挂 `sessionTelemetry/record` 监听器时，离开进程的就是捕获原样的副本，上游 README 把「导出能干净到什么程度」明确交给部署方。本项目没有写过一条脱敏规则，而运行内容里有用户上传的文档——简历匹配工作流处理的就是个人简历。「内容不出本机」这句默认方向，说的就是这件事。
  - 本项目对同一条会话流已经有一个本地消费者。`ontoflow-rpc` 在子进程里监听 `session/event` 并经 stdio JSON-RPC 通知 Next 进程，`src/server/engine/events.ts` 把每条事件到达即写成 `run_events` 与 `node_usage`；权威转录是运行目录里的 `sessions/*.jsonl`，轨迹面板从它投影。上游 seam 的「捕获—投影—交接」在这里已经成立，只是后端是本机的 SQLite。再挂一个指向外部 collector 的捕获，工作台多不出一个能展示的字段，只多出一条内容外流的通道。
  - 上游 base 里没有这一行：`SessionTelemetryBackend` 是抽象类，provider 继承它，base 只挂 provider。所以它在上游也是「随 provider 进来的库」。不挂 provider，它就是一个永远不会被加载的包；本项目的 `package.json` 里也没有它。
  - 它的运维记录（`agent/error`、`shutdown`）是给接收端告警用的信号；本项目的失败面已经由引擎持有——节点抛错落 `run_nodes.error`，运行终态由 `executeRun` / `cancelRun` / `failWholeRun` / `reconcileOrphanRuns` 保证不停在 `running`——不需要一条飞出本机的 ERROR 日志来知道运行失败了。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session-telemetry-otel`

- **seam 角色**：Service Provider（telemetry seam 的 OpenTelemetry 后端；上游称它是「部署方唯一要加载的条目」）
- **决定**：不挂
- **它给会话带来什么**：无。它只把 seam 交出来的记录映射到 OTel SDK 的 `logger.emit()`（`LoggerProvider` → `BatchLogRecordProcessor` → OTLP/HTTP 日志导出器），资源身份带 `dsh-llm` 的 `APP_IDENTITY`（`service.name` / `service.version`）与匿名 `user.id`；绝不向模型请求贡献任何内容。
- **理由**：
  - **上游 base 在每个 profile 里都挂它，headless 也不例外。** base 行的值：`mode` 取 `process.env.DSH_TELEMETRY_MODE || 'DISABLED'`；`exporter.url` 取 `process.env.DSH_TELEMETRY_OTLP_URL ?? 'https://harness-telemetry.deepseeksvc.com/v1/logs'`，`compression: gzip`，`timeoutMillis: 1000`；`processor` 为 `scheduledDelayMillis: 10000`、`maxQueueSize: 2048`、`maxExportBatchSize: 2048`、`exportTimeoutMillis: 1500`；`shutdownTimeoutMillis: 3000`。默认 `DISABLED` 时它不构造协调器、provider、processor 或导出器，没有记录离开进程；关闭状态下这一行仍挂着的可见效果只有一个：`sharing` 披露为 `disabled`，`/feedback` 的确认文本能据此报告本会话未被共享（没挂它时该文本报告「未配置」）。硬退出是任何非空的 `DSH_TELEMETRY_DISABLED`（含 `'0'` / `'false'`）——由启动器把这一行 patch 成 `disabled`，因为 config 关不掉一行。
  - **我们的差异是这一行不存在，而不是把它设成 `DISABLED`。** 三个后果：第一，没有任何环境变量能把它打开，`DSH_TELEMETRY_MODE` 没有收件人；退一步说，子进程环境以上游自己的 `scrubbedParentEnv()` 为底——它剥掉父环境里全部 `DSH_*` 名字——`launch.ts` 显式注入的只有凭据白名单与 `DSH_HOME`、`TMPDIR`、`ONTOFLOW_DB_PATH`、`ONTOFLOW_DATA_DIR` 四个运行事实，Next 进程 shell 里的 `DSH_TELEMETRY_*` 无论如何到不了子进程。第二，这个包与它带来的 `@opentelemetry/sdk-logs`（上游 README 自述来自实验性源码树）都不在依赖闭包里，把它挂上是一次依赖变更加三方同步，不是翻开关。第三，它在关闭状态下唯一的价值——`sharing` 披露——的读者是 `@deepseek-ai/dsh-command-feedback`（组 6），后者也不挂，披露没人问。
  - **为什么不「跟 headless 一致」挂一行 `DISABLED`。** README 的体验基线说的是模型在会话里的体验，而这一行没有模型体验；为了一个没人能敲的命令的一句确认文本，往每个运行子进程里装一套 OTel SDK 流水线，是纯粹的负重。举证方向在组 5–8 本来就反过来：不挂是默认，挂才要理由。
  - **如果哪天真要外部 collector。** 上游 `FULL` 会把上一行列出的整份 `event.data` 交出去，`FEEDBACK_ONLY` 在 `feedback/record` 时回放权威日志到该事件为止，两者都以当时挂着的脱敏规则为准、没有规则就是原样。凭据不会泄漏——适配器的 API key 是构造参数不是会话事件，结构上不在日志里，与 ADR-0006「值不落日志」一致——但内容会。走的路径是配置：本行的 `mode` + `exporter.url`（上传模式必填、必须 `http(s)`）+ `processor`，外加自己写的 `sessionTelemetry/record` 监听器；更诚实的替代是从 Next 侧读 `run_events` 与 `sessions/*.jsonl`，同一份记录已经在本机。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-anonymous-user-id`

- **seam 角色**：库。上游 README 明说它不是 cordis 插件，消费方直接 import `getOrCreateAnonymousUserId()`；它的不变式伴生插件刻意留空。
- **决定**：不挂。这一行没有可挂的 entry；「不挂」在这里的含义是：不挂任何为遥测或反馈消费这个身份的插件（`dsh-session-telemetry-otel`、`dsh-command-feedback`）。
- **它给会话带来什么**：无。这个标识符只作为模型不可见的 HTTP 传输元数据发给 DeepSeek，绝不进入请求正文、提示词或模型可见内容；不改变 token，也不改变模型可见前缀。
- **理由**：
  - **它在闭包里，而且每次模型请求都在用。** `package.json` 把它钉在 `0.1.1-rc.2`，原因是组 1 必挂的 `@deepseek-ai/dsh-llm-deepseek` peer-depend 它：凭据解析成功后，每个 chat 请求（`llm/stream` 走的那条）都带 `x-deepseek-harness-user-id`；携带会话 id 的请求再带 `x-deepseek-harness-session-id`——agent-loop 的不变量要求每个循环构造的请求都带会话 id，在本项目里那就是 Action 的节点 id；压缩摘要那次调用另带 `x-deepseek-harness-compact: 1`。三个头都发往解析后的 `baseURL`（包括覆盖过的 gateway），不受任何遥测模式影响，`DSH_TELEMETRY_DISABLED` 也不关它。上游 README 说的「每个提供方请求」实际只覆盖 chat：Files API（图片上传、查询、删除）的请求只带 `authorization` 与 `user-agent`，不带这三个头。目录那句「随遥测一起不挂」说的是没有插件消费它，不是它没被用到。
  - **身份是每次运行新铸的。** 文件落在 `$DSH_HOME/.anonymous-user-id`（未设 `DSH_HOME` 时是 `~/.dsh/.anonymous-user-id`），在凭据解析成功后的首次模型请求时以独占创建写入随机 UUID v4，同一进程内按文件路径缓存。本项目的子进程 `DSH_HOME` 钉在 `<run>/home`（ADR-0007），所以每个运行在第一次模型调用时铸一个自己的 id，随运行目录一起被清理删除。已在一次冒烟运行里核实：`<run>/home/.anonymous-user-id` 是一个 UUID，与本机 `~/.dsh/.anonymous-user-id` 里的不同。后果是 DeepSeek 侧能把**一次运行内**的请求关联起来（同一 user id，每个 Action 一个 session id），但跨运行没有稳定身份，也不与本机用户自己敲 `dsh` 的身份重合。这是 home 隔离的副产品，不是一个为身份做的决定。
  - **为什么可以接受。** 它是随机数，上游保证不从 hostname、网络地址、git remote 等可识别来源派生；它不是内容；它去的地方是我们本来就把提示送去的模型端点，不是第三方 collector。它是本组唯一真正离开本机的数据，而离开的理由是模型调用本身。
  - **如果要跨运行稳定的身份。** 唯一的杠杆是在 spawn 前把 `<run>/home/.anonymous-user-id` 预置成工作台级的值——上游读到合法 UUID 就直接采用。目前刻意没做，见文末「待核对」。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-message-feedback`

- **seam 角色**：Service Definition（`ctx.messageFeedback`，上游 capability-seams 标为 core 类，包自带实现、没有独立 provider），同时发布 Host 一元 Remote 契约 `messageFeedback.list` / `put` / `delete`。
- **决定**：不挂
- **它给会话带来什么**：无。它不注册工具、提示词段落、模型可见上下文或会话事件；评分、备注、时间戳与失败都不进模型请求，token 为零，对 KV cache 相互独立。
- **理由**：
  - **它是什么。** 由宿主拥有的、针对单条已完成 assistant 消息的可编辑反馈：`rating: 'positive' | 'negative'` 加可选备注，按会话在 storage-domain 的 `message_feedback` 域里存一条生命周期绑定的伴随记录，`put` 之前经 `ctx.sessions.flush` 与物理复读建立持久性屏障。它与 `feedback/record` 事件（`dsh-command-feedback`，组 6）相互独立，**不执行遥测交接，也不触发 `FEEDBACK_ONLY` 的释放**——所以严格说它不是一条外流通道；它在这一组，是因为它是身份/反馈家族里「反馈」的那一半，而且它存在的前提是有一个人在看消息。
  - **上游只在 web-app 挂它，base 与 headless 都没有。** web-app 的值是 `maxNoteBytes: 8192`，排在 `storage` / `storage-json`（root 在 `dshHomePath('storages')`）/ `storage-domain` 之后；它注入 `storageDomain`、`sessionPersistence`、`sessions`，经 typert 的 `@Remote` 发布三个一元契约、由 `dsh-api-gateway` 承载调用，浏览器端的消费方是 `dsh-client-ui-message-feedback`。本项目不挂 storage 枢纽（组 7 的 `dsh-storage`、组 9 的 storage-json / storage-sqlite）、不挂 api-gateway 与 typert 族（组 7）、没有浏览器客户端（组 7 的 `dsh-client-*`）。把它挂上意味着再拖四五行进组合，去服务一个没有调用方的 Remote。它也不在依赖闭包里。
  - **本项目里「这一步做得好不好」不是对一条消息点赞。** 判断归工作流自己：下游 Action 读产物再判定、出口端口决定走哪条边（ADR-0009）、专用调用入口的完成门禁核验最终产物后才写 `run_results`；人看的是工作区里的产物文件（ADR-0008），不是聊天气泡。运行页从 `run_events` 投影轨迹与事件，没有一个 assistant 消息可以让评分挂上去。
  - **上游自述的限制也说明它是给单宿主网页用的。** compare-and-set 只在单进程内串行化，storage-domain 没有跨进程条件写；没有持久删除级联；`list` / `put` / `delete` 不带认证的 actor，上游要求只经受信任边界暴露 Host gateway——本项目没有这样的边界，也不打算为它造一个。
- **可按工作流切换**：否

## 待核对

- **每运行新铸匿名身份是否是我们想要的。** 这是 `DSH_HOME` 钉进运行目录的副产品，不是决定。今天的结果是 DeepSeek 侧只能关联一次运行内的请求；如果将来需要厂商侧按工作台关联用量（例如对账），要在 spawn 前把 `<run>/home/.anonymous-user-id` 预置成工作台级的稳定值，并在 ADR 里记下「一个随机 UUID 跨运行稳定」的隐私取舍。需要人拍板。
- **目录里 `@deepseek-ai/dsh-anonymous-user-id` 那句一句话理由（「随遥测一起不挂」）低估了它的实际存在**：它在闭包里、每次模型请求都把它发给 DeepSeek。本文只改这一个文件；是否把目录的 `reason` 改成「库，随 llm-deepseek 进闭包并作请求头发出；不挂任何消费它做遥测的插件」由维护者决定。
