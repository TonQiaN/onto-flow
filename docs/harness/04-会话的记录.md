# 04 会话的记录

> 默认方向：跟上游。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

这组是会话事件流的落盘，以及在这份日志之上派生的读模型。上游把「会话日志是唯一真源」当成事件溯源模型：`dsh-session` 发出事件，持久化 seam 把同一套 `SessionEvent` 词汇写到磁盘，检查点策略决定哪些边界必须先落盘再往下走；投影、统计、检索、导出全部只读这份日志，不碰提示词、消息、schema 或工具结果。所以本组没有一行会改变模型在会话里的体验，判据不是「模型需不需要」，而是「谁读这份记录、在哪个进程读」。

本项目里读者只有一个：Next 进程的运行详情。`run_events` 是跨节点的实时摘要，某个 Action 的 Agent 轨迹以运行目录内 `<run>/sessions/**/session.jsonl` 为权威源，用户展开面板时由 `src/server/harness/trajectory.ts` 按需读取并按回合与步骤折叠（docs/DESIGN.md）。读取发生在子进程退出之后、在 Next 进程里、按数据库记的 `runDir` 直接开文件——运行之间没有长驻的 harness host 可供查询。再加上每一轮都是全新的会话、上一轮的产物经工作区文件传给下一轮（CONTEXT.md「轮次」），本项目对这份记录只有「写」的需求，没有「恢复」「续聊」「检索历史」的需求。

总体结论：写的一侧完整跟上游 headless——持久化 seam 定义、JSONL provider、检查点策略三行都挂，原子写库随闭包进入；读的一侧全部不挂——投影注册表、投影缓存、统计单元、检索契约、检索工具、导出命令七行，读模型在 Next 侧。与上游 base 的差异只有两处：base 挂 `session-projection` 与 `session-query-sqlite`（后者 `openAt: never`，见组 9），我们都不挂，理由写在各自那行。

## 逐行

### `@deepseek-ai/dsh-session-persistence`
- **seam 角色**：Service Definition（`ctx.sessionPersistence`）
- **决定**：挂（不是组合行；作为 provider 的 peer 依赖进入闭包）
- **它给会话带来什么**：不添加提示词或 schema。持久化单元就是 `SessionEvent` 本身，没有另一套「持久消息」类型；恢复时把已存储事件还原为消息历史，崩溃修复用 `TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN` 平衡未获回答的调用。普通持久化期间零 token。
- **理由**：seam 定义与 provider 分包是上游的角色划分（与 `dsh-shell` 同一模式）：本包定义「持久存储、重新加载、列出会话」的契约与每个后端必须遵守的不变量——仅追加、连续 `seq`、JSON 可序列化、`append` 只在批次持久后返回、崩溃轮次被合成 closer 关闭而不是截断。挂 JSONL provider 就等于挂了它，这一行没有独立的取舍；单列是为了说清本项目消费这个 seam 的方式与上游不同。上游的 Consumer 是 `agent-loop`（恢复）、`tool-bash`、`session-query` 及其 sqlite provider、两个 hooks 包与 `message-feedback`（docs/capability-seams.zh.md）；本项目只依赖它的写侧行为：`SessionHeader` 里持久化的 `cwd` 决定磁盘上的项目目录，会话 `session/disposed` 时协调器对它做最终 drain——节点结束即关闭会话，日志尾部随之落定。`load` / `prepare` 的恢复路径在本项目没有任何调用者，`readFrom` / `listSnapshots` 也没有；README 列的「无删除或保留接口」对我们无关紧要，运行目录由清理路径整体删除。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session-persistence-jsonl`
- **seam 角色**：Service Provider
- **决定**：挂
- **它给会话带来什么**：不向当前请求提供提示词或 schema，当前请求不新增 token；每个会话一个仅追加的逻辑 JSONL 日志，默认存为 `.jsonl.zstd`，禁用压缩时是原始 `.jsonl`。
- **理由**：这是 Agent 轨迹的权威源，所以必挂，而且两个配置键都要改。
  - **`root` 钉到 `<run>/sessions`。** 上游 README 明言 `root` 无默认值（`process.cwd()` 默认会随 bash 调用与子进程分散文件），base 钉在 `$DSH_HOME/sessions`。我们不沿用 home 下的位置而放在运行目录一级，是让轨迹读取只依赖数据库记的 `runDir`：`trajectory.ts` 从 `<run>/sessions` 出发枚举，与子进程当时的 `DSH_HOME` 无关；清理路径删的是整个运行目录，轨迹随之报 `cleaned`，不会出现「工作区没了、日志还在 home 里」的半残状态。
  - **`compression: 'none'`。** 上游默认 `zstd`，README 自己写明「压缩文件不能直接按行读取：使用后端加载；或选择 `compression: 'none'`，以便外部行 reader 使用」。我们的读取端正是外部行 reader：它在子进程退出后、在 Next 进程里读文件，逐物理行解析，只认「换行是提交边界」这一条上游约定，把最后一个未换行的物理行当作尚未提交而忽略，因此活跃 writer 与读者并发也不需要后端参与。明文还让运行目录本身就是可直接 `cat` 的调试证据。代价是逻辑日志不再压缩——但 `packChunks` 走上游默认 `true`，连续的 `assistant/chunk` delta 段仍打包成一行（上游实测逻辑日志约小 60%），读取端用 `dsh-session` 公开的 `decodeStorageRecord` 解包，打包与否不影响可读性。
  - **磁盘布局是读取端的契约。** `<root>/--<normalized-cwd>--/<encoded-id>/session.jsonl`：首轮会话 id 就是节点 id，回边重入的第 N 轮（N ≥ 2）是 `nodeId#N`，目录名是 id 的单射转义（`#` 转成 `~0023`）；轨迹读取用目录名缩小候选范围，归属仍以 header 为准，所以展开一个节点不会把同一运行里其它 Action 的日志整份读进内存。首行 header 是 `dsh-session` 拥有的 `SessionHeader`，格式版本不等于 `SESSION_FORMAT_VERSION` 时读取端直接拒绝——上游升级会同时改这两端。
  - **上游列的限制在本项目里自然满足。** 「一个根只属于一种编码、没有迁移」：每次运行新建目录。「每会话一个活动 writer」：每运行一个子进程（ADR-0007）。「不删除会话文件」：运行目录由清理路径整体删除。「POSIX 实体化需要硬链接」：`data/` 在本机文件系统上。
  - **合并窗口是下一行存在的原因。** `writeBatchMaxDelayMs` 默认 200 ms，首个待写事件开窗、后续事件不重置；单靠这一行，崩溃可能丢掉仍在窗口内或写入未完成的事件，所以检查点策略必须同挂。
- **配置要点**：`root` = `<run>/sessions`（上游 base：`$DSH_HOME/sessions`；README 无默认值）；`compression` = `none`（上游默认 `zstd`）；`packChunks`、`preparedSessionCacheSize`、`writeBatchMaxDelayMs` 走上游默认（`true` / `5` / `200`）。
- **定制**：配置 / 改 `root` 与 `compression` 两个键 / 轨迹读取端是 Next 进程里的外部行 reader，路径只能依赖 `runDir`、编码只能是明文 / `packages/session/session-persistence-jsonl/README.zh.md`@0.1.1-rc.2
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session-checkpoint-policy`
- **seam 角色**：Consumer（零配置函数插件，消费 `ctx.sessions`、`ctx.llm`、`ctx.tools` 与 `ctx.sessionPersistence` 的存在性）
- **决定**：挂
- **它给会话带来什么**：不添加提示词或工具 schema；成功的检查点不添加 token、不改变请求。崩溃后恢复时模型会看到 `TOOL_OUTCOME_UNKNOWN`（由 `dsh-session` 负责），允许重试只读或幂等工作、要求对有副作用的调用先验证状态。
- **理由**：上游刻意把「落盘」和「哪些边界必须先落盘」拆成两个插件，并明说不带此策略加载后端是有效的，但崩溃可能丢失仍在合并窗口内的事件或尚未完成的写入。本项目的崩溃面是真实的：子进程未经 dispose 的退出算崩溃，取消是终止整棵进程树（ADR-0007），节点有墙钟超时。这三条路径里任何一条落在 200 ms 窗口内，没有策略就意味着最后一段模型响应或最后一次工具调用只存在于内存批次，轨迹面板永远看不到它。策略在三个边界 flush：模型适配器收到请求前、顶层工具正文运行前、每个 `agent/pre-step`。于是崩溃后的 JSONL 至少含有「前一条完整响应与有序的工具结果」，与 `run_events` 的实时落库互为补充——后者是 SSE 的源，前者是轨迹的源，两边都不能等节点跑完才写。策略是失败即阻止：检查点被拒绝时适配器与工具正文都不运行，步骤边界被拒绝会让轮次失败。对付费节点这是正确方向，宁可节点失败也不要一段无法追溯的模型调用。我们不需要它的恢复价值（每轮新会话），只要它的持久性价值，这与上游 headless 的挂法完全一致。README 记的限制照样成立：流式 `assistant/chunk` 没有逐分片检查点，硬崩溃可能丢当前内存批次——这正是轨迹投影把 token chunk 聚合成「运行中或中断的模型响应」而不是逐条展示的原因。
- **配置要点**：上游默认（零配置；base 同样零配置挂载）。要求 `ctx.sessionPersistence` 先可解析，组合里排在 JSONL provider 之后。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-atomic-write`
- **seam 角色**：库（零依赖的原子文件替换原语 `writeFileAtomic` / `withFileLock`；无 ctx 服务，不是插件）
- **决定**：挂（随闭包进入；不是组合行）
- **它给会话带来什么**：无。纯文件系统原语，此处没有任何内容会到达模型请求或进入请求前缀。
- **理由**：它是 `dsh-credentials-local` 与 `dsh-llm-deepseek` 的 peer 依赖（docs/module-graph.zh.md 与两包的 `peerDependencies`），我们挂这两行它就在闭包里，package.json 直接钉版是因为整个 `@deepseek-ai` 闭包逐包钉 0.1.1-rc.2。上游用它保证文件型存储「绝不在磁盘上留下不完整、被符号链接劫持或权限过宽的内容」：独占创建临时文件、新 inode 带 `mode` 走 rename、rename 替换符号链接本身而不写穿。它归这一组是因为关切相同——记录不能半残——但要说清它**不**服务会话日志：JSONL 后端有自己的 fsync 与硬链接无覆盖发布；本包 README 明言「原子但不保证持久（不 fsync）」。上游两个调用方各服务一份 `DSH_HOME` 下的文件：`dsh-credentials-local` 的 `.credentials.yaml`，只在 `set` / `unset` 时写；`dsh-llm-deepseek` 的图片上传索引（`src/upload-index.ts`，附件到 Files API 文件 id 的映射，按端点与 API key 作用域记录），每次成功上传后写。本项目自己的代码不导入它。一次运行里凭据只以引用名进入、值从 spawn 环境注入，凭据文档不会被写；会真正触发它的是 Action 经 `read_image` 把图片送进模型请求的那一刻（`attachment-local` 在组合里，见组 2），索引落在 `<run>/home`，随运行目录一起被清理路径删除。它的「遗留锁需要操作者恢复」限制因此只可能出现在一次运行自己的 home 里，不会跨运行残留。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-invariants`
- **seam 角色**：Service Definition（`ctx.invariants`，包自有运行时不变量的注册表）
- **决定**：不挂
- **它给会话带来什么**：无。服务与配套入口只观察运行时事件与可变快照，不更改提示词、消息、schema、流或工具结果。
- **理由**：上游三个 bundle 的 patch（base / headless / web-app）都没有这一行，仓库里也没有任何 cordis yml 挂它；README 里「标准 agent 组合挂载服务和 4 个核心有状态配套入口」在源码里唯一对应的运行时挂载是示例包 `packages/examples/agent-spine-demo`，不是发布的 bundle。每个 dsh 包发布一个 `./invariant` 配套入口并 peer 依赖本包，所以它在闭包里、package.json 钉版；但 README 明言「在没有服务时加载配套入口，会等待其声明的 `invariants` 注入」，也就是 fiber 挂起、产品行为不变，包的根入口独立于诊断。它是给上游开发者查自己包的跨记录规则用的：检查失败抛 `InvariantError`。在付费运行里我们不想因为上游的诊断断言炸掉一个节点，而且不挂就与 headless 一致。与 base 的差异：无。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session-projection`
- **seam 角色**：Service Definition 与驱动注册表（`ctx.sessionProjections`）
- **决定**：不挂
- **它给会话带来什么**：无。注册表只对已入日志的会话状态计算面向客户端的读模型，从不组装或发送提供方请求。
- **理由**：上游 base 挂它（无配置），是因为三个消费者都在 base 里：subagent 目录的身份折叠经它，`list_agents` 没有它会失败即报错；`session-title` 与 `tool-todo` 向它注册单元；Web 列表行复用同一挂载。本项目三条都没有：subagent 不挂（ADR-0014，组 5），`session-title` 不挂（组 6），没有 Web 列表（组 7）。`tool-todo`（组 3）是在 `ctx.inject(['sessionProjections'], …)` 下注册单元的，README 明言「不带注册表的 headless 组装完全不受影响」——todo 工具照常工作，只是没有投影。本项目的投影在 Next 侧：`trajectory.ts` 直接读 JSONL 折叠出回合、步骤、三泳道与用量，用户展开面板时才算，不需要子进程内为每个会话维护水位 cell。注册表「单元表是进程级的」这条限制也说明它的定位是长驻 host，而每次运行的子进程是短命的。与 base 的差异：base 挂、我们不挂。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session-query`
- **seam 角色**：Service Definition（`ctx.sessionQuery`：可信的精确读取、关系查询、过滤与搜索契约）
- **决定**：不挂
- **它给会话带来什么**：无。可信读取契约，不注册面向模型的提示词、schema、工具或消息。
- **理由**：上游 base 挂的是它的 provider `session-query-sqlite`（组 9 备选），配置 `path: ':memory:'`、`openAt: never`：`ctx.sessionQuery` 保持挂载，精确读取、标题与血缘追踪可用（供 session export 与 subagent-fork 的工作区继承），全文搜索以 `SESSION_QUERY_SEARCH_DISABLED` 失败、SQLite 从不打开——上游自己在 headless 里也只把它当精确读取用。本项目的消费者一个都不在：`session-log-export`（Web）、`tool-session-query`（不挂）、`session-reference`（组 3，不挂）、subagent-fork（ADR-0014）。运行详情按数据库记的 `runDir` 直接开 JSONL 文件，不经 `ctx.sessionQuery`，因为读取发生在 Next 进程、子进程早已退出，没有长驻 host 可查。与 base 的差异：base 挂 sqlite provider（连带定义），我们一行不挂。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tool-session-query`
- **seam 角色**：Consumer（`ctx.sessionQuery` 之上、经工作区授权的模型工具：`session_search`、`session_event_search`、`session_trace`、`session_event_trace`、`session_event_read`）
- **决定**：不挂
- **它给会话带来什么**：系统提示词多一段固定的「既往历史指引」，每次请求发送 5 个固定只读 schema；搜索结果以纯文本块进入工具历史直到压缩。
- **理由**：上游自己是 opt-in——README 明言「已发布的宿主组合默认不挂载它」，base / headless / web-app 都没有。在本项目它还与领域模型正面冲突：每一轮都是全新的会话，上一轮的产物与评审意见经工作区文件传给下一轮，不靠会话记忆延续（CONTEXT.md「轮次」）；下游只拿到工作区里的产物路径（ADR-0008、ADR-0012）。而这个工具的跨会话授权规则是「目标与调用方会话的 `cwd` 严格相等」——同一运行内全部 Action 的 cwd 都是 `workspace/`，一旦挂上，模型能搜到同一运行里其它 Action 的会话，包括还在跑的兄弟节点，把产物边界打穿。没有 `ctx.sessionQuery` 它也无法工作。
- **可按工作流切换**：否
