# 01 骨架

> 默认方向：必挂。参照：上游 headless 会话（ADR-0013）。上游版本见 README。

骨架是「拿掉任何一行就没有会话」的那部分：插件框架与装载器、启动粘合层、模型 seam 及其唯一
适配器与重试器、凭据 seam 及其本地 provider、会话日志、提示词组装、工具注册表、agent 接口与
循环驱动器、作用域原语、线协议，以及两个基础库。判据只有一条——去掉它之后，要么子进程根本
起不来，要么起来的会话与人在工作区里 `dsh --profile headless` 聊出来的那个会话不是同一种东西。
这组没有「跟不跟上游」的问题，只有「怎么配」的问题。

本组 18 行里 10 行是组合 entry（`timer` / `llm` / `llm-deepseek` / `llm-retry` / `credentials` /
`session` / `system-prompt` / `tools` / `agent` / `agent-loop`），另外 8 行是框架、库、seam 定义
或 boot 路径上的包，不出现在 `cordis.yml` 里。10 个 entry 与上游 base 的对应行一一同名；配置上
与 headless 基线真正不同的只有两处：`llm-deepseek` 的连接事实写在 entry 配置里而不是 settings
文档里（因为不挂 settings-file，见组 7），`system-prompt` 的 persona 留空而 headless 给的是一句
编码 persona（`tools` 的 `mode` headless 接到 `DSH_TOOLS_MODE`，环境变量不设时与我们不配置
等价，不算第三处）。其余 entry 要么无配置，要么与 base 的值逐字相同。围绕这组行、base 挂了而我们
没挂的邻居——`settings-file`、`agent-default-model`、`.env` 分层——分别在组 7 与本文对应行里
说明它们的缺席怎样改变了这一行的行为。

组内定制全部停在「配置」一阶：没有包装、没有 fork。上游给这组留的扩展点——`agent/pre-step`、
`agent/request`、`tools.restrict` / `tools.guard`、`setup(agentCtx)` 创建窗口——本项目都用了，
但用它们的代码住在 `ontoflow-rpc` 里，归组 10；本文只指出每个扩展点是哪一行提供的、上游对它
的约定是什么。

## 逐行

### `@deepseek-ai/cordis`
- **seam 角色**：库（插件框架本身）
- **决定**：必挂
- **它给会话带来什么**：模型看不见它，但会话里的一切注册——工具、提示词段、事件监听、定时器——
  都是它的 fiber 拥有的副作用，fiber 释放即撤销。Action 会话「创建时收窄、关闭时全部释放」的
  生命周期就是这条机制。
- **理由**：引擎就是一棵 cordis 插件树（ADR-0006），没有替代物可选；本项目自己 `new Context()`
  起树（经 `dsh-app-boot` 的 `boot()`），所以它不是组合行而是 runner 的直接依赖。上游把它源码
  vendor 进 monorepo 并改到 `@deepseek-ai` scope，对 `fiber.ts` 做过可重入释放加固、对 Loader
  做过事务化配置调和；这些改动只在上游 `vendor/README.md` 的「Local modifications」里有账，
  升级时要一并看。版本单独钉在 `package.json`（`4.0.1`），不在 `0.1.1-rc.2` 那条钉版线上，
  `catalog.test.ts` 的版本检查也不覆盖它。
- **可按工作流切换**：否

### `@deepseek-ai/cordis-plugin-loader`
- **seam 角色**：框架插件（Loader 服务，`ctx.loader`）
- **决定**：必挂
- **它给会话带来什么**：无直接影响。它拥有 entry 树、按 `name` import 插件模块、把 `config`
  交给插件，`loader.await()` 是「整棵树 settle」的边界。
- **理由**：`boot()` 内部安装，不是组合行。它对本项目有两条硬约束：一、裸包名从 Loader 自己在
  `node_modules` 里的位置解析，而本仓库不是 workspace、没有指回自己的软链，所以本项目自己写的
  插件（`ontoflow-rpc`、按运行生成的 Tool 插件）一律以绝对路径进组合，`boot()` 的
  `bareModuleBaseUrl` 只救得了上游包名；二、`ontoflow-rpc` 回答 `initialize` 前先等
  `loader.await()`，把「树已 settle」当作对 Next 侧的就绪边界，Action 会话不会在插件半挂载时
  创建。上游 headless 运行器创建 agent 前同样先等这一步。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-app-boot`
- **seam 角色**：库（app bin 共用的启动粘合层）
- **决定**：必挂
- **它给会话带来什么**：无直接影响；它决定的是子进程「要么整棵树激活、要么退出 1」。
- **理由**：`runner.ts` 与 `boot.ts` 合起来只用它两样：`boot(binName, 组合路径, 无 patch, 无 prepare,
  bareModuleBaseUrl)` 与 `installFailLoud()`。`boot()` 起根 Context、向 `!!js` 表达式提供
  `dshHomePath`、安装 Loader、经静态注册的 `cordis:include` / `cordis:group` builtin 挂上我们的
  `cordis.yml`、等 settle，最后 `assertEntriesActivated`：任何启用了却没有 fiber、或还在等某个
  服务的 entry 都让启动整体 reject 并带上那个插件自己的错误堆栈。因此 `cordis-plugin-include` /
  `cordis-plugin-group` 作为机制一定在进程里（它们是 `app-boot` 的 peer），组 7 把这两行标为
  「不挂」说的是用法——不叠 patch、不写 `insert`、不嵌套分组——两组口径一致。激活审计正是
  「一个 Tool 插件 schema 用了类型数组 → 插件加载失败 → 整个运行在任何节点开跑前失败」这条
  行为的来源，也是我们要的：付费节点不该在半棵树上开跑。与上游 `dsh` 启动器相比，我们不走的部分都是有意的——不 `loadLayeredEnv`（子进程不读任何
  `.env`，凭据只经 spawn 环境白名单进入，ADR-0006）、不组 profile / bundle、不叠 patch
  （ADR-0013）、不 `watchUserPatches`（每运行一个短命进程，没有热改的对象）、不
  `addHarnessSourceSection`（那是给开发者看源码路径的）。`installFailLoud` 把启动后未处理的
  Loader rejection 变成一行带 `ontoflow-harness` 前缀的 stderr 并退出 1，落在
  `logs/harness.stderr.log`。
- **可按工作流切换**：否

### `@deepseek-ai/cordis-plugin-timer`
- **seam 角色**：Service Provider（`ctx.timeout` / `ctx.interval` / `ctx.throttle` / `ctx.debounce`）
- **决定**：必挂
- **它给会话带来什么**：无直接影响。它提供随当前 fiber 注册、fiber 释放即清除的定时器句柄。
- **理由**：上游 base 的第一行就是它，无配置。它保证任何经 `ctx.timeout` 起的定时器不会在会话
  关闭后继续跑——这在每运行一个进程、多会话同进程的形态下有实际意义：一个已关闭 Action 的
  残留定时器不该在下一个 Action 的会话里触发。诚实地说，对本项目实际挂载的上游包做源码检索，
  没有找到调用 `ctx.timeout` / `ctx.interval` / `ctx.throttle` / `ctx.debounce` 的消费方（它们
  用 Node 原生定时器与 `AbortSignal`；`app-boot` 虽把它列为依赖，自己的 fail-loud 超时也用的是
  `setTimeout`）。上游源码里的调用方只有四处，全部不在本项目组合里：`cordis-plugin-hmr` 的
  `ctx.debounce`（组 7）、`dsh-cordis-host-runner` 的 vm 沙箱（组 7）、`dsh-cordis-client-runner`
  与 `agent-spine-demo` 示例。保留它是零成本对齐 base，并为按运行生成的 Tool 插件留出
  「用 ctx.timeout 就自动随 fiber 回收」的正确路径。
- **配置要点**：上游默认（无配置）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-llm`
- **seam 角色**：Service Definition（`ctx.llm`：适配器注册表与单一流式调用接口）+ Consumer
  （消息、内容块、`StreamChunk` 词汇由它定义并使用）
- **决定**：必挂
- **它给会话带来什么**：上游明说「无」：它不添加任何模型可见文本、schema 或消息，只填入并记录
  适配器配置的思考强度与输出上限。
- **理由**：没有它没有模型调用，但它对本项目的分量不止于此。第一，`LlmCallConfig`
  （`provider` / `model` / `reasoningEffort` / `temperature` / `maxTokens` / `stop`）是每会话请求
  状态，`agent/request` waterfall 提议替换、`prepareCall()` 校验并填入适配器默认值、循环再把
  生效值记进 `request/header`——思考强度只能经这条路到达模型，因为 `AgentOptions` 只有
  provider / model / maxTokens，交给 `llm/stream` 的 `GenerateOptions` 已经冻结。第二，
  `usage` 是流协议里独立的 chunk，每步一个、先于 `finish`，这是「按步求和即正确、无重复计数」
  的根据。第三，它是跨进程边界的共同词汇：Next 侧 `runtime.ts` 从它 import `ContentBlock`
  类型来描述 prompt 帧的内容块，子进程里的 `ontoflow-rpc` 用它的 `createUserMessage` 把同一
  帧还原成 `Message`——两侧对「一条用户消息长什么样」的约定都来自这一个包。
  失败一律以终止 `finish { kind: 'error' | 'aborted' }` 到达消费方而不是抛出，稳定的 `code`
  （`AUTH` / `QUOTA` / `RATE_LIMIT` / `CONTEXT_WINDOW_EXCEEDED` / `EMPTY_RESPONSE` / …）是
  重试器与节点错误信息的依据。
- **配置要点**：上游默认（无配置）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-llm-deepseek`
- **seam 角色**：Service Provider（`ctx.llm` 上的 `deepseek-official` 路由）
- **决定**：必挂
- **它给会话带来什么**：所选 DeepSeek 模型收到 harness 系统提示词、消息历史、工具 schema、
  stop sequence 与调用配置；视觉模型经 Files API 引用收到保留的图片，Files 失败时整请求回退到
  内联 base64；前一 assistant 轮次的 `reasoning_content` 原文回传。推理、文本与工具参数转成
  harness chunk 交给循环。
- **理由**：这是本项目唯一的模型路由（`models` 表的 `providerId` 就是它注册的
  `deepseek-official`），默认模型 `deepseek-v4-flash-vision-exp`——多模态是扫描件逐页栅格化后
  读图的前提。`ontoflow-rpc` 的 `initialize` 留有一条兜底：`deepseek-official` 没有已注册适配器
  时以空配置挂一份本插件（组 10）；本项目的组合总是先挂了这一行，兜底从不触发。与 headless
  基线相比，本行的差别全在「连接事实从哪来」：上游 base 给这一行**不写任何配置**，端点、目录、
  思考默认值统统从 `$DSH_HOME/settings.yaml` 的 `llm-deepseek:` 分节热读；我们不挂 `settings-file`（组 7），所以 entry 配置是唯一来源，也就没有「运行中改设置、进行
  中的流保持起始事实」这回事——全局设置在受理时冻结进组合，一次运行从头到尾一个版本，正是
  AGENTS.md 说的「运行持有它启动时的快照」。凭据只以引用名进入（ADR-0006）：`apiKeyEnv` 每次
  请求经 `ctx.credentials` 解析，值来自 spawn 时注入的环境白名单，配置文件、日志、运行目录里
  永远只有名字；密钥缺失以 `MISSING_CREDENTIAL` 点名配置入口失败、格式非法以
  `INVALID_CREDENTIAL` 失败且不泄露任何片段，路由保持注册。
  两条上游行为值得知道：一、`reasoningEffort` 省略即 `high`，且 `agent/request` 可以按步替换——
  `ontoflow-rpc` 无条件覆盖它（组 10），所以这里的默认值只在 Action 没声明思考强度时生效；
  二、每个提供方请求携带 `x-deepseek-harness-user-id`，值来自 `$DSH_HOME/.anonymous-user-id`
  （`dsh-anonymous-user-id` 是它直接 import 的库，不是插件，不受组 8 「不挂」影响）。因为
  `DSH_HOME` 钉在 `<run>/home`，每次运行都会在那里生成一个新的随机 UUID，也就是每个运行对
  DeepSeek 而言是一个新的匿名身份；这是传输元数据，不进请求正文，模型看不见。压缩摘要请求另带
  `x-deepseek-harness-compact: 1`，宿主端可以据此把压缩流量与会话请求分开。
- **配置要点**：我们写 `apiKeyEnv`（全局设置的模型凭据引用名，默认 `DEEPSEEK_API_KEY`）与可选
  `baseURL`（全局设置的模型端点覆盖；省略时上游依次取 `$DEEPSEEK_BASE_URL` 与公开 API）。
  `entries.ts` 的 entry 生成器还接受 `maxTokens` 与 `models`，但今天的全局设置不暴露这两项，
  受理时不会写入。其余取上游默认：`thinking: enabled`、`reasoningEffort: high`、`maxTokens: 256000`、
  `streamIdleTimeoutMs: 300000`、`defaultContextWindow: 1000000`、`models` 默认公布
  `deepseek-v4-flash` / `deepseek-v4-pro` / `deepseek-v4-flash-vision-exp`（后者
  `inputModalities: [text, image]`）、`retryPolicy` 省略即 normal 模式五次。上游 base：无配置，
  一切靠 settings 分节。
- **定制**：配置。`apiKeyEnv` 由全局设置的凭据引用名给出，`baseURL` 可覆盖；值永远不进配置文件。
  为什么：凭据以引用名进入、值由 spawn 环境白名单注入（ADR-0006）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-llm-retry`
- **seam 角色**：Consumer（函数插件：`agent/request-error` waterfall 上的恢复监听器，不包装
  `ctx.llm.stream()`）
- **决定**：必挂
- **它给会话带来什么**：模型看不到重试事件、延迟、提供方错误或失败的部分输出；重试轮次从持久
  表层历史重建同一个请求，失败 chunk 绝不进入派生消息。
- **理由**：一个付费节点不该因为一次 DNS 抖动、一次 429 或一次空响应就失败，而循环自己对失败
  请求的默认行为是「保留原始失败」——重试是这行插件的事。策略不在它这里而在适配器上：
  `llm-deepseek` 未配置 `retryPolicy` 即 normal 模式，对 `EMPTY_RESPONSE` / `RATE_LIMIT` /
  `SERVER` / `TIMEOUT` / `TRANSPORT` 重试五次，500 ms 起、10 s 封顶、10% jitter 的指数退避，
  提供方 `Retry-After` 不超过封顶时原样采用。`AUTH` / `QUOTA` / `INVALID_CREDENTIAL` 不在集合里，
  这些错误每次都会以同样方式失败，重试只是烧时间；always 模式会无上限重试连这些在内的一切，
  我们不用。每次重试是一次新的提供方请求，可能重复计费输入 token——这是接受的代价，比一个失败
  节点便宜。它写入不进表层的 `llm/retry` 与 `llm/retry-started` 事件，Agent 轨迹面板把前者
  投影成一条「重试事实」（第几次、等多久、哪个失败）；run_events 的摘要词汇不收它。取消会中止
  活跃退避，与 `cancelled` 终态一致。
- **配置要点**：上游默认（执行器没有配置项；策略住在适配器的 `retryPolicy`，本项目未配置）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-credentials`
- **seam 角色**：Service Definition（`ctx.credentials`）
- **决定**：必挂
- **它给会话带来什么**：经消费它的模型适配器间接生效；凭据绝不进入请求前缀。
- **理由**：不是组合行，是 `credentials-local` 与 `llm-deepseek` 共同 import 的 seam 定义。它的
  三条准则就是 ADR-0006 那句「凭据只以引用名进入」的上游原文：配置只携带对机密的引用
  （`apiKeyEnv: DEEPSEEK_API_KEY`），消费方按操作解析、绝不跨操作缓存，空值等于不存在。本项目
  的全局设置把凭据表示成「引用名 + 用途」而不是值，设置页可以渲染、可以同步、轮换密钥不触碰
  任何配置，全是靠这条 seam 的形状。将来若要把值放进 OS 钥匙串而不是进程环境，换的是这条 seam
  的 provider 行，不是任何消费方。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-credentials-local`
- **seam 角色**：Service Provider（`ctx.credentials` 的文件型实现）
- **决定**：必挂
- **它给会话带来什么**：经模型适配器间接生效；存储的值为适配器请求授权，模型可见内容全归适配器。
- **理由**：与上游 base 同一行、同样无配置，但在本项目里它的四层来源实际只剩一层。上游的顺序是
  继承的进程环境（只读、始终优先）> `$DSH_HOME/.credentials.yaml`（可写）> `<调用目录>/.env`
  > `$DSH_HOME/.env`。后两层由启动器冻结的环境快照提供，「并非由产品 CLI 启动的组合只有继承
  环境这一层」——我们的 runner 不是产品 CLI，这两层结构性缺席；`.credentials.yaml` 的位置随
  `DSH_HOME`，而 `DSH_HOME` 被钉在 `<run>/home`，那里没有这个文件，托管存储为空。于是唯一能
  解析出值的层是继承环境，也就是 `launch.ts` 按全局设置的凭据引用名从 Next 进程环境挑出、显式
  注入子进程的那几个变量——机器主人 `~/.dsh/.credentials.yaml` 与 `~/.dsh/.env` 里的密钥一个也
  到不了运行里，这就是 ADR-0007 「工作区隔离」在凭据上的落点。既然只剩环境层，为什么还挂：
  `llm-deepseek` 的引用解析路径是「先 `ctx.credentials`、seam 缺席才退到 launch-environment 的
  继承环境层」，两条路在本项目里读到的是同一份环境、缺密钥时抛的也是同一条点名配置入口的
  `MISSING_CREDENTIAL`——挂不挂它，可观察行为一样。保留它的理由只有两条：base 与 headless 都
  挂它，ADR-0013 的举证责任在去掉的一方，这里没有去掉的理由；将来把值搬进 OS 钥匙串时换的正是
  这一行，seam 消费方一个不动。上游自己标注的安全边界要如实转述：`.credentials.yaml` 的 0600
  权限挡得住别的 OS 用户、挡不住模型，harness 守的只是「不把路径交给模型、不载入进程环境」；
  本项目里文件根本不存在，但凭据值确实在子进程环境里——它到不了模型的 `bash`：`dsh-subprocess`
  的 `scrubbedParentEnv()` 在每次 spawn 前丢弃形似凭据的名字（`*KEY*` 等）与所有 `DSH_*`，
  `DEEPSEEK_API_KEY` 正落在这条规则里（组 2 的 `dsh-subprocess` 行）。
- **配置要点**：上游默认——`path` = `<DSH_HOME>/.credentials.yaml`（即 `<run>/home/.credentials.yaml`，
  不存在即空存储）、`watch: true`（对该路径起一个 chokidar watcher，文件不存在照样监视）、
  `debounceMs: 100`。上游 base：同样无配置。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-session`
- **seam 角色**：核心服务（`ctx.sessions`：事件溯源的会话日志与内存存储；持久化是另一条 seam，见组 4）
- **决定**：必挂
- **它给会话带来什么**：模型收到的历史是从这份仅追加日志派生出来的——`user/message`、
  `assistant/message`、`tool/result` 表层条目原样进入请求，chunk、边界、用量等仅日志事件不产生
  消息。崩溃修复时它会合成两段模型可见文本：工具调用没记到 `tool/call` 时是
  `TOOL_NOT_STARTED`（提示可重试），记了调用没记结果时是 `TOOL_OUTCOME_UNKNOWN`（提示只重试
  只读或幂等操作）。
- **理由**：「模型可见即已记录」这条上游不变量住在这里：到达模型请求的一切都必须能从日志重建，
  `request/header` 记下系统提示词、工具 schema 与调用配置的完整快照。本项目的三条数据链路都
  建立在这份日志上：`ontoflow-rpc` 把每条 `session/event` 实时转发成 `session.event` 帧、Next
  侧到达即写 `run_events`；`node_usage` 读的是每步的 `assistant/chunk { type: 'usage' }`；
  Agent 轨迹面板从运行目录的 `sessions/*.jsonl` 投影，读的就是这套事件词汇。会话 id 由调用方选
  且假定全局唯一——我们用节点 id 做会话 id，所以 `node_usage` 的唯一键必须带 `run_id`。轮次
  结束原因是带 `kind` 标签的和类型：取消是 `{ kind: 'aborted', reason }`、失败是
  `{ kind: 'error', error }`、崩溃恢复才有 `interrupted`，这是「`cancelled` 与 `failed` 是两个
  终态」在日志层的依据。
- **配置要点**：上游默认（无配置）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-system-prompt`
- **seam 角色**：核心服务（`ctx.systemPrompt`：提示词段、工具 schema 与变量的组装注册表）
- **决定**：必挂
- **它给会话带来什么**：每次组装以 harness 身份开头（`You are an AI agent powered by DeepSeek
  Harness.`，顺序 −100），接 persona（顺序 0）与各插件的有序段（工具引导 100–199），严格插值
  `{{model}}` / `{{cwd}}`；工具 schema 是组装结果的一部分。空段消失。
- **理由**：这是「模型看见什么规范」的唯一出口，也是本项目与 headless 基线在配置上真正分道的
  一行。上游 base 给 `persona: ''`，headless 与 web 都覆盖成 `You are a coding agent powered by
  the {{model}} model. Your working directory is {{cwd}}.`；我们回到空串。理由：一切规范以文件

  不在工作区里的规范。上游把 persona 定性为「部署方编写、只来自配置／组合」，本项目的「部署」是
  每次运行现生成的组合，留空比每次生成一句固定话更诚实。保留上游默认的 harness 身份句
  （`includeHarnessIdentity: true`）：上游说只有「兼容性部署拥有完整系统提示词」时才关，我们
  不是；它是每次请求的固定小成本，前缀稳定利于缓存。`toolOrder` 不配置，工具按名字典序——
  上游说重排只改缓存形状不改语义，且配置错误要到首轮组装才暴露，没有理由碰。作用域层由这里
  提供：`agent.ctx` 上注册的段只对该 agent 生效并遮蔽同名全局段，`ontoflow-rpc` 的结构化输出
  指令段（组 10）就是这样按会话挂上去的。
- **配置要点**：`persona: ""`。上游 base：`persona: ''`；headless 基线：上文那句编码 persona。
  `includeHarnessIdentity` / `includeRuntimeContext` / `toolOrder` 取上游默认（`true` / `true` /
  缺席即字典序）。
- **定制**：配置。persona 固定为空串。为什么：一切规范以文件进入（工作区 AGENTS.md、Action
  规则），运行目录里能查到模型看见的每一句话。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-tools`
- **seam 角色**：核心服务（`ctx.tools`：作用域化的工具注册表与带把关的执行流水线）
- **决定**：必挂
- **它给会话带来什么**：native 模式下模型看到每个可见定义的确切名称、描述与 JSON Schema，按
  agent 作用域的限制、遮蔽与扩展注册决定最终集合；抛出或被拒的调用统一变成 `Error: <message>`。
- **理由**：Action 级收窄（ADR-0015）与 Tool 契约（ADR-0017）全部建立在这一行的三个约定上。
  第一，`restrict(filter)` 是 agent 作用域的允许／拒绝掩码，注册时对全局工具面做快照：deny 掩码
  会接纳之后出现且未点名的工具，allow 掩码会排除之后出现的名字，未知名字与空筛选直接拒绝——
  这解释了为什么 `ontoflow-rpc` 先把 deny 清单与已注册面求交再 `restrict`、且用第二层
  `guard()` 按名拒绝执行：只靠创建期快照会被晚注册的工具（如迟连的 MCP 桥接工具）击穿。上游对
  `restrict` 的定性要照抄：「这是实时可见性组合，不是权限边界」；所以「全局停用的工具从会话的
  工具清单消失而不是调用时报错」的证据是它不在 `request/header` 里，而 guard 才是执行期的最后
  一道拒绝。第二，`register()` 要求规范的 `output { schema, render }` 声明，`render` 的签名是
  `(args, value)`——写成 `(value)` 会渲染出 `undefined`、以「非无损 JSON」失败，读起来像序列化
  bug。第三，`assertSupportedJsonSchema()` 强制的 JSON Schema 子集比 JSON Schema 窄，类型数组
  被拒，插件加载即失败、整个运行在任何节点开跑前倒下（见 `dsh-app-boot`）；`ontoflow-rpc` 对
  RPC 送来的 `outputSchema` 先过 `assertObjectJsonSchema` 再注册，走的是同一套子集。定义里的
  `timeoutMs` 只是声明，注册表不执行截止——强制靠 `tool-call-timeout-policy`（组 3）。
  与 headless 基线的差别只在呈现模式：headless 把 `mode` 接到 `DSH_TOOLS_MODE`（未设即
  native）并挂了 Code Mode 的 worker；我们不配置 `mode`、不挂 code-runtime（组 2），模型只有
  原生 Function Calling。上游自己把那个环境开关标注为「临时」。
- **配置要点**：上游默认（无配置，`mode: native`）。上游 base：无配置；headless：
  `mode: !!js process.env.DSH_TOOLS_MODE`。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-agent`
- **seam 角色**：核心服务（`ctx.agents`：`Agent` 接口、注册表、发起方作用域与 `agent/*` 事件词汇）
- **决定**：必挂
- **它给会话带来什么**：接口本身不贡献固定文案；经 `agent.ctx` 的注册可以为一个 agent 遮蔽提示词
  段或工具，或在未发布的 setup 期间安装只对该 agent 生效的拦截器。
- **理由**：`ontoflow-rpc` 只注入这一个服务（`inject = ["agents"]`），每个 Action 会话都经
  `ctx.agents.create({ sessionId, meta: { cwd }, agentOptions, setup })` 懒创建。上游对这条工厂
  API 的三点约定决定了本项目的形状：一、`setup(agentCtx)` 在 agent 发布前运行，是「受信任、仅
  用于组合的同进程代码」，这就是 ADR-0015 所说的会话创建窗口——步数上限、思考强度、工具收窄、
  技能注册都在这里挂到该会话自己的作用域上，任一步失败创建整体回滚，不发布半成品会话；二、
  `AgentOptions` 只有 provider / model / maxTokens，所以思考强度要经 `agent/request` waterfall
  而不是选项；三、`agent/pre-step` 的 `PreStepDecision` 允许 `{ kind: 'reject' }`，拒绝后已领取
  批次不保留、轮次以无步骤关闭——步数守卫用它当场收束回合，会话没交出结构化输出，节点判失败。
  `AgentHandle.dispose()` 是消费方能力，`session/close` 用它；`agent.cancel(cause)` 默认清空
  inbox 并协作中止，`session/cancel` 用它；`agent/status` 的 `running` / `idle` 转换被转发成
  `session.status` 帧，是 Next 侧判断「这一轮结束了」的依据。上游明说 `running` 描述的是驱动器
  的 drain 区间而不是「轮次仍开着」的证明，只有拥有完整区间的调用方才能把它概括成一次运行的
  结果——引擎是每个会话唯一的提示者，正是这个「拥有完整区间的调用方」。
- **配置要点**：上游默认（无配置）。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-agent-loop`
- **seam 角色**：Service Provider（`ctx.agentLoop`；实现 `AgentFactory` 并经 `ctx.agents.setFactory`
  注册，是 harness 里唯一含具体循环逻辑的包）
- **决定**：必挂
- **它给会话带来什么**：每步发送针对该 agent 呈现的系统提示词、可见工具 schema 与会话派生消息，
  提供 `provider` / `model` / `cwd` 变量值，不添加固定文案。取消后未分发的工具调用在历史里留下
  `Error: tool call aborted before dispatch`。
- **理由**：一切的基础——步骤 = 一次模型请求加它调用的工具，轮次 = 零到多个步骤；`agent/pre-step`
  → `step/start` → `agent/request` → `llm/stream` → `assistant/message` → `tool/*` → `step/end`
  的顺序由它驱动，每次成功的提供方调用恰好追加一个 `assistant/message` 锚点（用量可用时随
  锚点记下）。上游自己
  列在「已知限制」里的一条是本项目最在意的：**没有内置轮次预算**，工具调用或 steering 会让当前
  轮次一直继续，限制失控轮次的策略必须从既有扩展点执行——所以一个空转的 agent 会烧 token 直到
  节点墙钟超时，`ontoflow-rpc` 在会话作用域上注册的 `agent/pre-step` 守卫（`NODE_MAX_STEPS`）
  就是补这一条（组 10）。`agents: []` 与 base 相同：启动期不创建任何 agent，会话全部由 RPC 在
  `session/prompt` 时按各自的 Action 定义懒创建——这与 headless 基线是同一形状，headless 运行
  器同样在 `agents: []` 之上经 `ctx.agents.create` 程序化建一个 agent，差别只在谁提交消息
  （RPC 帧还是 argv 任务）、setup 里装的是模型选择还是节点作用域。`cwd` 由 `meta.cwd` 给出
  且只作用于全新会话，我们传工作区目录，`{{cwd}}` 变量与 bash 的 cwd 因此一致；
  `maxParallelToolCalls` 默认 10，并行安全的工具调用用滚动池、独占调用是屏障，我们不改。
  `resumeSessionId` 那条路径本项目不用：每轮都是全新会话，上一轮的产物经工作区文件传给下一轮
  （ADR-0008），不靠会话记忆。
- **配置要点**：`agents: []`；`maxParallelToolCalls` 取上游默认 10。上游 base：同样 `agents: []`。
- **定制**：配置。agents 固定为空数组，会话全部由 RPC 懒创建。为什么：启动期不创建任何 agent；
  每个 Action 的会话在 session/prompt 时按自己的定义创建。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-scope`
- **seam 角色**：库（按 agent 的作用域注册原语，无 ctx 键）
- **决定**：必挂
- **它给会话带来什么**：无直接影响；它决定「经 `agent.ctx` 的注册只对这个 agent 可见、随这个
  agent 释放」这件事成立。
- **理由**：不是组合行，是 `dsh-agent` / `dsh-tools` / `dsh-system-prompt` / `dsh-skill` 共同
  依赖的底层原语——`createScope(ctx, key)` 造出带标签的上下文，注册视图沿父链向下继承、事件
  放行沿链向上扩展，agent loop 为每个存活 agent 创建一个作用域。本项目会话级收窄的全部
  （工具掩码、guard、结构化输出工具、作用域技能、pre-step 与 request 监听）都是这个作用域上的
  注册，所以关闭会话就是撤销一切、不留残余。两条上游定性要记住：其一，「作用域用于路由受信任的

  「只有感知作用域的表层才会隔离状态」，经作用域上下文去调用一个不感知作用域的服务，那个服务
  仍是上下文全局的。ADR-0014 引用的那条事实——子 agent 获得全新的扁平注册作用域、父级所有权
  不导入父 agent 的工具限制——就是这套原语的直接推论：新作用域没有父链，什么都继承不到。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-sdk-protocol`
- **seam 角色**：库（纯库：无插件、无 Config、无注册）
- **决定**：必挂
- **它给会话带来什么**：无；它定义的是面向客户端的线协议，模型可见面在协议后方的运行时插件里。
- **理由**：不是组合行，是 Next 进程与运行子进程共用的传输与类型：`JsonRpcLineTransport` 在
  调用方持有的字节流上做换行分帧的 JSON-RPC 2.0——Next 侧的 `RunProcess` 把它架在子进程的

  原样复用（组 10）。分帧规则决定了 stdout 的纪律：带 `id` 与 `method` 是请求、仅 `id` 是响应、

  （组 7 的 logger-console 行）。`SessionPromptResult.messageId` 只标识入队的用户消息、不标识
  之后的回复或轮次结束——Next 侧等的是 `session.status` 的空闲转换，不是 prompt 的返回值。

- **理由**：与 include 同理，`boot()` 把 `Group` 与 `Include` 一并注册为 builtin——上游注释说得直白："一个 group 行是一份组装把一个提供方与它的消费方放进同一个 `isolate` realm 的方式"，这也是为什么 harness home 下的 agent preset 能用 group 行。上游用它的地方恰好都是我们不做的事：随发行版交付的四个 agent preset（`standard`、`code`、`cordis`、`minimal`）用 `cordis:group` 把 `planning`、`compaction`、`delegation`、`persistent-shell`、`filesystem` 各圈成一组；base 与 headless patch 本身不用 group。本项目的 Action 级差异不经 preset、不经 realm，而是在会话创建窗口于该会话自己的 scope 上收窄（ADR-0015：`tools.restrict` + `guard`、`agent/pre-step`、`agent/request` waterfall，组 10）；平铺清单里没有任何一行是 `cordis:group`，`plugin-inventory` 那种"跳过结构性 group 行"的逻辑在我们这里无事可做。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-home-paths`
- **seam 角色**：库（`resolveDshHome()`：显式配置 > `$DSH_HOME` > `~/.dsh`；`dshHomePath()`、`canonicalizeWatchPath()`）
- **决定**：必挂（Loader 机制或库依赖，不是可挂可不挂的组合行；本节原归组 7，按「机制/库一律归骨架」的口径迁到组 1，下文「不挂」指的是它的分层用法）
- **它给会话带来什么**：无。它只算路径。
- **理由**：不是组合行，是已挂行的共同依赖：`shell-env`、`skill-filesystem`、`attachment-local`、`credentials-local`、`agent-instructions`、`llm-deepseek` 与 `app-boot` 都经它解析 harness home。这一行值得单列，是因为它是**运行隔离的枢纽**：上游一切用户级根都从 `resolveDshHome()` 长出来，而这个函数的第二优先级是 `$DSH_HOME`——Next 侧 spawn 时把 `DSH_HOME` 注入为 `<run>/home`，于是凭据文档、附件存储、spill 根、技能的用户级根、shell 里的 `DSH_HOME` 变量全部落进运行目录，不碰机器上的 `~/.dsh`（ADR-0007）。有两行我们不信任环境变量、在 config 里再钉一次：`shell-env.dshHome` 与 `skill-filesystem` 的 `dshHome` / `agentsHome`（组 2）——后者的 `agentsHome` 不经 `resolveDshHome()`，默认取 `DSH_AGENTS_HOME` 否则 `~/.agents`，`DSH_HOME` 管不到它，实测加载过机器主人的技能。上游 README 还说明 `dshHomeDisplay()` 永不泄露绝对路径、默认显示 `~/.dsh`；本项目没有面向人的路径显示，运行详情直接给运行目录内的相对路径。
- **可按工作流切换**：否

### `@deepseek-ai/dsh-launch-environment`
- **seam 角色**：库（`launchEnvironmentOf(ctx)`：启动器冻结的分层环境快照，记住每个值来自哪一层）
- **决定**：必挂（Loader 机制或库依赖，不是可挂可不挂的组合行；本节原归组 7，按「机制/库一律归骨架」的口径迁到组 1，下文「不挂」指的是它的分层用法）
- **它给会话带来什么**：无直接影响；它是 `credentials-local`、`llm-deepseek`、`web-search-deepseek` 解析面向用户的值时读的东西。
- **理由**：产品 CLI 用它把三层环境（继承的进程环境 > `<cwd>/.env` > `$DSH_HOME/.env`）冻结成一份快照，让凭据解析说得清"这个值来自 shell 还是来自某个文件"；上游 README 明说"省略某一层是拒绝，不是降级"。本项目走的是它的**回退分支**：`launchEnvironmentOf(ctx)` 在没有启动器快照时返回只含 `process` 一层的快照，上游把这个回退写成正面陈述——"SDK 宿主或裸 `cordis.yml` 从未发现过任何文件，因此它拥有的一切确实就是它被启动时的环境"。而我们子进程的 `process.env` 是什么，由 Next 侧决定：`scrubbedParentEnv()` 洗刷后的父环境，叠上一张显式白名单——设置里登记的凭据引用名、`DSH_HOME=<run>/home`、`TMPDIR=<run>/tmp`、以及给 Tool 插件用的 `ONTOFLOW_DB_PATH` / `ONTOFLOW_DATA_DIR`。`runner.ts` 不读任何 `.env`（它自己的头注释就是这条规则），`app-boot` 的 `loadLayeredEnv` 从不被调用，因此机器上的 `~/.dsh/.env`、仓库根的 `.env.local` 都到不了子进程；凭据从 Next 进程环境按引用名挑出、只经白名单进入（ADR-0006）。"不挂"在这里的含义是：不用启动器那三层，而不是这个库不在子进程里——它作为已挂行的依赖照常装载，只是永远走单层分支。
- **可按工作流切换**：否
