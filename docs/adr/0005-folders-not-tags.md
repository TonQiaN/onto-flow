# 用单归属文件夹树而非标签组织各个库

推翻 [ADR-0003](0003-tags-not-folders.md)。实际使用中，双维度标签（业务域 × 能力类型）
让同一个 Action 同时出现在两棵子树下，浏览时重复、管理时更乱——多归属的灵活性没换来
好处，只换来"到底以哪棵树为准"的困惑。改为 Zed 式的**单归属文件夹树**：

- Action / Skill / Tool / Object Type 四个库共享同一棵树，每个库页只显示本库实体；
  Workflow 数量少、不分类，列表页只留搜索 + 排序 + 分页。
- 树里显示文件夹 + 本库实体叶子；未归类实体是根级散叶子，点叶子在右侧列表定位并高亮。
- 单选「进入」文件夹 = 右侧显示该文件夹**及全部子孙**的实体；「全部」清空筛选。
- 全套 Zed 式操作：右键新建子文件夹/重命名/删除，拖实体入文件夹，拖文件夹改层级；
  编辑器里保留只选不管理的文件夹选择器作为备选归类途径。
- 删文件夹时子文件夹与实体上移到父级（根级则变未归类），实体永不跟随删除。
- 标签系统（表、API、组件）彻底删除，不留兼容层；一次性脚本把「采购/…」业务标签
  转成文件夹并归位，「能力/…」「类型/…」「状态/…」维度全部丢弃。

理由：单归属给每个实体一个唯一位置，"它在哪"有确定答案，浏览与整理的心智模型
与 Zed / 文件管理器一致，不需要理解"看起来像文件夹但其实是标签"的折衷语义。
代价是丢掉多维分类——同一实体只能有一个位置，跨维度检索退回关键词搜索。
